# ADR-0004：会话隔离模式与跨会话意识（Awareness）

- 状态：已接受
- 相关：`kernel/context.py`、`domains/awareness/`

## 背景

需求是两种模式的并存：隔离模式下各会话互不可见；不隔离时角色**像一个人**——
在不同会话里都记得刚聊过什么、别处发生了什么，但**不能被无关会话的上下文干扰**。

拆成三条诉求：
- **(a) 隔离模式**：会话之间完全隔离
- **(b) 连续模式**：角色像一个人，跨会话知道"刚才聊过什么"
- **(c) 连续模式下不能被其他会话的上下文干扰**——最难的一条

## 依据

设计上有三条直接答案：

1. §1 第 3 条：**"共享连续性，不共享所有原文。"** 本人已授权的私聊可跨私聊端承接；
   群聊、其他人的秘密和设备观察按受众隔离。
2. §4.2：**"多端共享的是角色当前活动和同一 subject 允许的事实，不是把所有窗口
   拼成一个无限聊天记录。"**
3. §4.2：**"A 的私聊能影响角色的短时情绪，但 B 只看到允许外显的姿态，
   不能得知 A 的原话或关系内部数值。"**

所以"像人一样知道"**不是**"把所有会话拼成一个上下文"。实现方式是把
**事实与事件**与**对话状态**分开：前者可跨窗口，后者绝不。

## 决策

### 1. 三层隔离模式（per-subject）

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `sealed` | 窗口只读自己的消息；不召回长期记忆、不读胶囊、不读 awareness | 严格区隔；测试 |
| `per_window` | **默认**。窗口读自己消息 + subject 级长期记忆；群聊只读 `group_scope`/`public`；私聊→私聊交接需显式授权 | 当前已实测行为 |
| `continuous` | 在 `per_window` 之上增加 **awareness 车道**：角色知道自己刚才在别处做过什么、这个人说过什么事实 | 设计目标"像一个人" |

模式存放在 `session_policies` 表（per-subject），**不放 config revision**：
它是用户隐私选择，不是模型配置；也不能放窗口上，否则同一人不同窗口会互相矛盾。

### 2. 核心原则：跨窗口只传「事实与事件」，绝不传「对话状态」

**会跨窗口的**（awareness 条目）：
- 这个人说过的事实（`subject_fact`）
- 角色自己做过的事（`actor_activity`）

**绝不跨窗口的**：
- ❌ 另外一个窗口"上一句"说了什么（原话）
- ❌ 那个窗口的指代/代词/上下文
- ❌ 那个窗口未答的提问、草稿、半成品（`pending_elsewhere`）
- ❌ 群 A 的任何内容进群 B

第三条就是用户说的"干扰"：把未答问题带进另一个窗口，会让角色在新窗口里
追问一件对方从没提过的事。

### 3. AwarenessItem 的数据形状

派生投影，不是原文：

```text
AwarenessItem {
  item_id, subject_id
  kind: actor_activity | subject_fact | group_event
  text              # 第三人称中性摘要，绝不含某人原话
  source_window_id  # 内部溯源，不注入提示
  source_visibility # 产生时的可见范围
  audience          # 本条允许被谁看到
  created_at, expires_at
  origin            # 必须 user_statement / tool_receipt，不收 model_inference
}
```

`audience` 的判定（确定性，不看模型）：
- `subject_fact` → `subject_scoped`：只能在该 subject 的**私聊**窗口用
- `actor_activity` → `actor_private`：只能影响角色自身状态，**不得原样说出**
- `group_event` → `group_scoped`：只在该群用，不进其他群、不进私聊

### 4. 提示中的呈现（防止模型混用）

新增 `awareness` 车道，且必须**物理分隔并标注**：

```text
以下是你在别处做过的事和这个人说过的事实，仅作背景。
它们不是本轮对话内容，不要逐字复述，也不要当成对方刚说的话：
- （你在另一个私聊里得知）这个人住在杭州
- （你刚才）在另一个群回答了一个天气问题
```

与对话历史分开插入（system 消息），避免模型把背景当最新输入。
这只是**纵深措施**；真正的门在数据层（见下条）。

### 5. 真正的门是数据过滤，不是提示词

`ContextCompiler` 组装 awareness 车道时，按当前窗口类型确定性过滤：
- 当前窗口是**群聊** → 只允许 `group_scoped`（且必须是本群）+ `public`
  → `subject_fact` 和 `actor_activity` **根本不进候选集**
- 当前窗口是**私聊** → 允许 `subject_scoped`（同 subject）+ `public`
  → `group_scoped` 不进（群里的内容不带到私聊）

即：**群聊里模型看不到"这个人在私聊说过他在杭州"这条数据**，
所以它不可能说出来。不是靠它自觉。

### 6. 情绪与关系的跨窗口语义

- **情绪是 actor 级**（全局），允许跨窗口影响———这是有意为之
  "A 的私聊能影响角色的短时情绪"。这**不是干扰**，是"一个人有连续心情"。
- **关系数值是 actor↔subject 级**，但**只在私聊外显**；群聊只给
  "保持普通礼貌"（已实现）。
- **窗口短记忆/未答问题严格 window 级**，不跨窗口。

### 7. 模式切换的一致性

- `continuous → sealed`：**已有 awareness 条目立即失效**（按 subject 标记失效，
  不物理删除以保留审计）；此后不再生成。
- `sealed → continuous`：不追溯补历史；从那之后的新对话开始积累。
- `per_window ↔ continuous`：只影响 awareness 是否注入，历史消息与长期记忆不变。

**理由**：要求"隔离"时，如果旧 awareness 还在生效，等于没隔离。
撤销必须立即生效，这与 §4.2"撤权后派生投影必须失效"一致。

### 8. 与 HandoffCapsule 的关系：并存，边界不同

| | HandoffCapsule | Awareness |
| --- | --- | --- |
| 触发 | 用户显式生成（需 `memory.cross_device` 授权） | 角色自动积累 |
| 内容 | **对话状态**：话题、未答问题、短引用 | **事实与事件**：不含对话状态 |
| 时长 | 30 分钟 | 可配置，默认 7 天 |
| 作用域 | 私聊→私聊 | 按 audience 过滤 |
| 解决什么 | "刚才那个改成八点半"能接上指代 | "他知道我住杭州"能跨窗口 |

两者不重叠：capsule 管"指代承接"，awareness 管"事实与经历"。
`sealed` 模式下两者都关闭。

## 后果

**好处**：用户三种诉求各有明确落点；跨受众泄漏在数据层被排除；
模型无法通过"我知道所以我说"绕过隔离。

**代价**：awareness 需要额外的生成逻辑（从轮次派生条目）；
`continuous` 模式下提示变长（有预算约束）；模式切换要处理失效。

**未验证**：群 A→群 B 的泄漏、模式切换后的失效、真实模型是否会"逐字复述"
背景——这些都需要 W3 的专项测试。真实模型下的"不提私聊内容"已在
`per_window` 模式下实测通过（群聊问名字答"不清楚"）。

## 未采纳方案

| 方案 | 未采纳原因 |
| --- | --- |
| 把所有窗口拼成一个上下文 | 直接违反 §1 第 3 条与 §4.2；必然泄漏 |
| 只靠提示词让模型"注意别说" | 模型没有可靠的权限感；注入即可绕过 |
| 一个全局开关（隔离/不隔离） | 无法表达"私聊之间共享、群聊之间不共享"这种真实需求 |
| 用 HandoffCapsule 覆盖全部 | capsule 是对话状态，跨窗口注入未答问题正是"干扰" |

## 后续修正

主设计方向保留，但有 4 个点必须修正，均已落地：

### 1. 硬规则范围过宽（已修正）
原草案把「群聊普通聊天」判为**硬性沉默**。这里的问题是：*"没 @、没问号"一律判成
硬性不答会误伤*——「小王，你觉得呢？」是问句但未必在问机器人，反过来也成立。
**修正**：保留硬性沉默（避免刷屏是产品选择），但把「点名识别」从纯正则改为
可由连接器提供核验过的 @/reply-to 信息（`DecisionContext.mentioned` 由调用方决定），
正则只作兜底。

### 2. 软分支从未调用模型（已修正，真实缺陷）
原实现 `hard=False` 后直接返回规则默认值，`dialogue.group` 从未被调用——
等于"弹性区间"是空的。
**修正**：`_ask_group_model()` 让 `dialogue.group` 只输出 `reply`/`silence`。
约束：
- 模型不可用 / 超时（8s）/ 输出不可解析 → 一律退回规则默认值（不猜）
- 只接受两种结论；澄清与延后需要更多状态支撑，群里不用
- 失败只降级，不让整轮 500

### 3. 频率在"决定回复"时就记账（已修正，真实缺陷）
原实现在决策阶段 `mark()`，导致失败轮次也占额度。
**修正**：移到 `_mark_group_turn()`，只在流式**真正产出 delta** 后记账。

### 4. SpeakerArbiter 粒度不足（已记录，未在本轮修）
这里的问题是：
- 同一 `window_id` 的新轮次会直接续占并替换 `turn_id`
- 未取得占用的窗口，`TurnCoordinator` 仍会往输出队列推 delta

即"排队"还不能保证对外发言真串行。**已记入下一批工作**，不在视为已解决。

### 5. "延后"不该在没有持久任务时使用（采纳）
注意：*"无状态群聊中说'我等下回你'却没有任务和发送能力，是虚假承诺"*。
**当前实现**：`TurnDecision.defer` 已定义但**没有任何路径会选它**——这是刻意的，
等 Goals/Commitment 的真实投递能力接入后才启用。

## 第二轮修正：把隐私边界前移到取数处

### 原设计的缺陷

第一版把 `actor_activity` 的文字直接放进私聊提示，再靠"不要逐字复述"这类约束
限制模型。这是**把"模型能读到但不能说出"当成了可执行的隐私边界**——这条边界守不住：
中性摘要仍然携带事实，模型看到内容后可能复述、改写或据此回答；即使加发送后文本扫描，
也无法确定性识别任意改写后的语义泄漏。

确定性做法是在检索、排序和组装提示**之前**用代码核验来源、owner、身份绑定、
目标受众、授权版本、有效期和撤回状态；无权内容根本不进入该轮模型输入。

### 修正：AudienceSnapshot 作为唯一出口

新增 `kernel/audience.py`。一轮开始时冻结快照，所有会进入模型输入的内容
（长期记忆、情节、意识条目、交接胶囊）都必须过它：

可用范围 = **模式 ∩ 授权 ∩ 受众 ∩ 来源**（不是任一层级的继承）

来源核对是新增的关键一层，原先完全缺失：
- 群聊窗口：只允许 `group_scope` 且**必须就是本窗口这个群**，或 `public`
- 私聊窗口：只允许 `subject_private` / `window_private` / `public`；
  **群里说的话默认不进私聊**（要由本人明确提升，不能自动）

### 同时修掉三个真实数据泄漏

以下是实现中实际存在的缺陷（不是假想）：

| 缺陷 | 后果 | 修复 |
| --- | --- | --- |
| `worker` 提取固定写 `subject_private` | **群聊内容变成该用户的私聊事实** | 跟随来源窗口的 `source_visibility` |
| `recall` 对 `group_scope` 只按可见性过滤 | **群 A 的内容进群 B** | 新增 `source_filter`，核对来源窗口 |
| `MemoryRow` 无来源窗口/群键 | 上述过滤无从判断 | 迁移 0005 加 `source_window_id` / `source_visibility` |

另补 `AwarenessItemRow.source_event_ids` 与 `consent_revision`：
原事实被纠正/撤回时，派生条目必须能级联失效（原先缺这两列，
到期只能靠 TTL，不跟源）。

### 其他采纳的结论

- **Q2**：`subject_fact` 可跨该 subject 的**获准私聊窗口**；群里说的话默认保留
  群来源，不因说话者是本人就自动降密。已按此实现。
- **Q4**：模式放 per-subject 表是对的，但语义归属 Consent 领域；
  可用范围取交集（已实现为 `AudienceSnapshot`）。
- **Q5**：Awareness 与 HandoffCapsule **并存**，边界不同——
  Awareness 管"事实与经历"，Capsule 管"指代与未完问题"。
  Capsule 是"绝不跨窗口传对话状态"的**受控例外**，不是被 Awareness 取代。
- **Q3**：情绪可以有角色全局分量，但不能让另一窗口的具体原因/对象随之传播。
  **未完全实现**：当前 `AffectService` 仍是 actor 级、`sealed` 下也会注入，
  因此 `sealed` 目前**不能称为完全不受其他会话影响**，这是已知限制。

### 落实情况

| 待办 | 状态 | 处理 |
| --- | --- | --- |
| 1. `sealed` 仍注入全局情绪 | ✅ **已修** | 情绪拆 `global`（粗粒度趋势，可跨窗口）/ `window`（带原因，不跨窗口）；`sealed` 完全不注入；<0.15 的全局趋势也不注入（只是背景噪声） |
| 2. `HandoffCapsule` 未核对模式 | ✅ **已修** | `ContextCompiler` 走 `snapshot.allows_handoff_capsule()`：`sealed` 与群聊都不注入 |
| 3. 旧 awareness 切回来会复活 | ✅ **已修** | `set_mode` 任何切换都失效旧条目；读取时再核对 `policy_revision` 兜底 |
| 4. 缺"输出等价性"验收测试 | ✅ **已做** | `tests/integration/test_output_equivalence.py`：比较**发给模型前的完整输入**，7 项覆盖群A→群B、群→私聊、私聊→群、对照组、sealed、工具可用性、幂等性 |

第 2 条的"源/目标是否都是已绑定私聊"需要在接入多平台后按实际绑定关系细化；
单 Web 端无法验证双向绑定，属于外部前提。

### 输出等价性验收发现的泄漏

这类测试的价值在于能抓到单点测试覆盖不到的跨窗口泄漏。一个实例：

`MemoryService.recall` 里 `source_filter` 原先**只应用在 Episode 上**，
MemoryRow 的候选循环完全没过滤 → 群 A 的 `group_scope` 记忆会进群 B。

已修（在候选循环里补上 source_filter 调用）。

这条验证了 复核的判断："只测 Awareness 查询返回空，尚不足以证明整轮对话
不会串线。" 换成"比较模型实际输入"之后，漏掉的那一层立刻暴露。

### 验收方法说明

不比较模型输出文本（有随机性，不可靠），而是比较**编译后的 messages 序列**：

```python
baseline = compile(群B, "今天有人聊到猫吗")      # 群A 无数据
seed(群A, "养了一只叫团子的猫")                  # 埋入高相关数据
after    = compile(群B, "今天有人聊到猫吗")      # 群A 有数据
assert after == baseline                        # 逐条相等
```

若两轮输入逐条相等，模型不可能因该数据产生不同输出——这是确定性的、
可重复的证明，比多次采样比较输出文本更可靠。

**对照组必不可少**：`私聊A → 私聊B` 在 continuous 下必须**不同**，
否则说明 awareness 根本没生效，前面所有的"相同"都是假阴性。
