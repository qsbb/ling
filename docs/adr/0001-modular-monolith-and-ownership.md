# ADR-0001：单仓模块化单体与权威状态所有权

- 状态：已接受（2026-10-26）
- 相关：`src/ling/domains/`、`src/ling/contracts/v1.py`

## 背景

ling 需要"一个角色、一条权威时间线"，同时要能接入 Web、QQ、微信、手机、具身设备。
早期最容易犯的错是：每个入口各自维护一份对话状态，导致同一个人在 A 端和 B 端看到
不同的 ling；或者让插件/适配器直接读写领域表。

## 决策

1. **单仓模块化单体**，API 与 worker 分进程，共用一套数据库与迁移。
2. **领域各自只写自己的表**（见 ADR-0001 与 `src/ling/contracts/v1.py`）。跨域读投影可以，改别人的表不行。
3. **接入层只翻译协议**。渠道连接器不拥有第二套人格、记忆或领域库；它们把平台事件
   翻译成 `InteractionEnvelope`，把角色输出翻译成平台消息，并回报真实回执。
4. **依赖方向固定**：`api → kernel → domains → ports → infra`。领域不得 import
   渠道原生事件、其他领域私有表或适配器配置。
5. **权威状态在 PostgreSQL**：事件、投影、身份、任务、outbox、回执、审计同库。
   浏览器/手机缓存不是事实源。

## 后果

- 好处：跨端一致性靠数据库约束与单一写入方保证，不靠约定；故障边界清楚；
  迁移只有一条路径。
- 代价：单库是早期瓶颈；多实例时 `CancelRegistry` 这类内存态需要换实现
  （已在代码注释标注）。
- 约束：新增模块必须先声明 owner 与 port，再写表。第三方扩展没有
  "安装即可读写所有状态"的接口。

## 备选方案与未采纳原因

| 方案 | 未采纳原因 |
| --- | --- |
| 每端一套存储 + 同步 | 会产生多份人生，违背核心不变量 |
| 微服务 | 早期引入分布式事务与运维成本，收益不足 |
| 全事件溯源 | 过度；业务事件 + 事务投影 + 可录制模型结果已足够审计 |
| 让连接器直接写领域表 | 平台差异会污染领域模型，且无法保证受众隔离 |
