# 「检查更新」界面重设计

> 交付对象：Web 前端、API、独立更新器的实现者。范围仅为检查与呈现；不改自动更新、灰度或回滚策略。

## 结论

「关于与版本」只保留当前版本、一个结论句、一个主按钮和「上次检查」时间。
用户看到的结论只有四类：已是最新、可更新、有新版暂不可用、暂不能确认。
检查必须由用户动作触发更新器重新取目录、验证并解析 registry；读取旧 `status.json` 不算检查。
技术事实仍由更新器产生、API 白名单投影；前端不猜版本、不拼摘要、不绕过现有更新门禁。
旧安装请求 `POST /v1/version/image-update-requests` 与协议 `1` 保持不变。

## 已核对的现状与问题边界

- `AboutPage.tsx` 的「检查更新」只增加 `pollNonce`，重新 GET `/v1/version/image-update`。
- `ImageUpdateChannel.view()` 只读 `status.json`；`reason()` 把安装门禁的首个失败当页面总理由。
- `updater.py` 在启动、任务结束及空闲约每 300 秒刷新目录；远程目录失败会回退本地目录。
- 目录经 `catalog.py` 校验，条目无 digest；更新器用 `docker manifest inspect` 现场解析目标摘要。
- 更新器的 `available_targets` 含摘要为 null 的不兼容新版本；API 现有投影会整条丢掉。
- 前端 `imageUpdateTarget()` 在目录目标缺席时退回 request/task 的旧摘要，因此旧任务能冒充当前目标。
- `has_migration` 是发布元数据；代码里没有 `no_migration` 发现阶段原因码。
- 现有安装门禁、确认、`prepare → backup → migrate → switch → verify` 与成功三项核验继续有效。

## 卡片与四态

卡片首行例：「当前 v0.0.3」；第二行是下表一句话；第三行「检查于 11 月 9 日 14:20」。
这里的「最新」只指最近一次**可信目录**中没有更高版本，不声称覆盖尚未同步的发布。
按钮是卡片唯一主动作；展开「详情/诊断」和任务行的展开控件不是另一个更新动作。

| 状态 | 判定（按下文优先级） | 一句话文案 | 唯一主按钮及点击结果 |
| --- | --- | --- | --- |
| 已是最新 | 本次可信检查完成、当前版本可比较、无更高版本 | 「当前 v{current} 已是最新（检查于 {time}）。」 | 「检查更新」→ 发起按需刷新 |
| 可更新 | 有可信且兼容、摘要已解析的新版本，所有安装门禁通过 | 「发现新版 v{target}，可以更新。」 | 「更新到 v{target}」→ 先按需复查，结果仍一致才进入现有确认步骤 |
| 有新版暂不可用 | 已确认有更高版本，但没有可提交目标或安装门禁未过 | 「发现新版 v{newest}，但暂时不能更新：{一条人话原因}。」 | 「重新检查」→ 刷新目录与门禁，绝不提交安装请求 |
| 暂不能确认 | 更新器/通道不可用、目录不可信、当前版本未知或检查证据不足 | 「暂时无法确认是否有新版本：{一条人话原因}。」 | 「重试检查」→ 能写请求则刷新；不能写则重新读取连接状态 |

判定优先级：活动安装任务的进度覆盖结论展示；其后为「暂不能确认」→「有新版暂不可用」→「可更新」→「已是最新」。
活动任务不是第五种发现结果：仍保存上次发现结论，卡片暂显示「正在更新 v{version}：{阶段}」，主按钮「查看进度」。
排队任务同样显示「更新请求已提交，等待开始」，主按钮「查看进度」，不允许再发检查或安装。
任务完成后重新计算四态；旧任务收进下方历史行，不能持续压住新检查结论。
按钮的「重新检查」即使安装被禁用也应可用；只有 owner/通道写入条件不满足才退化为只读重试。
非 owner 不显示安装主按钮；使用同四态结论，但主按钮「查看详情」，不暴露请求写入口。

「详情/诊断」默认折叠，只保留：当前版本、当前 digest/commit、目录来源与检查时间、
目录状态/原因、更新器在线/状态/协议、恢复点及检查时间、新版列表及每条不可用原因、
推荐目标 digest/commit、当前请求 ID、最近任务的阶段/失败码/三项核验值。
路径、原始日志、自由格式异常与密钥不进入 API；`sha256`、协议号、原因码不出现在卡片首屏。
首屏不再堆叠三段横幅、`next_actions` 列表、安装门禁 notes 或「目标版本 sha256」字段。

## 判定数据与文案映射

API 新增白名单投影 `newer_releases`：从更新器 `available_targets` 保留每个更高版本的
`version/commit/has_migration/compatible/incompatible_reason`；`digest` 可为 null。
保留现有 `available_targets`/`target` 安装语义；摘要为空的条目**不能**进入可提交目标集合。
API 按严格 semver 选最高可信新版本；`target` 仍只能来自兼容条目，不接受任务或请求补位。
卡片当前版本与新旧比较统一采用更新器实测的 `catalog.current_version`；若它与 API 版本自报冲突，转「暂不能确认」。
若 `catalog.state != ok`、`catalog.current_version == null` 或旧更新器没有检查来源证据，
`newer_releases=[]` 不得被解读为「已是最新」。
`catalog.entries=0` 且可信检查完成、当前版本已知时，才可显示「已是最新」。
远程目录失败回退本地目录时，如果本地有新版可明确显示该新版；若没有，显示「暂不能确认」，
文案为「暂时连不上发布目录，只能看到本机保存的版本；请稍后重试。」
仅配置本地目录的内网部署，可显示「按本机发布目录，当前已是最新」，并标注来源。

同一轮里多个新版本同时受阻，先给用户当前版本**可直接升级**的最早一级；
若无可直接升级条目，显示最高新版本及阻碍，绝不提示直接跳过版本跨度。
原因优先级：更新器/目录/当前版本不可确认 → 安装中/人工门禁 → 恢复点/开关 →
可升级版本的摘要解析 → 版本跨度；同级只显示一条，详情可列其余原因。

| 机器事实 | 首屏一句话中的原因与可执行下一步 |
| --- | --- |
| `digest_unresolved` | 「新版已发布，但暂时取不到安装包；这不是你的操作问题，请稍后重新检查。」 |
| `not_in_min_from` | 「这个版本不能直接跨级安装；请先更新到页面提示的过渡版本，再检查一次。」 |
| 迁移链经只读预检证实不可用 | 「这个版本需要的数据库迁移尚未备齐；这不是你的操作问题，请等待修复后再检查。」 |
| `backup_gate_missing` | 「更新前需要一个可用备份；请先完成一次备份，再重新检查。」 |
| `update_disabled` | 「本机尚未启用网页更新；请在部署配置中启用后再检查。」 |
| `updater_offline`/状态过期 | 「更新服务暂时没有响应；请确认更新器容器在运行，然后重试。」 |
| `manual_required` | 「上次更新尚未处理完；请先展开上次更新，按提示处理后再检查。」 |
| 目录缺失/无效 | 「发布目录暂时不可用；请稍后重试，若持续如此请检查部署包。」 |

`digest_unresolved` 合并 registry 无 tag、网络不通、平台清单不可用，不能武断称「网络坏了」。
`not_in_min_from` 只有当存在可信过渡版本且确实可从当前版本安装时，才写出具体 v{step}；
否则改为「需要先安装过渡版本；当前目录没有可直接安装的一步，请等待发布者补齐。」
目前 `no_migration` 不存在，`has_migration=false` 不能翻译成「迁移无法完成」。
只有更新器通过现有发布预检得到明确迁移链缺失结论，才可加法写 `migration_unavailable`；
若迁移已尝试后发生 `migration_failed`，它是**上次任务失败**，按任务行处理，绝不冒充新版发现原因。
未知码一律退回「暂时无法确认更新条件，请重新检查」，仅在诊断里显示受白名单约束的码。

## 真正的按需检查协议

新增 `POST /v1/version/image-update-checks`，仅 owner，沿用安装写接口的会话、来源/CSRF 与 JSON 上限。
请求体固定为 `{ "check_id": "<32位小写hex>" }`，拒绝多余字段；不需要最近登录或安装风险确认。
API 不访问 GitHub、registry 或 Docker；它只把检查请求原子写入现有 requests 挂载目录。
更新器仍运行在独立 compose 项目：两个容器只靠既有 requests/status 共享卷交换请求和结果。
文件名 `refresh-<check_id>.json`，内容固定为 `schema:1, check_id, requested_at`，无 tag/URL/路径。
API 复用 `requests/.lock` 与原子临时文件 + rename；安装请求仍仅匹配 `request-*.json`。
锁内检查 `refresh-*.json`、`claimed-refresh-*.json` 和 `archive/` 中最近 30 秒的检查；
有待处理请求或 30 秒内已完成检查时返回同一个 `check_id`（200），绝不新写。
旧更新器留下的未认领文件只回同一 ID；后端不得擅自删除它来放开限流。
每个用户会话前端还需 500 毫秒去抖，点击后即刻禁用；服务端锁与 30 秒限流是最终保证。
检查请求上限一个，超龄未认领文件不能无限堆积；旧更新器不认领时不覆盖、不塞安装队列。

更新器在现有 `run_once()` 的单飞锁内优先完成/对账安装任务，再认领一个 refresh 文件。
认领仍用同目录 rename，完成后移到 `archive/`；`--once` 一轮处理一个检查后退出，常驻模式下轮询处理。
进行中的安装不启动目录刷新；检查保持排队并在任务收尾后处理，前端提示「更新结束后再检查」。
检查执行复用 `read_release_catalog()`：远程获取 → 本地回退 → `catalog.py` 校验 →
读取运行中镜像版本 → 对兼容目标执行 `docker manifest inspect`，不触发拉取、备份或切换。
此次刷新绕过**五分钟自动刷新节流**；自动刷新仍维持原间隔，检查完成重置节流计时。
检查失败仍写可读的 `status.json` 结论；永远不得用旧的兼容目标作为「本次检查发现」的目标。

`status.json` 加法新增 `catalog_check`：`check_id`、`state`（running/succeeded/degraded/failed）、
`started_at`、`finished_at`、`source`（remote/local/none）、`reason`（固定码）。
`release_catalog` 加法新增 `source` 和 `checked_at`；记录远程失败转本地的 `fallback_reason` 固定码。
状态文件顶层 `schema:1`、`protocol:1` 不变；旧更新器可以忽略 refresh 文件并继续现有安装。
API 对新增字段逐项白名单验证；缺字段时展示旧状态但不宣称「刚刚检查」或「已是最新」。
GET `/v1/version/image-update` 加法透出上述脱敏检查元数据及 `newer_releases`，仍 `no-store`。
前端用 `check_id` 匹配完成结果；状态文件 `updated_at` 变新但 ID 不匹配，不算这次完成。

点击后立刻显示「正在检查…」和「上次检查于 {time}」，不清空上次结论、目标或任务。
POST 202 仅表示已排队；前端每 2 秒读 GET，直到匹配 ID 的终态或等待 150 秒。
150 秒是**页面等待上限**而非取消请求；超时显示「这次检查还没返回，稍后会自动显示结果」。
断网或 API 读不到时保留旧结论并标注「上次结果」，禁用安装；重连后继续按 ID 核对。
远程目录失败但本地目录可用：`degraded`，显示回退说明；可安装的目标可保留，
但没有目标时不能说「已是最新」。registry 摘要失败：显示「有新版暂不可用」。
刷新文件 150 秒未被认领时，提示「更新器尚未接收检查；可能需要升级更新器，自动检查仍会继续」。
这个提示不封锁旧更新器已有的合法安装目标；点击「更新」仍走现有安装端点并受后端门禁约束。

## 任务记录与安装动作

卡片的「目标版本」只取本次可信 `target.version`；`request.target_digest` 和 `task.target.digest`
只属于任务详情。前端删除把它们回填到发现目标的逻辑，安装按钮不可从它们构造请求。
活动任务展示状态、阶段、开始时间；任务目标版本仅当可用可信目录条目的 digest 与 commit
同时匹配时显示，否则写「目标版本未记录」，不把摘要伪装成版本号。
失败或完成的旧任务默认收为一行：「上次更新（11月6日）失败：备份未完成」。
展开后显示任务 ID、目标摘要/提交、开始/结束时间、失败阶段和原因、已核验旧服务状态。
若任务是 `needs_manual` 且门禁仍在，首屏保留「上次更新需要处理」提示，不能折叠到不可发现。
失败在迁移前且旧服务已实测正常，可提示「检查条件后再试」；未实测则不得写「旧版正常」。
迁移后失败仅提示现有人工处理下一步，不引入一键回退按钮或新的回滚承诺。
成功任务须沿用 digest、commit、迁移 head 三项核验；未全部通过不能写「更新成功」。
「更新到 v{target}」先复用 30 秒内已完成的检查，否则发按需检查；版本/摘要/提交或门禁变化即停止确认。
检查一致后进入现有风险确认，提交时仍由 API 和更新器逐项复核，禁止把检查结果当安装授权。

## 为什么保留手动检查

只留「更新」按钮会让无新版、离线或内网回退目录的用户无法知道检查何时发生、是否真的联网。
因此保留手动检查，但它只在非可更新态作为主按钮；可更新态的「更新」点击先检查再确认。
离线部署仍可用本地可信目录判断可安装版本；没有远程证据时把范围说成「本机目录」。
五分钟自动检查继续提供被动发现，手动检查解决刚发布后等待和用户点了却没反应的问题。

## 可程序化验收断言

前端（`imageUpdate.test.tsx` 扩展交互测试，而非只用静态渲染）：

1. 可信检查完成、`catalog.entries=0`、当前版本已知 → 只见「已是最新（检查于…）」与「检查更新」，首屏没有 reason 码墙。
2. `target.version=v0.0.4` 且门禁通过 → 只见「发现新版 v0.0.4」和「更新到 v0.0.4」；点击先查 30 秒内检查结果，否则 POST checks，结果不变才确认。
3. 有 v0.0.4、摘要为 null、原因 `digest_unresolved` →「暂时取不到安装包」，安装按钮不存在，任务摘要不回填目标。
4. 有 `not_in_min_from`、无可用过渡版本 → 不提示直接安装 v0.0.4，给「等待补齐」一句话。
5. 旧失败任务带 `sha256:620b…`、当前无推荐目标 → 首屏没有该摘要和「目标版本」；仅有折叠的「上次更新失败」。
6. 连点检查 → 前端 500 毫秒内只发一个 POST；POST 后显示 loading 与上次检查时间，不把旧目标说成本次结果。
7. POST 超时/GET 断线 → 保留旧任务和结论、标记「上次结果」；同一 `check_id` 恢复后正常收尾。
8. 成功任务少一项核验值 → 不显示「更新成功」；`needs_manual` 的处理提示始终可见。
9. 更新器离线或当前版本与 API 自报冲突 →「暂不能确认」，不显示安装按钮；展开区仍能看诊断字段。
10. `has_migration=false` 单独出现 → 不显示迁移故障；只有明确预检失败才显示迁移不可用文案。

API（镜像通道契约测试）：

11. 首次 POST checks → requests 中仅一个合法 `refresh-<id>.json`；30 秒内再点返回同 ID 且不写第二个文件。
12. 并发两个 POST checks → 锁内最多一个待处理文件；相同待处理请求返回同一 ID。
13. 非 owner、跨站来源、无效 ID、多余字段 → 不写文件；安装请求的原有鉴权与门禁不变。
14. 摘要为 null 的新版保留在 `newer_releases` 且无可安装 `target`；未知码不透出自由文本。
15. 远程失败转本地且本地无新版本 → 不返回「已是最新」所需的可信远程检查标记。
16. 旧 `status.json` 无新增字段 → GET 正常，现有安装目标可用，检查时间为「未知」且不伪造最新结论。

更新器（`test_updater.py`）：

17. 认领一次 refresh 仅执行目录/镜像只读检查，写匹配 ID 的终态并归档；不调用安装、备份、迁移或切换。
18. 手动请求绕过 300 秒节流；无请求时仍按 300 秒刷新；30 秒限流期间不会重复访问 registry。
19. 远程失败且本地有效 → `degraded/source=local`；本地也坏 → `failed`，不沿用旧目标。
20. 有安装任务时 refresh 排队；`--once` 处理一个 refresh 后退出；旧 `request-*.json` 单飞与归档不受影响。
21. `digest_unresolved` 与 `not_in_min_from` 都保留版本和原因但无可提交 digest；迁移原因只在确有预检证据时产生。

交付检查：以上断言通过，`git diff --check` 通过；人工看 NAS 断网、空目录、新版已发布但 GHCR 无 tag、旧失败任务四个画面。
