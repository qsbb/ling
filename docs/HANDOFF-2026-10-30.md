## 1. 这是什么

`ling` 是一个**独立运行**的拟人化 AI 角色系统（不依赖 AstrBot 运行时/桥接/事件链），
对标 maibot 与 astrbot，跑在个人服务器上、单用户。

技术栈：Python 3.13 + FastAPI + Pydantic v2 + SQLAlchemy 2(async) + Alembic +
PostgreSQL；前端 React 19 + Vite（`clients/web-console`，手写路由与样式表）；用 `uv` 管依赖。

**贯穿全系统的分工原则（改动前必读）**：

- 说话风格、语气、主动性倾向 → **人设文档**（persona），不写进代码
- 正确性（隐私、回执、`model_inference` 不等于事实、L0 上限、紧急内容不能丢）→ **代码**
- 能力在代码里，**选择权属于人设/模型**

## 3. 本轮做完的事

### 3.1 仪表盘补齐到 9 个分段（`fc42e40`、`7b42bef`）

方案要求 9 段，原来只有 6 段 / 6 张卡。新增：

- `presence`（可用性）：只暴露**一个** `availability` 结论 + 精力/社交负担原始值。
  不让前端各自按数值划阈值，否则界面和提示词迟早给出互相矛盾的"她累不累"。
  `describe()` 在正常态**故意返回空串**（给提示词用，正常无需额外约束），
  首屏留白会像"没读到"，所以接口补了一句人话，实质仍是那个唯一结论。
- `agenda`（今天的安排）：日程 / 承诺 / 目标**分三个字段给，不合并**。
  计划是她"打算"做的（`tentative` 还可能变），承诺是答应了对方的事；合成一份列表
  会让人以为两者等价，用户会据此决定能不能当约定依赖。
- `timeline`（近期生活）：只给已发生事件，每条带 `origin`。内部推理不能当角色经历展示。

前端加三张卡并按"角色状态优先"重排：此刻 → 情绪/可用性 → 主动联系/安排 → 记忆 →
近期生活 → 关系/渠道。安排卡加了 `renderWhenEmpty`：日程空、承诺空、目标空是**三件事**，
用一句"没有数据"盖掉就看不出是哪种空。

### 3.2 账号页（`551e2c1`）

原来只有"首次登录强制改密"页，`POST /v1/auth/password` 早就有但**没有任何入口**。

- 后端新增 `PATCH /v1/auth/account`：改登录名要验证当前口令（cookie 被盗时改名是接管
  账号的第一步）；重名检查**不区分大小写**（`Admin` 与 `admin` 登录时看起来一样）→ 409；
  改完吊销**其它**会话、保留当前这次登录（全吊销会点一下保存就被踢下线）。
- 前端 `AccountPage`（`/settings/account`）：登录名 / 密码 / 退出登录三块，设置中心有入口，
  没填当前密码时保存按钮禁用。

### 3.3 两个真故障（`333161d`、`982f6f6`）

- **她永久不接话**：`PresenceService.settle()` 里精力**只减不增**（只有
  `energy_decay_per_hour`，没有任何恢复路径），跑到一定小时数必然落到地板，
  `availability` 永远 `resting`，`rest_may_skip` 让所有消息不进决策——外面看是
  "她突然不理我了"，日志里只有一条完全正常的 `skip_code=resting`。开发库实测第三天精力 18。
  改成两段式：精力 ≤ 25 时按 `energy_recover_per_hour`（默认 8）回升，高于阈值继续衰减，
  状态变成循环：累了 → 歇 → 回血 → 能聊。阈值抽成常量与 `view()` 共用。
- **静默留空气泡**：`turn.completed` 带 `decision: silence` + `message: null` 时，前端
  `applyFinal` 无条件 `updateActor()`，于是画出空文本角色气泡，渲染成「（无内容）已完成」，
  看着像生成失败；而"为什么没回"那条（`silence-reason`）反而没显示。改成撤掉气泡、
  把原因挂到用户那条消息上（显示「她没回：<原因>」）。

## 6. 测试纪律（这是本项目的硬要求，别退让）

1. **每条测试都要回答：把它保护的那行改坏，它会红吗？** 写完必须真的改坏验一次。
   本轮新增的 presence 两条、账号 5 条都做了负例验证（把 `energy_recover_per_hour`
   改成 0 → 两条同时红）。
2. **不许写永远为真的断言**。踩过：`if 不是总览就点进去，然后断言 URL 是总览`——
   改坏也绿；`返回条数 ≤ N` 检测不到 SQL 缺 LIMIT，改成捕获 SQL 语句断言含 `LIMIT`。
3. **负例要能区分两种坏法**。E2E 里"她不回"不能直接算过（那会把"消息被静默吞掉"
   这种真故障放绿），要断言"回了 / 没回但给了原因 / 没回也没原因=失败"三种。
4. **空数据与查询失败必须长得不一样**（`ok` / `empty` / `unavailable`），
   不许用一句"读取失败"把整页变成错误页。仪表盘每块独立降级，失败块要 `rollback`。
5. **不要依赖墙钟**。生活/作息相关测试会冻结时钟（`FROZEN_LOCAL_HOUR = 15`）。

## 7. 已知问题与待办（按优先级）

### P0（功能不正确，建议下一轮先做）

1. **部署不对齐** → §4。这是"用户看到的东西和仓库不一致"的唯一原因。
2. **主动联系的 Web 投递未在部署实例端到端验证过**。
   现状：`ling-worker-1` 每 5 分钟一条
   `proactive_dispatch_skipped reason_code=no_proactive_channel`（"没有外部主动推送渠道，
   改投 Web 会话"），但**没有候选**可派（`considered=0`）。
   已验证过的部分：手工造机会 + `dispatch_pending(..., deliver_to_web=True)` 返回
   `{'sent': 1, 'rejected': 0, 'considered': 1}` 并落库一条 `('actor', ..., 'simulated')`。
   缺的是"真实候选从哪来"：到期承诺 / 未回答问题 / `intent.tick`——线上都没有到点的。
   做法：造一条到点承诺（`CommitmentRow`，`due_at` 过去）→ 触发 `proactive.draft` →
   `proactive.dispatch` → 看 Web 会话是否多一条 actor 消息 + `proactive_dispatched` 事件。

### P1（设计债，有明确的坏味道）

3. **向量召回与 SQL 行序耦合**：`src/ling/domains/memory/service.py` 的 `recall()`

   向量路径依赖 SQL 返回顺序）。正确修法：先按 `id` 对齐再去重排序，然后在池内按时间收敛，
   现在文件里有 TODO 注释。
