# 多用户识别与区分（含同名不同人的防误判）

> **设计目标**：区分不同平台/不同账号下的同一个人，同时避免「同名不同人」的误判。

## 1. 现状（已核实的代码事实）

| 项 | 现状 |
| --- | --- |
| 身份键 | `(connector_instance, external_account_id)` → `subject_id`（`IdentityService.resolve_account`） |
| 解析前提 | 必须 `proof` 已证明（`require_proven=True`）；`pending` 的绑定**不解析** |
| 记忆隔离 | `MemoryService.recall(subject_id=...)` —— **按 subject 隔离**，不按名字 |
| 关系隔离 | `RelationshipState.subject_id` —— 同样按 subject |
| 按名字查人 | **不存在**（`IdentityService` 里只有登录用的 `User.username`） |
| 群聊窗口 | 一个群一个窗口，`window.subject_id` = 建窗者的 subject（通常是主人） |

结论：**地基是对的**——记忆/关系都以 subject 为键，没有任何按名字找人的路径。
所以"同名不同人"目前不会混。真正的问题是别的。

## 2. 三个真问题

### 2.1 群里未绑定的人整条被拒 → 她在有陌生人的群里是聋的

`bridge.handle` 第一步就 `resolve_account`，返回 `None` 直接

```
{"accepted": false, "reason": "渠道账号尚未绑定到已证明的自然人，需走绑定流程"}
```

实测：群消息来自未绑定 QQ `555000111` → 被拦下（白名单先命中，
放开白名单后会卡在未绑定）。

这意味着：**她只能听见已绑定的人说话**。朋友拉她进一个群，群里其他人说什么她都收不到。
对"像一个真人一样在群里待着"这个目标，这是硬伤。

### 2.2 缺少「只认识账号、未验证身份」的人这一档

现在只有两态：**已证明的自然人** 或 **不存在**。
现实中人是渐进的：先"群里的那个 QQ 号"，聊久了才知道是谁。

### 2.3 同名不同人现在不混，但很脆弱

不混的原因**不是**因为有防护，而是因为所有路径都碰巧用 subject 当键。
只要以后有人加一行"按名字找记忆"或"同名就合并"，立刻就混。

所以需要把它变成**被测试钉住的规则**，而不是"目前恰好没写错"。

## 3. 设计

### 3.1 铁律：身份键永远是账号，名字只是标签

- 任何"这是谁"的判断只用 `(connector_instance, external_account_id) → subject_id`
- `display_name` **允许重复**，且**永远不参与查找、去重、合并**
- 昵称是**声明**（claim），不是身份：她说"小明"时，指向的是"本群内 QQ xxx"，
  不是"所有叫小明的人"

代码层保证方式：
1. 提供 `IdentityService.resolve_account`，**不提供** `find_by_name`
2. 加一条 gate 测试：`src/ling/domains/identity/` 里出现按 `display_name`/`nickname`
   过滤的查询就红——把"不能按名字找人"变成可执行的约束

### 3.2 引入 subject 亲疏等级（不是权限，是记忆范围）

| 等级 | 含义 | 记忆范围 | 能触发跨窗召回？ |
| --- | --- | --- | --- |
| `owner` | 主人（已证明绑定） | 全部私聊记忆 | 是 |
| `known` | 群里聊过、未验证身份 | 只限**本群**内与 ta 相关的记忆 | 否 |
| `stranger` | 第一次见 | 无（只记"见过") | 否 |

落地点：`ActorAccount` 增加 `trust_level`；`resolve_account` 对未绑定账号
**自动建 `known` 级 subject**（而不是拒绝），但：

- 这类 subject 的记忆 `visibility` 只能是 `group_scope`，**不能**写 `subject_private`
- `Awareness`（跨窗事实）对 `known`/`stranger` **一律不注入**——隐私是 ling 对
  这是这类系统里最不该妥协的一条，不能为了"群里热闹"把它换掉

### 3.3 群内指代消解：同名怎么办

她在群里说"小明"时，必须能对应到**一个**账号。规则：

1. 群内**唯一**同名 → 可以直接叫名字
2. 群内**多个**同名 → 加可区分的前缀（"那个爱发猫图的小明"），或者干脆不点名
   （"你"、"刚才那位"）
3. 记忆写入时**永远**带 `subject_id`，不带名字当键 —— 所以两个小明各有一份记忆，
   互不污染

这条要在**人设层**表达（怎么称呼是表达问题），而"两个小明是两个人"要在
**代码层**保证（记忆/关系按 subject 分开）。

### 3.4 记忆里出现的名字不能当身份

一条记忆 `用户的名字是 阿澄`，只说明"这个 subject 自称叫阿澄"。
当她要判断"现在说话的是不是阿澄"时，答案是：**看账号，不看名字**。

具体到实现：记忆渲染时（`render_evidence`）已经按 `subject_id` 取的，
所以天然满足；要防的是**以后**有人写"按记忆里的名字匹配发言人"。

## 4. 落地顺序（下一轮开始）

1. `IdentityService` 加 `find_by_name` 的**禁止**测试（防回归，最便宜）
2. `ActorAccount.trust_level` + 未绑定账号自动建 `known` subject（迁移 + 服务）
3. 群聊里 `subject_id` 与 `window.subject_id` **分离**：
   - `window.subject_id` 表示"这个群属于谁"（主人）
   - 每条消息的 `subject_id` 表示"谁说的"
   - 记忆/关系用后者；隐私过滤用前者判断可见范围
4. 记忆写入侧强制：`known` subject 的记忆只能是 `group_scope`
5. 端到端：群里两个未绑定的人各自说"我叫小明" → 断言
   - 建了**两个** subject
   - 各自记忆互不可见
   - 她不会把 A 说的话算到 B 头上

## 5. 不做什么

- **不做"同名合并"**：同名不是同一个人的证据，合并必然出错
- **不让 stranger 触发跨窗召回**：那是隐私泄漏，不是"更聪明"
- **不用昵称当主键或去重键**：QQ 群昵称可以随时改，也可以完全重名

# 第二部分：同一个人，多个号 / 多个平台

> 用户问：「不同平台、相同用户，同平台、不同号、相同用户，如何设计才能明确身份还不会误判」

## 6. 好消息：schema 本来就支持

```
subjects（自然人） 1 ──── n actor_accounts（渠道账号）
```

`actor_accounts` 的唯一约束是 `(connector_instance, external_account_id)`，
**不是** `subject_id`。也就是说：一个 subject 天然可以挂 QQ 大号、QQ 小号、
微信、Telegram 四个账号。不需要改表。

`subjects.merged_into` 这个字段早就声明了，但**全代码库没有任何地方用它**——
又一个"声明了但没接线"的占位（和之前 `chunks`、`traits` 是同一类问题）。
要么实现合并，要么删掉；留着不动最误导人。

## 7. 真正的难点不是"怎么合"，是"合错了怎么办"

自动按昵称/头像/说话风格猜"这两个号是同一个人"，一定会错：
- 群昵称可以改，也可以完全重名
- 头像可以撞图
- 同一台设备上两个人轮流用不同号

一旦合错，**两个人的记忆会混在一起**——这是不可接受的隐私事故，
而且很难被发现（她突然知道 A 的私事，但没人知道为什么）。

所以设计原则是三条：

### 7.1 合并永远是**人的决定**，系统只能**建议**

系统可以产出"这两个号可能是同一个人"的候选（依据：同一个群、资料相似、
发言时间互补），但：
- 只作为**待确认建议**呈现给主人
- 主人点确认才合并
- 建议本身**不改变任何行为**

### 7.2 合并必须**可无损拆分**

这是整条设计里最关键的一点。合并之后，"她记得 A 说过的话"要在拆开后
还能分清是谁说的。做不到无损拆分，就不敢合并。

**做法：记忆记录来源账号，而不是只记 subject。**

```
memories.subject_id      当前归属的 subject（合并后是同一个）
memories.source_account  产生这条记忆的账号（"onebot:10001"）
```

- 合并 = 召回时按 subject 查（跨越两个账号）→ 她"都记得"
- 拆分 = 把 subject_id 改回去；因为 source_account 一直在，
  **每条记忆都能准确回到产生它的那个账号**
- 不作弊：不靠"窗口"反推账号——群窗口是多人的，反推不出来

**现状：`memories` 只有 `subject_id`，没有来源账号。这是第一部分没提、
但合并功能的前置条件。** 没它就实现合并，等于给自己埋一个拆不干净的地雷。

### 7.3 合并是显式动作，留痕、可审计

- 合并写一条事件（谁在什么时候把 B 合进了 A）
- 拆分同样写事件
- 两个 subject 的 `merged_into` 只做**指向**，不删数据

## 7.4 实现方式：只加指针，不动数据（已落地）

上面 7.2 写的是"合并 = 召回跨账号查"。实现时发现还能更彻底：

**合并只写一个字段 `subjects.merged_into`，一个字节的数据都不搬。**

```
subjects:
  A (owner)              merged_into = NULL   accounts: A 的号
  B                      merged_into = A      accounts: B 的号（仍在 B 名下）
  C                      merged_into = A      accounts: C 的号
```

- `resolve_account` 解析出账号所属 subject 后**跟随指针**取 canonical
  → 三个号的对话都算同一个人
- `subject_group(A)` = {A, B, C} → 召回时按这个集合查记忆
- 记忆行**始终留在产生它的 subject 名下**

于是：

| 操作 | 做什么 | 数据影响 |
| --- | --- | --- |
| 合并 B→A | `B.merged_into = A` | 0 行 |
| 拆开 B | `B.merged_into = NULL` | 0 行（另加下面一条归位） |

比"把 B 的账号记忆搬到 A"好在哪：搬运是**有损**的——搬完之后就没有信息
能说明"这行原本属于 B"，一行写错就永久串号。加指针则是纯视图，
拆开就是改一个字段。

### 合并期间写的记忆

合并那段时间，解析出的主体是 A，新记忆记在 A 名下（但 `source_account`
写着"是哪个号说的"）。拆开 B 时按 `source_account` 把落在 A 名下的
B 的记忆**送回 B**——这就是 `source_account` 那一列的用途。

### 拒绝的情形

自己并自己、目标本身已被合并（会成环）、两个已属于同一人——都在写入前拒绝。
`canonical_subject` 还带环检测：线上脏数据不能把身份解析卡死。

### API

```
GET  /v1/accounts/subjects                    现状：每个 subject 的账号与合并状态
POST /v1/accounts/subjects/merge              {source_id, target_id}
POST /v1/accounts/subjects/{id}/unmerge       拆开（含记忆归位）
```

**没有"自动合并"接口**，也不打算有。系统可以将来产出候选建议，
但合并永远需要人点一下。

## 8. 落地顺序

1. `memories` 加 `source_account`（迁移 + 写入侧填值）。**先做这个**，
   不然以后合并功能做出来也是残缺的
2. `IdentityService.merge_subjects(a, b)` / `split_subject(a, source_account)`
   —— 纯数据操作，可单测
3. 合并候选的**建议**产出（只读，不改行为）
4. 前端：待确认列表 + 合并/拆分按钮，每次操作显示将影响多少条记忆

## 9. 明确不做

- **不做自动合并**，不论证据多强。证据只能生成建议。
- **不做"同名即同一人"**。名字是标签，账号才是身份。
- **不靠头像/昵称相似度自动决策**：那是猜，而猜错要串号。

# 第三部分：识图与动图

## 10. 已实现并实测

`perception.vision` 绑定到多模态供应商（早就验证过它能看图），媒体管线本来完整，
缺的是"没人绑这个职责"。

### 动图为什么要拆帧

视觉接口对 GIF 基本只取**第一帧**。第一帧经常是片头、空白、黑场——
不拆帧就会出现"她看了动图说「这是一张黑色图片」"。

`expand_animation`：均匀取最多 4 帧（含首尾），每帧**整帧合成后转 RGB**
再编码 PNG。为什么要转 RGB：GIF 是索引色 + 局部帧 + 透明色，直接取帧会
拿到半透明残片或上一帧残留（鬼影），转完才是人眼看到的样子。

多帧时提示词也换：明确"这是同一段动图的先后帧"。不说的话模型会当成四件
不同的事，描述成"图一…图二…"。

实测（真模型）：

| 输入 | 描述 |
| --- | --- |
| 4 帧 GIF（红→绿→蓝→黄） | 这组关键帧显示画面正依次由纯红色变为纯绿色，再变为纯蓝色，最后变为纯黄色。 |
| 蓝底红圆 PNG | 图片是蓝色背景，中央有一个红色圆形。 |

两条边界仍然保留：
- 解析失败 → 原样返回单帧，**不因为拆帧失败就不描述**
- 描述恒为 `model_inference`，`fact_eligible=False`——看图是猜，不能当事实

## 11. 同一轮发现并修掉的媒体 bug

上传链路把占位 `media_ref` 写死成 `"pending:upload"`，去重键由它算出 →
**从第二张图起全都返回第一张图的证据**；而 `_by_dedupe` 还不按窗口过滤、
唯一约束也只有 `dedupe_key` 一列 → 后一个窗口拿到**前一个窗口的** evidence。

后果：消息里引用的证据属于别的会话，"能发图"看起来正常，发的永远是第一张。

修：占位 ref 带内容指纹、`_by_dedupe` 按窗口过滤、约束改成
`(dedupe_key, window_id)`（迁移 0040）。
