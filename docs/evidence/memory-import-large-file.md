# 导入旧记忆 · 大文件接续（前端）

分支 `lingxi/memory-import-web`，基线 `edb8959`（`lingxi/v0.0.15-backend-followups`）。
后端已解除文件总字节与记录总数上限，本次只改前端：同一份 `File` 走完预览与确认、
等待状态不说假进度、失败后能重试或换文件、去掉按 8 MiB / 5000 条劝人拆分的文案。

**诚实声明**：判据与实现出自同一个人，因此下文的「判据」不能证明它独立于实现。
能补救的是变异验证：每条关键断言都构造过一次会让它红的缺陷，并**观察到它真的红了**。

## 判据

| # | 输入 | 期望 | 会让它红的错误实现 |
|---|---|---|---|
| L1 | >32 MiB、>5000 条的合成档案 | 预览、确认、重复预览都能完成，三次请求体字节都等于文件真实大小 | 按 32 MiB 或 5000 条拒绝；把 `File` 读成文本再发（字节数会变）；第二次请求换了新 `File` |
| L2 | 大档案预览挂起时 | 界面说明"在做什么"并给出真实字节数，**没有百分比**；文件选择器不可用 | 只写"正在读取…"；渲染一个按时间推算的百分比 |
| L3 | 同一帧内连点三次确认 | 只发出 1 份 commit 请求 | 只靠按钮 `disabled` 防连点（同帧内两次点击都读到旧状态） |
| L4 | 预览返回 413 | 指向反代上传配置（`client_max_body_size`），保留已选文件并能「再试一次」 | 教用户用 `--limit` 拆文件；把已选文件清空 |
| L5 | 预览返回 422 `invalid_encoding` / `unsupported_archive` | 两种 detail 给出不同文案，文件标记为"这份文件用不了"并可换文件 | 所有 422 显示同一句；失败后不保留文件名 |
| L6 | 可导入 0，重复 12000 + 跳过 8047277 | 提示"已经导入过的 12000 条会跳过"，不劝人重新导出 | 只看跳过的最大项，让人白跑一遍导出脚本 |
| L7 | 375×760 + 32.5 MB 文件名 | `scrollWidth - clientWidth <= 0` | 文件名不换行，撑出横向滚动 |

## 变异验证（先定"什么算红"，再构造缺陷）

| 变异 | 结果 | 说明 |
|---|---|---|
| 去掉 `runCommit` 的 `inFlight` 守卫 | L3 **红**：`commitCalls` 由 1 变 2 | 同一帧连点确实能绕过按钮 `disabled` |
| 413 文案改回「用较小的 --limit 分段」 | L4 **红**：`client_max_body_size` 断言失败 | 断言打在文案内容上，不是"有错误框" |
| 去掉「重复优先」判断 | L6 **红**：期望「已经导入过了」得到「这批记录都不满足导入条件」 | 两种输入在"可导入 0"上结果相同，只有文案能区分 |

反例说明：如果把 L3 改成"等按钮 `disabled` 后再点"，去掉守卫仍是绿的——**那次变异先红过，
被改掉了**。所以现在的 L3 用 `element.click()` 在同一任务里连派三次。

## 真实后端实测（本机 PostgreSQL，独立库 `ling_accept_memimport`）

合成档案：33,078,823 字节、8,059,277 行，其中 12000 条合法记录，其余为 `invalid_record` 填充行。

| 步骤 | 结果 |
|---|---|
| 预览 | 200，`accepted=11994`、`duplicates=6`、`skipped=8047277`，18.9s |
| 确认 | 200，`imported=11994`，19.4s |
| 重复预览 | 200，`accepted=0`、`duplicates=12000`、`skipped=8047277`，18.9s |
| 小文件（4.9 KB / 6 条） | 预览 6 条 → 确认新增 6 条 → 重复预览 0 条 / 重复 6 |

`invalid_record` 的 8,047,277 条来自填充行（合法 JSON、不满足记录 schema），
验证了「超出单条记录校验的内容计入 `invalid_record`」这条契约。
