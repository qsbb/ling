# QQ 群内并行话题与指代：合成证据与 Ling 输入判据

> 观测对象：`de43cbe79a78e0c01f7821470500eaa04ea79497`（`main`，开始时工作树干净）。
> 本文是**只读研究 + 证据文档**，不改业务代码。
>
> 本文的对话样本全部是 **synthetic（合成）**：人物、群号、QQ 号、时间、消息 id 都是编造的，
> 没有使用任何真实群聊记录，也没有获得或处理任何用户数据。
>
> 置信度约定（与 `AGENTS.md` 一致）：
> - **已核实**：能在下文「实际 URL」列出的页面里逐字读到，或能在仓库代码里定位。
> - **推测**：由合成样本推演的行为归纳，未经真人实验。
> - **未核实**：找不到原文、仅知标题或二手转述，一律显式标注。

## (1) 数据与伦理

### 1.1 数据来源

本研究的输入只有三类：

| 来源 | 性质 | 用途 |
|---|---|---|
| 本文编写的 6 段合成对话 | synthetic，编造 | 构造「多话题交错 + 指代」的最小样本 |
| QQ 机器人官方文档（可访问） | 平台事实 | 区分单聊/群聊/频道、消息 id、被动回复、去重 |
| ling 仓库当前代码与既有 evidence | 本地可核实 | 说明 Ling 输入构造里四类标识如何落地 |

没有使用的来源：真实 QQ 群聊记录、生产库、NAS、任何含真实 QQ 号或真实昵称的数据。
按 `AGENTS.md` 的安全纪律，本文所有 QQ 号使用 `100200300` 一类的假号，
内网地址不出现，不写任何真实账号、口令或主机名。

### 1.2 伦理边界

- 群聊消息是多人内容，即使「我」是群成员，其他发言人的话也不是我的个人数据。
  未经群内告知与同意，不把原始聊天记录抄进代码、测试、issue 或公开文档。
- 因此本文不引用任何真实对话。合成样本用虚构昵称（阿岚、小满、老周、Kiki）与虚构群号
  （示例群 `100200300`），不映射真人。
- 若后续要做真实验证，必须先取得数据使用许可，并在此节补记许可范围、脱敏方式与保留期限；
  在此之前，本文所有「人类理想解读」都是**推测性的规范断言**，不是实测的人类行为数据。

### 1.3 本文不证明什么

- 不证明「真人一定这样读」。合成样本只能说明**在哪一种线索组合下会产生歧义**，
  不能替代人因实验。
- 不证明 QQ 客户端某种界面行为的细节（气泡如何显示、引用块长什么样）。
  用户侧功能说明原文未取得（见第 (5) 节），相关描述均标「未核实」。
- 不证明 CSCW 文献的结论。原文未取得，只列线索与本项目的相关性，标「未核实」。

## (2) 行为观察与来源

### 2.1 已核实：平台侧把「会话」「消息」「回复序号」分开

QQ 机器人官方文档（[消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)，
访问日 2026-11-22）明确写了：

- 机器人可在 **QQ 单聊、群聊、频道三种场景**收发消息；三者的发送接口与接收事件不同
  （群聊接收 `GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE`，单聊接收
  `C2C_MESSAGE_CREATE`）。
- **被动消息（回复用户）携带 `msg_id`**；响应事件则携带 `event_id`。
- 群消息支持**用群消息的 `msg_id` 调用发送单聊消息接口私聊回复该消息的发送者**，
  且与群内回复共用同一个 `msg_id` 的次数上限。
- **相同 `msg_id` 可能多次推送，请结合 `msg_seq` 去重**；被动回复时相同的
  `msg_id + msg_seq` 重复发送会失败，可递增 `msg_seq` 实现对同一消息的多次回复。

这几条对本题的意义：在平台协议层，会话种类、被回复的那条消息、同一消息的多次回复
本来就是**三种不同的标识**。把它们压成一个「消息 id」或按气泡顺序现编序号，
就会丢掉平台本来提供的消歧能力。

### 2.2 已核实：ling 里四类标识各自落在不同地方

下表是**代码定位**，不是设计愿望；括号给出可核对的文件。

| 标识 | ling 中的对应物 | 关键事实 |
|---|---|---|
| 平台聊天标识 | `window_ref`，形如 `<instance>:group:<gid>` / `<instance>:private:<uid>` | 群/私聊由**第 2 段**决定；字符串匹配 `":group:" in ref` 会把 `onebot:private:group:123` 误判成群（`src/ling/kernel/visibility.py`） |
| 内部会话 | `Window.visibility`，唯一权威值是 `group_scope` | `is_group_visibility()` 是唯一判据；未知值 fail-closed 到「非群」。「source_visibility 与 Window.visibility 不一致」被实证为不会发生，但会**一起错**（`src/ling/kernel/visibility.py`） |
| 消息级引用 | 平台 `message_id` → `[msg_id:<token>]` → `[quote:<token>]` → `OutboundMessage.reply_to` | 引用只能针对本轮真正渲染过的 id；`[quote:3]` 那种「消息序号」是线上真实出现过的瞎编，会被校验丢掉引用段而正文照发（`src/ling/kernel/context.py`、`src/ling/capabilities/tag_specs.py`） |
| 说话人识别 | `sender_subject_id` + `subjects.display_name` / 群名片 | 群聊里每条历史消息署名；群名片与人名昵称不同时写成 `名片（人名）`，避免一个人顶两个名字被当成两个人（`src/ling/kernel/context.py`） |

四类不能互相替代：
- `window_ref` 说的是**消息发到哪个聊天窗口**，`Window.visibility` 说的是**这个窗口按什么可见性规则处理**；
  前者是拼接出来的字符串约定，后者是受约束的语义列。
- `[msg_id:…]` 是**平台消息 id 的短 token**，用于引用别人；
  `<<撤回 r…>>` 用的是**本地消息 id 的另一套短号**，二者混用必然静默失效
  （`src/ling/kernel/context.py` 的 `MESSAGE_ID_MARKER` / `RECALL_REF_MARKER` 注释）。
- 说话人是**人级身份**（`subject_id`），昵称和群名片只是显示名；同一显示名可能是不同人，
  同一人可能有不同显示名。

### 2.3 已核实：ling 自己踩过与本题同构的坑

`docs/evidence/context-media-identity.md` 记录：同一分钟发出的多条媒体，渲染后**前缀逐字相同**，
造成 10 轮里 3 轮把上一轮视频说成本轮视频。修复靠的是给条目加**可区分的短号**，
而不是更细的时间戳；文档明确写「时间只到分钟」是缺陷之一，
且刻意「**不靠秒兜底**」。

这与群聊里「同一分钟多人各发一条『？』」是同一类问题：**当上下文条目不可区分，
模型会挑最近的一条顶替本条**。该结论在媒体场景是实测，迁移到群聊场景是**推测**。

另外 `src/ling/capabilities/tag_specs.py` 记录了产品裁决：`@` 只在群聊给（私聊里「回你」
没有歧义，@ 只会多一个通知），但**引用与群/私聊无关**，只问「本轮有没有可见的真实 id」。
这正是本文第 (4) 节规则建议的代码依据。

## (3) 合成群聊样本目录

记号约定（所有样本通用）：

- `G1` = 虚构群，平台群标识 `onebot:group:100200300`（**synthetic**）。
- 昵称均为虚构；QQ 号为假号。`bot` 是 Ling 自己。
- `【m<n>】` = 平台消息 id 的短 token，仅在本轮上下文里可见；
  `【回复→m<n>】` = 引用关系；`T+Ns` = 与上一条的相对时间。
- 「说话人」列写的是**人级身份**，不是显示名；显示名单独在消息里给出。

### 样本 1：@ 把「你」钉到人，但钉错了语气归属

**synthetic — 群 `G1`，说话人：阿岚 / 小满 / bot**

| 时间 | 消息序列 | 说话人 | 引用关系 |
|---|---|---|---|
| T+0 | 【m1】阿岚：明天几点集合？ | 阿岚 | 无 |
| T+6s | 【m2】小满：@阿岚 我定的是九点 | 小满 | 无 |
| T+9s | 【m3】bot：九点收到 | bot | 无 |
| T+12s | 【m4】阿岚：？ | 阿岚 | 无（表面） |

- **时间关系**：四条在 12 秒内，话题单一（集合时间），但 `？` 出现在 `@` 与回答之后。
- **人类理想解读（推测）**：m4 的 `？` 是阿岚对小满那句「我定的是九点」的质疑或追问，
  不是对 bot 的「九点收到」不满；`@阿岚` 只说明 m2 是**对小满对阿岚说的**，
  并不把后续所有消息都判给阿岚。
- **常见误读**：把 `？` 当成对紧邻上一句（bot 的「九点收到」）的否定；
  或把 `@阿岚` 当成「这条是阿岚说的」。
- **对 Ling 输入构造的判据含义**：
  1. `sender` 必须逐条绑定（`m1`=阿岚、`m2`=小满），**不能**用「上一条说话人」继承；
  2. `mentions` 是**目标字段**，不是说话人字段：`[at:100200301]` 指向阿岚，
     不等于这句话是阿岚说的（`src/ling/ports/channel.py` 的 `OutboundMessage.mentions`）；
  3. 低信息量回复不应该只靠「紧邻上一句」定位被引对象——见样本 4。

### 样本 2：引用回复跨话题，气泡相邻但语义不相邻

**synthetic — 群 `G1`，说话人：老周 / Kiki / 阿岚 / bot**

| 时间 | 消息序列 | 说话人 | 引用关系 |
|---|---|---|---|
| T+0 | 【m10】老周：周五评审改到下午了 | 老周 | 无 |
| T+20s | 【m11】Kiki：好，我改日历 | Kiki | **回复→m10** |
| T+24s | 【m12】阿岚：午饭谁一起？ | 阿岚 | 无（新话题） |
| T+28s | 【m13】Kiki：我 | Kiki | 无 |
| T+31s | 【m14】bot：那我订四份 | bot | 无 |
| T+35s | 【m15】老周：@bot 评审材料你整理吗？ | 老周 | 无 |

- **时间关系**：两个话题（评审、午饭）在 35 秒内交织；午饭话题插在评审的引用链中间。
- **人类理想解读（推测）**：m14 的「订四份」只对午饭话题有效（m12/m13），
  与 m10/m11 的评审无关；m15 虽然紧接 m14，但通过 `@bot` 明确切换到评审话题。
- **常见误读**：把 m15 当成对「订四份」的追问；或把 m14 的「四份」算进评审人数。
- **对 Ling 输入构造的判据含义**：
  1. **引用关系必须显式给出**，不能靠气泡相邻推断——本样本里 m11 有 `回复→m10`，
     而 m12 没有，尽管 m12 紧挨着引用链；
  2. 话题切换不一定要有标记，`@bot` 是一种「注意力重置」信号，应作为强线索；
  3. 会话窗口只有**一个** `window_ref` 和一个 `Window.visibility`；
     两个话题不是两个内部会话，不能靠「换窗口」来分离（这是样本 5 的反面）。

### 样本 3：昵称复用与群名片——同名人 vs 同名不同人

**synthetic — 群 `G1`，说话人：小满(100200302) / 小满(100200303) / bot**

| 时间 | 消息序列 | 说话人（人级） | 引用关系 |
|---|---|---|---|
| T+0 | 【m20】小满：快递到了吗 | 小满 A（100200302） | 无 |
| T+7s | 【m21】小满：到了，我放前台了 | 小满 B（100200303） | 回复→m20 |
| T+10s | 【m22】bot：谢啦，我去拿 | bot | 无 |

- **时间关系**：7 秒内两人用相同显示名发言，第二句带引用。
- **人类理想解读（推测）**：m21 的「我放前台了」是**另一个小满**说的；
  引用 m20 只表示「我在回答这个问题」，不表示「我是刚才问问题的那个人」。
- **常见误读**：把两句话并成同一个人的自问自答；或以为 bot 该谢的是提问者。
- **对 Ling 输入构造的判据含义**：
  1. 说话人识别的键必须是 `sender_subject_id`，显示名只是展示；
  2. 引用关系是**消息 → 消息**，不是**消息 → 人**，更不能反过来推出说话人；
  3. ling 已有对应防护：群名片与人名昵称不同时渲染成「名片（人名）」，
     避免同一人顶两个名字；但**不同人同名**仍需人级 id 才能分开
     （`src/ling/kernel/context.py:1818` 附近）。

### 样本 4：「？」「嗯」「哈哈」——低信息量回复的三种落点

**synthetic — 群 `G1`，说话人：阿岚 / 老周 / Kiki / bot**

| 时间 | 消息序列 | 说话人 | 引用关系 |
|---|---|---|---|
| T+0 | 【m30】阿岚：方案 A 还是 B？ | 阿岚 | 无 |
| T+5s | 【m31】老周：B | 老周 | 回复→m30 |
| T+8s | 【m32】Kiki：？ | Kiki | 无（**表面**） |
| T+11s | 【m33】bot：我选 B，理由待会儿说 | bot | 无 |
| T+14s | 【m34】老周：嗯 | 老周 | 回复→m33 |
| T+18s | 【m35】Kiki：哈哈 | Kiki | 回复→m32 |

- **时间关系**：18 秒，三类低信息量回复各出现一次，且分别挂在不同目标上。
- **人类理想解读（推测）**：
  - m32 的 `？` 最可能是**对 m31 那个孤零零的「B」**的追问（信息不足），
    但表面没有引用，存在真实歧义；
  - m34 的 `嗯` 有 `回复→m33`，落点是 bot 的理由，不是「同意选 B」这一结论本身；
  - m35 的 `哈哈` 有 `回复→m32`，是对 Kiki 自己那句 `？` 的自指玩笑，
    不构成新的话题贡献。
- **常见误读**：
  - 把 `？` / `嗯` / `哈哈` 当成有独立语义的「反对 / 同意 / 大笑」；
  - 在缺少引用时把 `？` 判给紧邻的 bot；
  - 把 `哈哈` 当成新话题开始，导致话题计数虚增。
- **对 Ling 输入构造的判据含义**：
  1. 低信息量消息**必须保留原始短文本**，不得在输入构造时压缩成「某人回应了某事」——
     压缩会丢掉「信息量低」这个事实本身；
  2. 有引用时以引用为准（m34、m35），**无引用时标为歧义**（m32），
     不要静默选一个最近的候选；
  3. 这类消息不应被当作可独立提炼长期记忆的事实来源。

### 样本 5：多窗口注意力切换——同名话题在两个聊天窗口里

**synthetic — 窗口 A `onebot:group:100200300`（G1）、窗口 B `onebot:group:100200400`（G2），说话人：阿岚 / 小满 / bot**

| 时间 | 窗口 | 消息序列 | 说话人 | 引用关系 |
|---|---|---|---|---|
| T+0 | A(G1) | 【m40】阿岚：明天九点集合 | 阿岚 | 无 |
| T+3s | B(G2) | 【m50】小满：明天九点集合 | 小满 | 无 |
| T+6s | A(G1) | 【m41】bot：收到 | bot | 无 |
| T+9s | B(G2) | 【m51】bot：收到 | bot | 无 |
| T+12s | A(G1) | 【m42】阿岚：@bot 我说的是 A 群 | 阿岚 | 无 |

- **时间关系**：12 秒内两个窗口出现**逐字相同**的话题与回复；最后一句才显式消歧。
- **人类理想解读（推测）**：人在两个窗口间切换时，靠的是**窗口身份**（左侧会话列表选中项）
  而不是消息内容；m42 之所以必要，正是因为内容本身已经不足以区分。
- **常见误读**：把 G2 的 m50/m51 当成 G1 话题的延续；
  或把 bot 在两个窗口的「收到」合并成一次回应。
- **对 Ling 输入构造的判据含义**：
  1. `window_ref` 必须带进每一轮的取数条件；**引用 id 的可见集合必须按窗口限定**——
     `src/ling/kernel/context.py::_has_replyable_ids` 的查询带
     `Message.window_id == window_id`，注释明确说「不带会把其他窗口的 id 也算进来」；
  2. 两个窗口的消息不能拼成一条历史流；跨窗口召回在群聊语境里应关闭或显式授权
     （`src/ling/kernel/audience.py` 的群聊来源限制）；
  3. `@` 只在群聊给，但**群聊内仍需窗口隔离**：`is_group=True` 不等于「所有群是同一个对话」。

### 样本 6：旧话题被误续——可见旧气泡 + 多人交织

**synthetic — 群 `G1`，说话人：老周 / 阿岚 / Kiki / bot**

| 时间 | 消息序列 | 说话人 | 引用关系 |
|---|---|---|---|
| T-2 天 | 【m60】老周：上次说的报销单，记得贴发票 | 老周 | 无 |
| T-2 天 | 【m61】bot：好，我记着 | bot | 回复→m60 |
| T+0 | 【m62】阿岚：新来的同学下午到 | 阿岚 | 无（新话题） |
| T+5s | 【m63】Kiki：嗯嗯 | Kiki | 无 |
| T+9s | 【m64】老周：发票呢 | 老周 | 无（**表面**） |
| T+12s | 【m65】bot：贴好了，在报销系统里 | bot | 无 |

- **时间关系**：旧话题相隔 2 天，但**旧气泡仍留在同一窗口可见**；新话题只有 12 秒。
- **人类理想解读（推测）**：m64 大概率续的是 2 天前的 m60（老周自己提的报销单），
  而不是 m62 的「新同学」；但因为它没有引用、又夹在 `嗯嗯` 之后，
  读者必须在「旧气泡」与「当前相邻」之间做一次显式判断。
- **常见误读**：
  - 把 m64 当成对新同学话题的追问，于是 m65 的「贴好了」变成完全答非所问；
  - 反过来，把 m60/m61 的旧上下文整段当成当前话题，忽略 m62 已经切题。
- **对 Ling 输入构造的判据含义**：
  1. 旧消息**可见不等于当前**：历史块应明确标注哪些是本轮新输入、哪些是之前的对话
     （`src/ling/kernel/context.py` 的 `KEY_LABELS`：`history` vs `input`）；
  2. 「被撤回」的消息要保留原文但加旁白注记「后来被撤回了」，
     否则下一轮还会把它当有效事实引用（`RETRACTED_NOTE`）；
  3. 旧话题续接应优先看**引用关系 + 同一说话人 + 时间跨度**，而不是「最近一条」；
  4. 这与 `context-media-identity.md` 的实测同构：不可区分的旧条目会被拿来顶替新条目。

## (4) 群聊规则建议：怎么跟对说话人和被引用消息

以下规则分两类：**[已核实]** = 直接对应仓库中现有判据；**[推测]** = 由合成样本归纳，
尚无人因实验支撑。

### 4.1 先分清四类标识，再谈「跟对」

**[已核实] 输入构造应分别携带，不得互相推导：**

1. **平台聊天标识**：`<instance>:group:<gid>` 形式，按段解析，第二段必须是 `group`
   且第三段非空。不要用 `":group:" in window_ref`（会把 `onebot:private:group:123`
   误判成群，且错误会落进 `Window.visibility`）。
2. **内部会话**：以 `Window.visibility == group_scope` 为唯一权威判据；
   `is_group` 是从它派生的结果，不是独立事实。未知值按私聊处理（fail closed）。
3. **消息级引用**：用**本轮真实渲染过的** `[msg_id:<token>]` 作候选；
   `[quote:…]` 只接受本轮 `visible_message_ids` 里的 token。
   「消息序号」不是 id——`[quote:3]` 是线上真实出现过的瞎编，会被静默降级。
4. **说话人识别**：键是 `sender_subject_id`；显示名（含群名片）只用于展示。
   `@` 的账号是**目标**字段，不是说话人字段。

### 4.2 跟对说话人的规则

1. **[已核实]** 逐条绑定说话人，不继承上一条。群聊历史每条消息都要署名；
   私聊不署名（那里只有一个「你」）。
2. **[已核实]** 同一人在同一提示里只能有一个名字：
   群名片 ≠ 人名昵称时写「名片（人名）」，不能变成两个名字。
3. **[推测]** 同名不同人必须靠人级 id 分开；显示名相同不构成同一人的证据（样本 3）。
4. **[推测]** `@` 只改变「这条对谁说」，不改变「这条是谁说的」（样本 1）。

### 4.3 跟对被引用消息的规则

1. **[已核实]** 引用可用性只看两件事：渠道声明了引用能力、本轮真的渲染过消息 id；
   **不看群/私聊**。没有 id 时不要宣告「可以引用」，否则模型只能瞎编。
2. **[已核实]** 引用目标必须命中本轮可见 id 表；`None`（未采集）、`{}`（采集过但没有）、
   非空（有白名单）是三态，不许合并。
3. **[推测]** 引用关系显式存在时以引用为准；没有引用时，把「回指哪条」标为歧义，
   不要静默取紧邻上一句（样本 4 的 `？`、样本 6 的「发票呢」）。
4. **[推测]** 引用是消息→消息，不是消息→人；被引用的说话人 ≠ 引用者的说话人（样本 3）。

### 4.4 话题交错与注意力切换

1. **[推测]** 话题边界不应由模型猜；输入构造要给出「哪些是这一轮新输入、哪些是历史」，
   并保留时间跨度（样本 6 的 2 天）。
2. **[已核实]** 媒体/条目必须有可区分标识；同分钟内多条不能靠时间戳兜底——
   这是 `context-media-identity.md` 的实测结论，迁移到群聊是推测。
3. **[已核实]** 多窗口按 `window_id` 隔离取数；引用 id 的可见集合不能跨窗口。
4. **[推测]** 低信息量消息（`？`/`嗯`/`哈哈`）保留原文，不压缩成摘要，
   且不作为长期记忆提炼的事实来源。

### 4.5 建议在 Ling 输入构造中加的判据（可验收形式）

> 这些是判据草案，不是本次实现；写成条件式是因为具体数值应从设计推导，
> 不能从某次运行抄来（见 `AGENTS.md`「判据里的数字，查一句从哪来的」）。

| 判据 | 通过条件 | 失败时说明什么 |
|---|---|---|
| 平台标识解析 | `onebot:private:group:123` 判为非群 | 误用子串匹配，错误会落进数据库 |
| 内部会话权威 | `window_ref` 与 `visibility` 冲突时以 `visibility` 为准 | 派生值被当成事实 |
| 引用三态 | `None` / `{}` / 非空三种输入有不同结果 | 三态被合并，静默降级 |
| 引用越窗 | 窗口 A 的 token 在窗口 B 不可引 | 可见集合未按窗口限定 |
| 说话人逐条 | 两条相邻消息不同 sender 时，渲染后各自署名 | 用上一条说话人继承 |
| 同名不同人 | 相同显示名、不同 subject_id 渲染后可区分 | 用显示名当身份键 |
| 低信息量保留 | `？` 原文进入输入，且被标为无独立事实 | 被摘要掉或当事实提炼 |
| 旧话题标注 | 历史块与本次输入分开，撤回消息带旁白 | 旧气泡被当当前事实 |

每条判据都应配一个「错误实现会让它变红」的反例；例如「引用三态」若只测
「有 id 时能引用」，那么把三态合并成布尔的实现也会绿——必须另测 `None` 与 `{}` 的区分。
