## 1. 数据性质与伦理边界（合成）

本文所有「消息序列」都是 **synthetic（合成）**，由本子智能体为说明上下文选择行为而构造。没有使用任何真实用户聊天记录、真实 QQ 号、真实内网地址或生产数据。样例里的 QQ 号统一用 `100200300`、`100200301` 这类假号；时间用相对时间（T、T+40s、次日 09:12）而非真实时间戳；场景均为虚构的日常安排。

边界分两层写清楚，不能混：

- **观察到的行为层**：只有「人如何读一串气泡」这个层面的论述，来源是公开的可 Retrieval 语料（语用学、格莱斯含义、关联理论）。这些是理论框架，不是「QQ 用户实测」。
- **未观察到的层**：本文**没有任何**真实 QQ 私聊样本、没有模型输出样本、没有截图、没有回放。下表每个样本的「人类理想解读」「常见误读」都是基于理论的**预测**（置信度：推理），不是实验事实。
- **输入事实的唯一来源**：任务规定「真实输入只能来自提示词快照/回放」。本次**没有**取得任何提示词快照或回放，因此本文所有「对 Ling 提示词的判据含义」都是**建议性判据**（应当让快照里出现什么、快照应能区分什么），**不是**对当前 Ling 实际提示词的断言。要验证当前行为，必须先拿到合法获得的 `CompiledContext` 快照（见第 5 节）。
- 不把界面截图、表情、回复气泡样式或任何「看起来像」的表现当成输入事实。气泡流只是人类读者的视觉呈现，Ling 的输入只能是结构化的消息序列 + 编译后的提示词。

## 2. 行为观察与来源

### 2.1 已取得原文的来源

**斯坦福哲学百科《Implicature》**（2024-01-10 实质修订版，检索并读取到 §1–§13 主体）：

- 会话含义（conversational implicature）依赖会话语境，不由句子的常规意义决定；同一个句子在不同问句下含义不同（例中 Barb 说「I have to work」，因 Alan 问「去不去 Paul 的派对」而被理解为「不去」）。[Stanford Encyclopedia of Philosophy: Implicature](https://plato.stanford.edu/entries/implicature/)
- 会话含义具有**可取消性（cancelability）**：「Some athletes smoke」通常含义是「不是所有」，但加上「其实所有都抽」就取消；语境也能隐式取消。这解释了「嗯」在紧接回复时和隔天开场时功能不同——后者缺少把含义绑定到上一问句的语境，含义可以被取消或改写。
- 一般会话含义（GCI）是「默认推断」，但 SEP 同时指出「默认」说法过强：同一个「Some athletes smoke」在「你知道所有运动员都抽烟吗？」下含义是「我不知道」。因此**不能把「嗯 = 确认」「？ = 追问」写成无条件默认**，必须看它紧邻的上下文。
- 关联理论（Relevance Theory）把理解描述为：听者沿最省力的路径，停在第一个满足关联期望的解释上；同时「最优关联」还受说话者能力与偏好约束。这为「人只看最近几句就把一串气泡读成一个意图」提供了理论依据：读者倾向用最近的、最省力的语境来消歧，而不是扫描整个历史。
- SEP 也明确列出理论困难：过度生成、不确定性、原则冲突。所以下面的「人类理想解读」只是最省力路径下的预测，不是唯一正确解。

**腾讯客服 QQ 专区 / QQ 官网 / 腾讯网首页**：检索到官方入口存在，但页面只提供产品导航与客服入口，**没有**关于「引用回复 / 撤回 / 合并转发」在认知层面如何被用户解读的说明。只能作为「这些功能属于 QQ 官方产品范畴」的弱证据，不能作为行为证据。[腾讯客服-QQ专区](https://kf.qq.com/product/QQ.html) · [QQ 官网](https://im.qq.com/) · [腾讯网](https://www.qq.com/)

**Ling 源码（只读，非行为来源）**：`src/ling/kernel/context.py` 的注释记录了两类已经发生过的真实工程事故，可作为「提示词必须区分哪类 id」的本地证据：引用要平台消息 id `[msg_id:…]` / `[quote:…]`，撤回要本地消息 id `[recall:…]`，两套 id 语义不同；线上曾出现模型编造 `[quote:3]` 被平台静默丢弃。撤回消息在提示词里保留原文并加旁白注记（`RETRACTED_NOTE` / `SELF_RECALLED_NOTE`），而不是删掉。这些是**代码里的事实**，不是人类行为数据。[context.py:363-405](/Users/lingxi/project/ling/src/ling/kernel/context.py#L363-L405) · [context.py:1738-1777](/Users/lingxi/project/ling/src/ling/kernel/context.py#L1738-L1777)

### 2.2 核心行为观察（理论支撑，置信度：推理）

1. **只看最近几句成串读**：关联理论预测读者停在第一个满足关联期望的解释上；在气泡流里，最近几句构成最省力的语境窗口。更早的气泡不是「消失」，而是**不再作为默认消歧材料**，除非有显式回指标记（引用、撤回提示、合并转发、话题词）强制跳回。
2. **「嗯」与「？」的功能随位置变化**：紧接回复时，上一问句提供语境，「嗯」是确认/接受，「？」是追问/要求澄清（会话含义绑定在紧邻问句上）。隔天开场时，上一问句不在最近窗口，默认绑定失效；「嗯」更像「我还在/重新开始」，「？」更像对**当前可见的最后一句**的质疑或开启新话题的信号。这是可取消性与语境依赖的直接推论，不是统计规律。
3. **引用 / 撤回 / 合并转发是「强制回跳」装置**：它们把远处旧话重新拉进当前语境。引用自带被引用文本；撤回留下「这里原来有话」的痕迹（人会去找或推断被撤内容）；合并转发把一段旧对话打包成新气泡，读者面临「这是新话题还是旧话题重放」的再判断。
4. **异步隔天开场的续旧/开新判断**：人通常依据三个线索——(a) 是否显式回指（引用、提到旧话题词、问句承接）；(b) 时间缺口是否伴随话题边界标记（早安/新问候）；(c) 上一轮是否留了未关闭的开放问题。没有回指且出现新问候时，最省力解释是开新话题；有回指或开放问题仍在时，倾向续旧。

### 2.3 来源边界声明

以上 2.2 的四条**不是** QQ 用户实验结论，也没有真实聊天记录佐证。它们是把已取得的语用学理论套到 IM 气泡流上的**推理**。要升级为「实测」，需要合法许可的数据或受控合成实验（见第 5 节）。

## 3. 合成样本目录

记号：`A` = 用户（假 QQ `100200300`）；`B` = 对方（假 QQ `100200301`）。所有内容 synthetic。`[quote …]` / `<<撤回 …>>` 只表示「这里存在平台动作」，不是真实 id。

### S1 — 连续气泡读成一个意图（看最近三句）

- 消息序列（synthetic）：
  1. A 09:10：「明天下午的评审」
  2. A 09:10：「改到 3 点了吗」
  3. A 09:10：「我把会议室订了」
  4. B 09:11：「订的哪间」
- 时间关系：前三条 1 分钟内连发，B 在约 1 分钟后追问一条。
- 人类理想解读：A 的三条合成一个意图——确认时间变更并已采取行动；B 的「哪间」承接的是第 3 条的具体行动，不是孤立地问任意会议室。
- 常见误读：把第 1 条单独当主题陈述、第 3 条当新话题；或把 B 的追问读成对第 2 条（时间）的回答。
- 对 Ling 提示词的判据含义：快照应让模型看到三条连续 A 消息与 B 的回复**在同一最近窗口内且顺序、时间接近**；若窗口切片把第 1、2 条和第 3 条分到不同可见块，模型就失去「三条是一个意图」的合并依据。判据：编译后的 `history` 车道中这四条相邻出现（允许有 id 标注），不应被摘要吞掉前两条。

### S2 — 「嗯」：紧接回复时

- 消息序列（synthetic）：
  1. B 14:02：「快递放门口了」
  2. A 14:03：「嗯」
- 时间关系：相隔约 1 分钟，紧接回复。
- 人类理想解读：「嗯」= 收到并认可，话题可关闭。会话含义绑定在 B 的告知上。
- 常见误读：读成敷衍/不满；或在无证据时扩展成「我同意你之后所有安排」。
- 对 Ling 提示词的判据含义：快照必须把 B 的告知保留为**紧邻上一句**，才能让「嗯」的确认对象可判定。若低信息轮次规则把「嗯」这一轮的自检和上一句一起跳过召回没问题，但**历史窗口不能跳过 B 那句**。判据：短回复的 `memory_recall_skipped` 可以触发，但 `history` 里仍有 B 的原话紧挨着当前输入。

### S3 — 「嗯」：隔天开场时

- 消息序列（synthetic）：
  1. B 昨日 18:40：「那方案就按 A 版定？」
  2. A 昨日 18:41：「嗯」
  3. （无消息，隔夜）
  4. A 次日 09:12：「嗯」
- 时间关系：上一轮在昨天傍晚，当前「嗯」在次日早上，中间无消息。
- 人类理想解读：隔天的「嗯」默认不再绑定昨天那个问句；更像「我还在/接着说」，需要对方或系统补语境才能续旧话题。昨天的「嗯」才是确认。
- 常见误读：把次日「嗯」也读成「确认按 A 版定」，于是继续推进旧方案，而用户可能已经换主意。
- 对 Ling 提示词的判据含义：快照需要**明确的时间缺口标记**和一个「最近话题/开放问题」来源，让模型知道当前「嗯」与昨天的问句不在同一紧邻窗口。判据：历史块里昨日与今日消息之间有可识别的日期分隔或 `created_at` 精度足以显示跨天；若只有相对序号而无时间，模型会把隔天「嗯」误接到昨天问句上。

### S4 — 「？」：紧接回复时 vs 隔天开场

- 消息序列（synthetic，同一符号两种位置）：
  - 位置甲：B 10:05：「我十分钟到」，A 10:06：「？」
  - 位置乙：B 昨日 21:30：「明天见」，A 次日 08:55：「？」
- 时间关系：甲相隔 1 分钟；乙隔夜。
- 人类理想解读：甲 = 对「十分钟到」的质疑或要求澄清（到底几点）；乙 = 重新开场，可能是对「明天见」的调侃式追问，也可能只是打招呼，必须看更早语境或后续消息才能定。
- 常见误读：把乙也当成对「明天见」的严肃质疑，回一长串解释；或把甲当成纯表情/已读。
- 对 Ling 提示词的判据含义：判据必须区分「？紧邻某条可质疑的陈述」与「？跨天且上一句只是寒暄」。快照应带 `created_at`（至少到日）与上一句内容；单看「？」本身不能决定应答类型。

### S5 — 引用回复跳回旧话

- 消息序列（synthetic）：
  1. A 昨日 16:10：「上周说的那个域名续费了吗」
  2. B 昨日 16:12：「续了」
  3. （隔夜）
  4. B 次日 10:20：「[quote 昨日 16:10 A：上周说的那个域名续费了吗] 刚想起来，确实续了」
- 时间关系：引用指向昨天的第 1 条，回复发生在次日。
- 人类理想解读：引用强制回跳；尽管物理上隔天，读者会把「域名续费」作为当前话题，B 是在补一句确认。
- 常见误读：只看最后一句「确实续了」而不看引用，当成新话题或莫名其妙的确认。
- 对 Ling 提示词的判据含义：快照里必须同时可见**引用动作 + 被引用文本/可解析的引用 id**。Ling 当前只给最近 `HISTORY_MESSAGE_ID_LIMIT = 12` 条入站消息标 `[msg_id:…]`（[context.py:381-384](/Users/lingxi/project/ling/src/ling/kernel/context.py#L381-L384)）；若被引用消息落在 12 条之外，引用文本本身仍在消息里，模型仍能回跳，但**可执行的 `[quote:…]` 句柄会失效**。判据：引用样本在快照里既有被引用正文，也有可映射回平台 id 的 token；不能只给 token 不给正文。

### S6 — 撤回造成「跳回旧话」的空洞

- 消息序列（synthetic）：
  1. B 11:00：「我昨天其实把报价改了」
  2. B 11:00：「（消息已撤回）」
  3. A 11:02：「你刚才说改了什么？」
- 时间关系：B 连发后立刻撤回第二条；A 在约 2 分钟后针对「刚才那句」追问。
- 人类理想解读：A 的追问跳回的是**被撤回前那句可见内容**；撤回提示让读者去找「刚才说了什么」，而不是忽略整段。
- 常见误读：把撤回当成「没说过」，忽略第一条，从而答非所问；或把撤回的空洞当成新话题起点。
- 对 Ling 提示词的判据含义：Ling 已有策略——撤回但已看过的入站消息保留原文并加 `（这条消息后来被撤回了）`，自己撤回的加 `（我后来撤回了这条）`（[context.py:389-404](/Users/lingxi/project/ling/src/ling/kernel/context.py#L389-L404)）。判据：快照里**不能删掉被撤回的原文**，必须带旁白注记；否则下一轮模型无法解释自己上一轮的回复，也无法回答「刚才说什么」。这是从代码事实推出的建议，不是行为实测。

### S7 — 合并转发把旧对话当作新气泡

- 消息序列（synthetic）：
  1. B 15:00：「[合并转发：聊天记录（A 与 B 昨天关于机票的 6 条对话）]」
  2. A 15:01：「看到了，那张票退了吗」
- 时间关系：合并转发发生在今天下午，内部承载昨天的 6 条记录；A 紧接着问一句。
- 人类理想解读：读者需要先判定转发内容是「旧话重放」还是「当前新信息」，A 的「那张票」指代的是转发**内部**的某条旧话，因此当前话题是旧机票话题的延续。
- 常见误读：把合并转发当成一条独立的、与历史无关的新消息，于是「那张票」无指代对象；或反过来把整个转发内部每条都当当前待办。
- 对 Ling 提示词的判据含义：快照应把「这是一段被打包的历史」与「当前输入」区分开——转发内部内容应标为历史/引用来源，而不是和当前消息平铺成同一串。判据：编译后的历史车道里，转发内部条目有来源标记（来自合并转发/旧时间），当前输入的「看到了…」单独作为本轮输入；两者不能被合并成同时间同形态的普通气泡。

### S8 — 异步隔天：续旧话题 vs 开新话题

- 消息序列（synthetic，两个变体）：
  - 变体甲（续旧）：B 昨日 20:15：「那你明天把合同发我」，（隔夜），A 次日 09:05：「[quote 昨日 20:15 B：那你明天把合同发我] 发了，你看下邮箱」
  - 变体乙（开新）：B 昨日 20:15：「那你明天把合同发我」，（隔夜），A 次日 09:05：「早，今天天气不错」
- 时间关系：两者都隔夜，差别只在次日第一句是否带显式回指。
- 人类理想解读：甲有引用回指 + 上一轮开放问题（等合同）→ 续旧；乙有开场问候且无回指 → 读者最省力地判为新话题，旧合同待办仍在但不作为当前对话主题。
- 常见误读：乙被读成「用天气回避合同」，于是追问合同；甲被读成纯打招呼，漏掉「发了」这个完成态。
- 对 Ling 提示词的判据含义：判据需要同时具备三个可见事实——(a) 跨天时间分隔；(b) 上一轮的开放问题/最近话题是否有来源；(c) 当前输入是否含回指。Ling 已有 `capsule.recent_topic` / `open_questions` 注入（[context.py:1226-1230](/Users/lingxi/project/ling/src/ling/kernel/context.py#L1226-L1230)）与低信息轮次跳过召回（[memory-context-recall.md](memory-context-recall.md)）。判据：隔天短消息若触发 `memory_recall_skipped`，仍应看到 `recent_topic/open_questions` 与历史窗口；只有当前输入带回指时，才把旧话题当作当前主题续写。

## 4. 对 Ling 的规则建议

以下都是**建议**，基于上面的推理和本地代码事实；没有一条经过真实用户数据或提示词快照验证。按优先级排列。

1. **时间必须是输入事实，不能靠模型猜**：历史消息保留 `created_at`（至少到日，最好到秒，已有 `_as_local_hint_seconds` 先例），跨天要有可识别分隔。S3/S4/S8 都依赖这一点。若提示词里只有顺序没有时间，隔天短消息无法消歧。
2. **短回复不等于无上下文**：`memory_recall_skipped=low_information` 只能跳过长期记忆检索，不能顺带把紧邻的历史窗口裁掉。S2/S3 表明「嗯」的解读完全取决于上一句是否可见。
3. **窗口切片要保住「气泡成串」**：同一分钟内连发的多条（S1）应尽量落在同一个可见历史块；若因预算必须丢弃，优先丢更早的孤立消息，而不是把一串意图从中间切开。溢出走摘要时，摘要要覆盖被丢弃段的起点，避免出现缝（代码里已有 `new_through` 用保留窗口起点推的做法）。
4. **引用要同时给「正文 + 可解析句柄」**：被引用文本必须在提示词里可见；`[quote:…]` 句柄只对最近有限条数有效（当前 12 条），超出时宁可降级为普通消息也不要让模型编 id。S5。
5. **撤回保留原文 + 旁白，不删**：入站撤回加 `（这条消息后来被撤回了）`，自己撤回加 `（我后来撤回了这条）`，并保留原文，让「刚才说什么」可回答。S6。这与现有代码策略一致，属确认而非新发明。
6. **合并转发标来源**：转发内部内容标为「来自合并转发的旧消息」，与当前输入分层，避免平铺成一串新气泡。S7。
7. **隔天开场用「回指 + 开放问题」双判据**：只有当前输入带显式回指（引用、旧话题词、问句承接）时才续旧话题；否则默认开新话题，但旧待办仍保留在记忆/开放问题里。S8。
8. **规则表述要条件式，不要「嗯=确认」式**：按项目纪律，判据写成「若紧邻可确认陈述→确认；若跨天且无回指→重新开场」，而不是写死一个默认值。关联理论与 SEP 的可取消性都支持条件式。
