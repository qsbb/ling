# 轮询/刷新与历史分页冲突：修复判据

在**看修复代码之前**写下。被测对象：`lingxi/chat-workspace-redesign` 分支，
复现日志 `.data/v0.0.15-followups/final-accept/chat-active-history.log`。

## 复现输入（与验收日志逐项对应）

- 一个会话，260 条消息，`sequence` 1..260；
- 该会话**仍有** `active_turn`（所以轮询会跑）；
- 首屏 `GET /messages?limit=100` → 返回 161..260（最新 100 条）；
- 向上一次 `before_sequence=161` → 返回 61..160；
- 向上再一次 `before_sequence=61` → 返回 1..60；
- 此时第 1 条在视图里；
- 轮询触发：`GET /messages`（不带游标）→ 返回 61..260（最新 200 条）
  外加 2 条新消息 261、262，`active_turn=null`。

## 判据（每条都写清"哪种错误实现会让它红"）

| # | 断言 | 失败的实现 |
|---|---|---|
| 1 | 轮询后第 1 条仍在视图里 | 轮询用 `setMessages(latest)` 整体替换 |
| 2 | 轮询后第 1 条仍是**同一条**（message_id 一致） | 只是碰巧把旧条目重新拼进来的"假保留" |
| 3 | 新消息 261、262 出现在视图里 | 为保留历史而干脆不合并新消息 |
| 4 | 顺序单调：sequence 升序，且没有重复 | 拼接时把最新一批整体追加到末尾/去重失效 |
| 5 | 轮询后页顶**不显示**「这里是这段对话的开头」 | 合并时顺手把 `hasMoreHistory` 按"最新一页取满与否"重算 |
| 6 | 轮询后可继续向上加载，且再加载一页不重复 | 合并破坏游标（最早 sequence 计算错） |
| 7 | 轮询期间滚动位置不跳 | 合并后不补偿 `scrollTop`（本条允许在加载更多时跳，轮询时不许） |
| 8 | `active_turn` 变为 null 后停止轮询 | 合并了消息却没接收 `active_turn` |

## 反例输入（区分力）

- **空视图 / 刚切会话**：首屏仍是整体替换，`hasMoreHistory` 由这一页是否取满决定。
  若合并函数对所有情况都生效，"首屏边界"这条会读出错误的 true。
- **服务端返回空数组**：必须保持原视图不变（不能因为一次空响应清空历史）。
- **本地未落库消息**（`sequence=null`）：排在最末，不能被"比 serverFloor 早"
  的规则误删。

## 变异（验收方自行构造，不由开发方代劳）

1. 把轮询改回 `setMessages(latest)` → 期望 #1、#5 红。
2. 合并时保留旧条目但不接收 `active_turn` → 期望 #8 红。
3. 合并后重算 `hasMoreHistory` → 期望 #5 红。

两个半成品都必须真的红；任一为绿即说明测试没覆盖到那个不变量。
