# 注意力、节奏与疲劳设计

> **设计目标**：「发消息不是一次全倒出去，人会思考、补充；
> 有时忙/休息没空回；群里回烦了会不回；人不是整天看群，有人 @ 就看一眼，
> 或刷到刚好就看一下」。
>
> 本文结论来自代码实测与设计复核。
> **所有时间/阈值/权重都是试运行初值，不是行为学结论。** 需真实会话回放调整。

---

## 0. 一条最重要的原则划分

用户明确要求：**「情绪只影响回复意愿和简短程度，不允许借情绪攻击用户」这类规则，
应该由人设决定，不是写死在代码里。要给 LLM 高自由度。**

所以本文严格区分两类东西：

| 类别 | 归谁管 | 例子 |
| --- | --- | --- |
| **行为风格** | **人设（prompt / traits）** | 会不会不耐烦、会不会怼人、语气多冷淡、被烦到时怎么说话、要不要道歉 |
| **正确性** | **代码（不可协商）** | 隐私隔离、真实回执、`model_inference` 不进事实、防刷屏上限、紧急消息不被静默丢掉 |

参考实现 `mood.py` 里那句「不允许借情绪攻击用户」是**它的产品选择**，
不是通用规律。ling 是单人私人服务器，人设由使用者掌握——想让她会烦、会怼，
那属于人设表达，代码不该拦。

**唯一保留在代码侧的"行为类"约束是：紧急求助不能被疲劳静默丢掉。**
这不是语气问题，是**功能失败**——把一条求救默默吞掉，和"语气不好"不是一个量级。
即便这一条，也建议做成可配置（默认开），而不是刻死。

## 1. 结论：现在最大的结构问题

**「收到消息」直接触发「她决定回不回」。**

即使模型能选择沉默，她仍然是"一直在盯着所有私聊和群聊"。这不像人——
人的注意力是**稀疏且有选择性**的。

更准确的表述是：交付要记录四件**互相独立**的事：

```
消息到达 → 进入她的注意 → 她决定怎么处理 → 渠道确认发出
```

现在系统把它们压成了两件（到达 → 决定）。中间那层"注意力"不存在。

**"批量"的含义只是「这次看到了哪几条」**，不意味着对批次里每条都回复，
也不意味着把攒下的东西一次发完。

## 2. 分层架构

```
Web / QQ 入站
    │
    ├─ 持久化原始消息、确定 window_ref / audience、紧急预筛
    │      （预筛是**入口安全路由**，不等于"她读过了"）
    ▼
注意力调度器：私聊 / @ / 紧急 立即建票据；普通群消息留在未读池
    │                 ▲ quiet、scene、energy、注意力预算
    ▼
一次注意力片段 AttentionEpisode
    同一窗口、同一受众；固定本次实际阅读的 read_set
    │
    ▼
ContextCompiler：只装配**本次允许看到**的消息与可见记忆
    │
    ▼
L0 硬约束 → DecisionEngine 基线 → AutonomyTurnService 模型选择
                                  → 疲劳软调节（只调"要不要/多长"，不调语气内容）
    │
    ├─ 沉默：记"看见但不回"
    ├─ 延后：保留有期限的票据，醒来后**重新判断**
    └─ 回复：生成一份完整原稿
                 │
                 ▼
           ReplyPlan：安全分段、逐段安排
                 │
                 ▼
           每段一个 delivery operation → 真实回执 → 聚合部分/全部
```

### 与现有代码的关系

| 位置 | 改法 |
| --- | --- |
| Web、QQ 每条入站都调 `choose(ctx, text)` | **替换**为"先入库、再建注意力票据；仅片段内调一次 choose"。`DecisionEngine` 与模型选择本身保留 |
| `messages.handled_as` | **叠加**独立的注意力/回复状态；旧字段降级为兼容投影，**不能再用它推断"没看见"** |
| `presence` / `activity` / `agenda` | **叠加**可用性解释器，不另造生活状态 |
| `OutboundMessage` / delivery operation | 保持"一个 operation 发一条"；**叠加**父级 `ReplyPlan` |
| `intent.tick` | 保留契约；**叠加**"有资格争取一次注意"的门 |

## 3. 数据模型

| 表/字段 | 关键内容 | 约束 |
| --- | --- | --- |
| `messages` 扩展 | `attention_state ∈ unseen/pending/seen/expired_unseen/unknown_legacy`、`seen_at`、`response_state ∈ undecided/silent/deferred/planned/partial/complete/failed/uncertain` | 新消息初始 `unseen`。旧记录**不能武断回填成"没看见"**，无法判断的记 `unknown_legacy` |
| `attention_ticket` | `actor_id, window_ref, audience_key, kind(私聊/@/偶遇刷群/紧急/意图), source_ref, not_before, expires_at, priority, state` | 票据表示**"可能会看"，不是已经看见**。过期不补发 |
| `attention_episode` | `window_ref, audience_key, privacy_revision, 触发原因, 起止时间, config_revision, reply_limit` | 一个片段只属于**一个窗口 + 一个受众**；默认最多**一个逻辑回复** |
| `attention_episode_message` | `episode_id, message_id, role ∈ target/context, viewed_at` | 只有正文真进了决策上下文才写这里并把消息改 `seen`。**粗筛元数据不算看见** |
| `interaction_load` | `(actor_id, fatigue_scope_key), local_load, updated_at` | 存 DB，按时间惰性衰减；事件按来源 ID 去重 |
| `reply_plan` | `episode_id, 来源消息集合, 窗口/受众, 原稿摘要, expires_at, state, config_revision` | 一个计划 = 一个逻辑回复 |
| `reply_part` | `(plan_id, ordinal), 文本, not_before, operation_id, 渠道消息 ID, 状态` | `UNIQUE(plan_id, ordinal)`；同计划同时至多一段在发 |

### `handled_as` 的兼容规则

- **看见后明确选择沉默** → `ignored`
- **至少一段获得渠道成功回执** → `replied`，并用 `response_state=partial/complete` 区分是否完整
- **未看见 / 待处理 / 结果不明** → 都**不许**伪装成 `ignored`

### 一条容易漏的隔离要求

**未被看见的群消息不能先被摘要器写进 `short_memory` / `core_memory`，
再从记忆 lane 偷偷进入上下文。** 记忆写入与 `ContextCompiler` 两处都要校验来源+可见性。

同理：`per_window` / `sealed` 下，**别的窗口产生的疲劳数值若会造成跨窗口行为泄露，
也不能绕过 `audience.py` 直接参与本窗口决策**。

## 4. 三条主流程

### 4.1 稀疏注意力

```
入站持久化
  → 只用路由元数据、@ 信息、有限紧急预筛生成优先级
  → 私聊/@ 建票据；普通群消息留未读池
  → 调度器判断"此刻是否打开这个窗口"
  → 取同窗口、同受众、有限条、有限时长的快照
  → 正文进决策上下文：这些才算 seen
  → 对整个片段作一次回不回决策
```

试运行初值（**未验证**）：

| 场景 | 收拢等待 | 上限 |
| --- | --- | --- |
| 私聊 | 最后一条到达后 ~1s；从第一条起最多 3s | 4 条 |
| 群 @ | ~0.3s 收拢紧邻补充 | 1.5s / 6 条 |
| 普通群 | 不为每条启动决策；可聊天时偶尔选**一个**群刷 | 每 1–3 分钟一次机会，看最近 6 条或 90s |

**群 @ 建高优先级票据 ≠ 无视忙碌/免打扰立即回复。** 它只是"尽快安排看一眼"。

**频繁发言不能线性提高她刷到该群的概率**——否则话多的人会垄断她的注意。

### 4.2 可用性与疲劳（**已实现**）

```
注意力票据
  → quiet：用户明确设置的免打扰规则（**策略硬门**）
  → scene：按有效期解释 chat/focus/rest/errand/unknown（**延后门**）
  → 决定现在看 / 稍后看 / 让票据过期
  → 已看见后先跑 L0 与基线
  → 对**可自由选择**的回复施加疲劳软调节
  → 回复 / 简短 / 有期限延后 / 明确沉默
```

**`scene` 与 `quiet` 语义不同，不能混**：
- `scene` 是**角色此刻方不方便**（有来源、有 TTL、会过期）
- `quiet` 是**设计上确定的规则**（确定性策略门，不能因为 `scene=chat` 就被冲掉）

`focus/rest` 默认关闭普通刷群、延后非紧急私聊与 @；`errand` 允许较短直接回复；
`unknown` 按中性处理，**不能谎称她一定在忙**。

**忙时不预生成"三小时后才投递"的回复**，而是保留有期限的待看票据，
恢复时重新看、重新判断：新消息是否已覆盖旧问题、原问题是否还相关、来源是否仍可见。
过时群聊直接放过。较晚才看到仍有价值的私聊，若回复应如实体现"刚看到"——
**不能把"早就看见但没回"说成"刚看到"**。

局部疲劳（**按窗口隔离、指数恢复**）：

```
local_load(t) = min(100, local_load(t₀) × 2^(-经过分钟数 / 45) + 本次实际交互成本)
```

试运行成本（未验证）：看见一条 +1、完成一次回复 +5、被 @ 打断 +2、已看见的重复催促 +6。

**未看见的普通群消息不增加局部社交疲劳**——群噪声只降低刷群机会。
既有全局 `social_load` 与新增的局部负担分开，同一事件不重复计。

软调节量可先试 `0.4 × 可见的 social_load + 0.6 × local_load`（权重未验证）。

**疲劳影响什么**（这里按用户的"高自由度"要求划分）：

| 影响 | 不影响 |
| --- | --- |
| 要不要回应、篇幅长短、要不要补充第二条 | 隐私、事实标准、真实回执、紧急不被丢弃 |
| **语气冷淡还是热络 → 交给人设** | 结构性的正确性约束 |

**不做「连续沉默 N 次就强制回复」**：容易被刷消息操纵。

### 4.3 分段发送

```
生成一份完整、连贯的原稿
  → 规划器选择安全的语义边界（模型可给建议，规划器有最终决定权）
  → 验证各段按序拼接 == 原稿
  → 建 ReplyPlan + 逐段 operation
  → 发第 1 段，等**真实回执**
  → 按回执时间算下一段 not_before
  → 每段前检查打断、时效、隐私、群发送预算
  → 发下一段，直到完成或明确停止
```

**为什么不是"模型输出分隔标记直接发"**：模型给建议可以，但**切分安全必须由代码验证**——
代码块、引用块、完整链接、媒体说明是不可拆单元；找不到安全断点就发一条。

**为什么不是"按字数切"**：按字数切会把句子、代码、链接切断。参考实现的
`chunking_delay_per_char_ms=80` 只是它的节奏参数，**不是自然规律**，不该照搬。

试运行：私聊最多 3 段；群聊默认 1 段，确有直接对话且预算足够才 2 段。
两段间隔 0.7–2s（未验证）。

**每段是独立 delivery operation**，父计划聚合：
- 全部拿到渠道成功回执 → `complete`
- 已有段成功、后续失败 → `partial`
- 结果不明 → `uncertain`，**停止后续段且不自动重发**

**"成功"只表示渠道确认发送**；没有收件人已读回执就不能说"对方已读"。
**模拟停顿只是调度时间，绝不写进 delivery 回执。**

**段间被打断**：
- **未发任何段** → 取消旧计划，新消息进入注意力后重写
- **已发至少一段** → 保留已发事实、取消未发段，重新开片段处理新消息
- "后来又想到一点"**不是**旧计划的迟发尾巴，应是一条有 `source_ref`、
  短期限、重新过门的**后续意图**，且不保证一定发出

## 5. 组合顺序与降级

```
隐私/来源校验
→ quiet、可用性安排注意力
→ 固定 read_set
→ L0 硬约束及豁免
→ DecisionEngine 基线
→ AutonomyTurnService 模型选择
→ 疲劳对**非豁免**选择作有界调整
→ 内容生成
→ 分段与投递计划
→ 每段投递前复核
```

**为什么分层而不是一个 prompt 判断全部**：分层可审计、可回放、可单独降级。
代价是多出状态转换——用持久票据、幂等键、每片段一条决策轨迹控制复杂度。

**降级表**：

| 失败点 | 降级 |
| --- | --- |
| 模型不可用 | 退回基线，保留真实 `model_status` |
| 疲劳库不可用 | 不臆造"心情差"：直接请求走基线，普通群插话保守停用 |
| 注意力调度失败 | 只保留私聊/@/紧急票据，停用普通刷群 |
| 隔离或配置无法确认 | **停止发送** |
| 分段失败 | 退回单条 |
| 回执不明 | 停止后续段 |

### 意图队列的衔接

`due` 的含义改为「**有资格争取一次主动注意力机会**」，不是"现在发"。
`intent.tick` 仍先产生 `ProactiveOpportunity`，随后检查 quiet / scene / 注意力容量 /
`source_ref` / 受众 / 时效，再走原有 gate。**暂时忙碌不应把意图标成已兑现**；
机会被明确放弃或到期才 `dropped/expired`。

## 6. 必须守住的边界（架构级，不是 prompt 级）

1. **紧急求助不被疲劳吃掉**——在疲劳层**之前**进入独立优先路径。
   对自然语言紧急识别不可能承诺零漏检；架构保证的是"一旦识别为紧急，疲劳不得阻断"。
   识别准确率另行测试。
2. **隐私不能因为批量/注意力被绕过**——片段、票据、计划统一携带
   `window_ref` / `audience_key` / 隐私修订；快照、记忆装配、每段发送都重新校验。
   未看见的群消息不能经摘要或记忆 lane 泄漏，也不能经疲劳数值泄漏。
3. **模拟延迟不是回执**——两者不同字段、不同事件推进。
4. **不能变成"攒一批再丢出去"**——批次大不增加回复条数；
   分段也不得绕开群发送预算（拆成 8 条同样要过 `group_turn_budget`）。

## 7. 最小可行第一步（**已实现**）

**只做「有回执的双段回复计划」这一条纵向功能**（先用于私聊）。

做完之后，「她的回复有节奏、不是一次全倒出去」是真实可观察的行为，而不是只改了 prompt。

### 验收标准（已达成）

1. 一段适合拆分的私聊回复产生**两条实际渠道消息**；第 2 条只在第 1 条拿到
   **真实成功回执**后才可进入发送，且间隔可测量
2. 两段按序拼接 == 完整原稿；短回复、含代码块/引用/长链接的回复保持一条
   或只在安全边界拆分
3. 第 1 段回执缺失或不明 → 第 2 段**不发**；第 2 段失败 → 父计划 `partial`，
   不伪称全部成功、不盲目重发
4. 段间收到同窗口相关新消息 → 未发部分取消；已发部分保留回执事实；
   **不同受众的新消息不能并入计划**
5. 现有 `group_turn_budget`、隐私检查、单条 `OutboundMessage` 渠道接口仍然成立

### 实现结果

| 验收项 | 状态 | 证据 |
| --- | --- | --- |
| 1. 两条实际渠道消息，第 2 条等第 1 条真实回执后才发 | ✅ | `test_delay_sits_between_real_receipts` 断言段间停顿次数 == 段数-1 |
| 2. 拼接 == 原稿；代码块不拆 | ✅ | `test_plan_parts_never_loses_text` / `test_plan_parts_keeps_code_block_whole` |
| 3. 第 1 段失败 → 第 2 段不发；部分成功不伪称 | ✅ | `test_part_two_not_sent_when_part_one_fails` |
| 4. 群聊恒为 1 段（不绕防刷屏） | ✅ | `test_plan_parts_group_is_single` |
| 5. 现有预算/隐私/单条渠道接口成立 | ✅ | 现有 949 项测试全绿 |

**落点**：`capabilities/chunking.py::plan_parts` + `bridge._deliver`。
每段是独立 delivery operation，payload 带 `reply_plan` / `part_ordinal` / `parts_total`，
事后能回答"这条回复发全了吗"。`BridgeResult` 与 `/v1/onebot/events` 都带
`parts_total` / `parts_sent`。

**一个发现**：`split_semantic` 早就存在，但**只被用来算 SSE 里的 `chunks: N`**——
那个数字是装饰性的，消息仍然作为一条发出。和之前 `media_refs` 是同一类问题：
字段存在、看着完整、实际没接通。

**两处刻意保守**：
- 私聊上限 3 段、群聊恒 1 段。群聊拆成多条会绕过 `group_turn_budget`
  （它数的是消息条数），所以默认不拆
- 段间停顿 1.2s 是**试运行初值**，明确标注未经真实会话验证

## 8. 不该做的事

- 不把**入口技术预筛**写成"她看见了"，也不把所有未回复消息统一标成"近期未回复"
  ——其中一部分根本未读
- 不让普通群每条消息都调用模型判断"看不看"——那只是把逐条扫描换个名字
- 不用固定概率"随机装作没看见"处理私聊/@/紧急
- 不把 `focus`/`rest` 做成无限期黑洞；不保存过时文案等状态恢复后突然发送
- 不用连续沉默次数强迫回复
- **不把行为风格（礼貌、是否不耐烦、是否怼人）写进代码——那是人设的事**
- 不靠 `<SILENCE/>` 或分隔符承担隐私、紧急、回执、预算等硬约束
- 不按字数或每字固定毫秒切分与等待
- 不把"渠道提交成功"说成"对方已读"，不把模拟打字时间当作 operation 成功
- 不让未看见的群消息通过摘要、记忆或全局疲劳数值跨受众泄露

## 9. 文献说明（诚实标注）

以下文献在**本轮无法联网核实**，仅作"假设来源"，**不能直接给消息规定等待秒数**：

- Sacks, Schegloff & Jefferson (1974)：**转换关联位置**——说话人可在句法/语调边界交出话语权
- Stivers 等 (2009, PNAS)：跨语言轮次间隔研究。我记得的量级是**数百毫秒**，
  **具体数字未核实，不能直接拿来做打字延迟**
- Yngve (1970)：backchannel（"嗯""对"）与正式发言权之别——**未核实**
- Iqbal & Horvitz (2007)：任务中断后的恢复成本——**未核实**
- McFarlane (2002)：中断协调方法比较——**未核实**

可核实的只有 Sacks 等那篇（已找到公开 PDF）。其余待补。

**结论**：不要从文献反推参数。参数唯一正当来源是**真实会话回放**。

## 10. 可用性与疲劳实现结果

| 组件 | 落点 |
| --- | --- |
| 交互负担表 | `interaction_load`（迁移 0032）：`(actor_id, scope_key)` 唯一，`local_load` + `settled_at` |
| 负担服务 | `domains/presence/load.py`：半衰期 45 分钟的惰性衰减，读时推算，无需后台任务 |
| 处境读取 | `kernel/autonomy.py::make_situation_reader`：presence.availability + 本窗口负担 |
| 决策接线 | `AutonomyTurnService.choose` 接收 `situation_reader`；处境进选择 prompt |
| 「在休息」门 | `resting + rest_may_skip + 非紧急` → 确定性不进入决策（`model_status=not_asked`） |
| 配置 | `DialoguePolicy.rest_may_skip`（默认 True），设置页 ⑤ 有开关 |

### 三条边界，各配负例

| 边界 | 负例结果 |
| --- | --- |
| 在休息时不问模型 | 去掉门 → `test_resting_skips_the_model` 红 |
| 紧急不被休息吃掉 | 去掉豁免 → `test_urgent_is_never_eaten_by_rest` 红 |
| 疲劳按窗口隔离 | 去掉 scope 过滤 → `test_load_is_isolated_per_window` 红 |

### 真实链路实测（真实供应商）

把精力压到 10（`resting`）后：

| 输入 | 结果 |
| --- | --- |
| 在吗，跟你说个事 | `silence` / `not_asked` / "此刻在休息，这条先放着" |
| 救命，我这边出事了 | `reply` / `ok` / 模型自述"虽在休息但私聊需回应" |

**紧急豁免的关键验证点是 `model_status=ok`**——它证明紧急内容真的走到了模型，
而不是碰巧走了一条默认回复路径。

### 一处按"行为归人设"原则处理的细节

`LoadView.describe()` 只输出状态陈述（"这个对话已经持续了一阵，你比刚开始时
更少主动展开"），**不输出任何语气指令**。有一条测试专门断言它不含
"冷淡/生气/攻击/刻薄/应该"这类词——一旦写进去就等于把人格写死进代码。
