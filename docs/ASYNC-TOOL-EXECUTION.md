# 异步工具执行可行性分析

核对日期：2026-11-09。依据为当前工作树源码；本文不代表功能已实现，也未做生产压测。
文中“拟增”“建议”“验收”均为实施条件；代码位置是现状证据，不能把提案字段当成已有接口。

## §1 结论

**有条件能做：优先支持“本轮结束，后台执行，结果供后续轮次读取”；不能直接把所有工具改成后台任务。**
可判定边界：本轮后续内容不依赖结果、执行已获授权、结果可持久化并去重、过期后有明确处置，四项同时满足才可脱离本轮。
依赖结果的判断必须等结果；外部动作的成功声称必须等真实回执；已结束轮次不得靠追加 delta“复活”。
“工具还在运行，她继续聊其他内容”能做；“她尚未知道结果，却先说已经完成”不可接受。
当前基础可复用，但没有通用的“模型提出工具调用 → 后台执行 → 结果触发回复”闭环。
证据：对话主路消费文本 `delta`，工具端口单独 `await`，模型增量无工具调用字段（`src/ling/kernel/turn.py:923-933`；`src/ling/capabilities/tools.py:113-161`；`src/ling/ports/model.py:327-332`）。
因此近期收益明确的是 A/C；真正并行的 B 需要新增调度与表达边界，不是删除一个 `await`。
模型“决定调用”的即时信号目前也不通用：看视频标记在首段模型流结束后解析，若要决定后立刻开工，还须新增增量意图入口（`src/ling/kernel/turn.py:1029-1042`）。

## §2 三种“异步”的定义与本仓库可行性

| 类型 | 明确定义 | 可行性与代价 | 会改变或破坏什么 |
| --- | --- | --- | --- |
| A：不阻塞本轮 | 本轮终结；后台执行；结果进入下一次合格输入或系统事件 | **有条件能做，优先实施**；补持久调用、结果消费及取消协议 | 旧提示快照不知道未来结果；下一轮须重编译，不能假装上一轮已知 |
| B：不阻塞这句话 | 同轮先说与结果无关的话，同时执行，结果到达后再生成补充 | **有条件能做，当前无通用实现**；需要分段生成、并发任务、截止时间和发言权检查 | 已说的话不可回滚；同轮新增证据必须记录，增加一次模型调用且延长轮次 |
| C：不阻塞交谈 | 结果只入证据/事实或记忆，不要求向对话返回，也不主动补话 | **有条件能做，成本最低**；已有媒体证据读侧可借用 | 对话可能永远不消费结果；不能承诺“稍后告诉你”，也不能把失败或推断写成完成事实 |

C 的“不回来”仅指不回到对话；任务仍须有完成、失败、超时或失联记录，不能永久悬空。
`Awaitable[str]` 只说明处理器可让出事件循环；调用它的协程仍等结果，不能据此称为 A（`src/ling/capabilities/tools.py:65,140`）。
实际时序：`compile()` → `router.stream()` → `_visible` 推 delta → 看视频分支 → `_finalize`。
编译在 `src/ling/kernel/turn.py:795-808`，流式出口在 `:904-1025`，视频等待在 `:1037-1055`，收尾入口在 `:1057-1074`。
收尾解析撤回标记并落提议，再落角色消息、终态和事件（`src/ling/kernel/turn.py:1492-1510,1571-1606,1723-1739,1763-1775`）。
**二次生成先例有严格限制**：先 `await _watch_videos`，且只有观察非空、原正文为空才 `_follow_up_after_watch`。
该函数沿用同一 `turn_id`、配置和队列，再调用一次模型；并不是已经说完一段后后台回来补一句（`src/ling/kernel/turn.py:1037-1055,1327-1389`）。
正文非空时仍等待视频读取，但不补话；观察留待下一轮，这只是 A/C 的数据路径先例，并未做到本轮免等待。
正在运行的 `router.stream(messages=messages)` 没有结果注入入口；B 必须在生成段之间重新调用模型，不能让已启动的同一条流突然知道新结果（`src/ling/kernel/turn.py:923-925,1363-1367`）。
撤回则是执行解耦的先例：本轮只等提议落库，不等人工确认或真实撤回；它不是无等待，也不是后台自动撤回（`src/ling/kernel/turn.py:1399-1409,1425-1447,1798-1803`）。

## §3 用户可见因果与硬规则冲突

**结论：结果回来前生成的内容，确实是在不知道该结果的情况下说的；异步不会赋予模型未来知识。**
当前 `_visible` 只暂扣、剥离工具标记，不验证正文是否声称成功（`src/ling/kernel/turn.py:904-920`；`src/ling/kernel/marker_stream.py:62-90`）。
因此“我看完了，挺好看的”先流出、随后读取失败，是已有出口也不能自动修正的风险；异步会扩大这个窗口。
人设硬规则明确不声称做过未做的事、没有回执不声称已发送/已执行（`src/ling/domains/persona/service.py:26-42`）。
`operations` 也声明计划不是结果；投递仅在 `sent/delivered` 回执下成功（`src/ling/infra/models.py:623-647`；`src/ling/capabilities/delivery.py:262-268`）。
所以允许的先行话只能表达意图或已证实的状态：“我想看看这个视频”；持久入队后可显示“已安排，结果还没回来”。
“正在读取”必须有执行中状态；“看过了”须有可用观察；“发出去了”须有投递回执；四者不得互换。
工具调用成功与外部事实成功也不同：普通字符串返回不能代替发布、通话接通或撤回的专用回执。
`ToolResult.succeeded` 仅说明 handler 正常返回，注册表并未核验外部事实（`src/ling/capabilities/tools.py:138-161`）。
**可判定准入规则**：会据结果评价、报数、确认成功或执行依赖动作的文本段，必须放到结果到达后的生成阶段。
无关话题可以继续；结果未决的状态由服务端展示，不能仅靠提示词要求自由流式正文“不要乱说”来保证硬规则。
若不能在输出前隔离依赖结果的段，就保留同步等待；不能先发出矛盾断言，再靠补话把错误当成合理因果。
失败时记录“未读到/结果未知”；允许解释失败，不允许把失败输出包装成“你刚看到了”的成功观察。
模型观察仍可能是推断而非客观事实；现有媒体上下文保留来源及不确定标识，应沿用（`src/ling/kernel/context.py:739-752,779-803`）。
结果稍后主动通知时须指明“刚才那个视频/那次查询”，否则用户只会看到无缘由的插话。

## §4 技术上怎么接

### 4.1 outbox：能承载执行请求，不能直接提供完整工具协议

**结论：可复用 outbox 的可靠调度；必须补工具业务状态与回灌契约。**
现表是 `id/topic/payload(JSON)/state/attempts/available_at/processed_at/last_error/processed_by`，没有专用调用、结果或目标轮次列（`src/ling/infra/models.py:665-680`）。
`kernel/outbox.py` 实际只有 LIKE 前缀转义；认领和确认实现位于 worker，不能误把它描述成执行引擎（`src/ling/kernel/outbox.py:1-24`）。
worker 短事务 `SKIP LOCKED` 认领一条，提交后事务外执行，再短事务确认；租约到期可重领，是**至少一次**（`src/ling/worker.py:3971-3999,4022-4085`）。
异常按指数退避重排，达到 5 次失败转 `dead`，退避上限 300 秒；未注册 topic 为 `unhandled`（`src/ling/worker.py:47-51,4088-4137`）。
`ToolRegistry.call` 把失败、超时、待确认都转成返回值，worker 却只凭抛异常判断失败，直接套接会把这些返回都确认成 `done`（`src/ling/capabilities/tools.py:122-155`；`src/ling/worker.py:4184-4188,4360-4374`）。
拟增 handler 必须先持久化业务 outcome：待确认停止执行，确定性失败终结；仅安全可重试的瞬时故障进入重排。
outbox 的 `done` 表示本次事件处理完，不表示工具动作成功；外部副作用超时须记结果未知并对账，不能盲重试。
`ToolOutcome` 尚无 `uncertain/cancelled`；不能用 `failed` 伪装“确定没发生”（`src/ling/capabilities/tools.py:30-35`）。
建议 outbox payload 只带稳定调用引用和协议版本；参数、结果正文进入有受众和保留期的业务记录，避免多份敏感副本。
拟增调用记录至少有 `call_id、tool_id/version、args_ref、actor_id、subject_id、window_id、source_turn_id、source_attempt、source_message_id`。
还需 `requested_at、deadline、authorization_ref、idempotency_key、feedback_mode、cancel_policy`；结果保存 `outcome、output_ref、observed_at、completed_at、receipt_ref`。
目标尚未产生时不预填“下一轮 id”：保存目标窗口和消费策略，实际消费时写 `consumed_by_turn_id`；不保证紧邻下一轮一定赶得上。
这些字段可由业务记录承载；是否复用 `Operation.payload` 或建专表需在迁移阶段定案，当前两者都没有完整工具协议。
请求与 outbox 入队须同事务提交；结果落库与结果事件也须同事务，避免“说已安排却没任务”或“完成却没有可消费结果”。
现有 `_enqueue_once` 以事件主键幂等插入，可复用模式；JSON 中写个幂等键本身不会形成约束（`src/ling/worker.py:2800-2823`）。
新增执行/结果 topic 要注册 handler 并纳入 `OUTBOX_TOPICS`；`PERIODIC_JOBS` 只负责必要的过期、失联扫描，不轮询调用模型（`src/ling/worker.py:4298-4349`）。
**容量限制**：当前 `drain_outbox` 串行 await handler，周期任务也串行 await；慢工具会拖延同进程其他工作（`src/ling/worker.py:4175-4189,4239-4256`）。
现租约 600 秒且此路径无执行期续租；长任务需独立执行容量、续租/认领代次或外部作业回调，不能仅延长工具超时（`src/ling/worker.py:4001-4005,4075-4082,4100-4105`）。

### 4.2 结果回灌：字符串不等于下一轮输入

**结论：先存结构化结果，再由上下文编译器明确读取；不能直接插 `messages(role=system/tool)` 解决。**
现 `observation_line` 是临时 `ChatMessageIn(role="user")`，内容为观察加接话提示，调用方式是 `messages=[*messages, observation_line]`；没有插消息表（`src/ling/kernel/turn.py:1352-1367`）。
这个先例证明可二次调用，不证明安全包装完整；其文本直接插值，不能原样推广到任意网页或工具输出。
消息契约只列 `user/actor/system`，模型端口未声明通用 tool-call 关联字段；历史编译把非 user 全映射成 assistant（`src/ling/contracts/v1.py:580`；`src/ling/ports/model.py:257-266`；`src/ling/kernel/context.py:1400-1402`）。
所以硬塞 system 会被误当“她说过的话”，硬塞 tool 也没有现成角色与供应商协议支持；DB 字符串列能存不等于链路能用。
`Turn` 没有通用 payload；`run_turn` 接收用户文本等显式参数，也无通用结果事件入口（`src/ling/infra/models.py:188-208`；`src/ling/kernel/turn.py:625-659`）。
建议新增有来源的结果输入/上下文贡献，包装 outcome、来源、调用时间与结果时间、受众及不可信正文；不要伪造用户发言。
可借用 `ContextCompiler.wrap_untrusted`，但包装不是安全隔离，结果不得产生授权或再次被当工具标记执行（`src/ling/kernel/context.py:1615-1618`；`src/ling/capabilities/tools.py:1-8,60-62`）。
C 可借媒体证据路径：视频回调提交观察，后续 compile 读取本窗口已描述媒体；只取最近 3 条，不保证每项结果都入提示（`src/ling/domains/media/watch.py:285-300`；`src/ling/kernel/context.py:749-752`）。
A 则须增加未消费结果选择：按窗口/主体/授权/期限筛选，记录实际纳入哪次提示；已编译中的生成不会因数据库更新自动得到结果。
消费记录要区分“进入提示”“产生补话”“实际送达”；前一项不能冒充后一项，失败重试也不能永久吞掉待通知结果。

### 4.3 新轮次与续轮次：完成后必须新建逻辑轮次

**结论：未 finalize 的 B 可以同轮分阶段；A 在原轮终结后补话必须走新轮次。**
终结时已有消息与 `turn.completed`，清理停止标记后队列放 `None`；重试接口拒绝 completed（`src/ling/kernel/turn.py:1571-1606,1763-1775,1171-1176`；`src/ling/api/routes/chat.py:747-752`）。
`window_id` 表示会话，`turn_id` 表示一次输入响应，`attempt` 是同轮重试；递增 attempt 会回到 pending 并重新回答原输入，不是结果续接（`src/ling/infra/models.py:188-208`；`src/ling/domains/conversation/service.py:478-490`；`src/ling/api/routes/chat.py:772-785`）。
底层 setter 能改状态不代表完成轮可合法重开；那会混淆消息、提示快照、停止信号与投递幂等。
新结果轮需新增事件来源入口，以 `source_call_id/source_turn_id` 关联原调用，重新 compile 当前上下文并取得发言权；不能复用旧队列。
B 沿用配置快照但增加观察，必须记录每个生成阶段实际看到的输入；现提示快照按 turn 唯一、重试覆盖，不能把一次快照当两次调用的完整证据（`src/ling/infra/models.py:350-351`；`src/ling/kernel/turn.py:288-298,1352-1367`）。
`(window_id, client_turn_id)` 唯一约束可支持稳定结果事件键，但目前建轮语义仍是用户输入响应，需要显式扩展（`src/ling/infra/models.py:188-204`；`src/ling/domains/conversation/service.py:415-434`）。
桥的入站先解析身份，再建轮落用户消息并提交，调用协调器收集结果，随后 `_deliver`；结果事件不能冒充新的渠道用户消息（`src/ling/kernel/bridge.py:354-364,660-729,1483-1539,849-856`）。
桥现有“续发”只投递已经生成的剩余段，不再次调用模型，不能拿来续写新观察（`src/ling/kernel/bridge.py:685-699`）。
新补话仍走 `DeliveryService`，产生 `operations → delivery_receipts`；本地 `turn.completed` 不是平台送达证明（`src/ling/capabilities/delivery.py:192-236,262-277`）。
Web 端亦需结果事件/新轮次订阅与展示适配；不能向已经关闭的原 SSE 队列硬塞消息便声称用户收到了。

### 4.4 幂等与取消：已有模式可借，现成保证不足

**结论：执行去重、结果消费去重、补话投递去重必须分别成立。**
注册表每次 call 都新建 `call_id`，`idempotent` 仅是声明；需调度层先持有稳定调用键，并关联各次执行 id（`src/ling/capabilities/tools.py:48-49,113-140`）。
同一结果重复投递若每次新建随机轮次，会重复生成与补话；应以稳定结果 id 原子认领一个目标轮次，并在消费提交事务中保存映射。
结果已落库但 outbox 未确认的崩溃必须重放已有结果；外部动作已发生而结果未落库时，靠外部幂等键或查询回执恢复，无此能力不自动重试。
投递已有 `(plan_id, ordinal)` 去重及 uncertain 停发规则；复用新结果轮的固定 plan，不能重复投递时生成新 plan（`src/ling/kernel/bridge.py:1615-1636`）。
本地 operation id 不是平台幂等键，所以不能宣称端到端 exactly-once（`src/ling/capabilities/delivery.py:225-232`）。
**取消规则建议固定为**：默认同窗口有新用户输入、源 attempt 被替代、授权撤销或 deadline 到期，即撤销旧任务的主动补话资格。
尚未开始的任务可取消；运行中的只读任务尽力停止，停不掉则只按保留策略留证据；已发生副作用及其回执不能丢弃。
仅当任务原先被明确标为“跨轮持续通知”且授权仍有效，才可在新输入后保留通知候选；仍须等发言权，通知前重新核验条件。
为处理“结果与新消息同时到达”，拟增窗口输入序号/取消代次，原子认领通知时比较，并在外发前复核；只在任务开始时检查一次不足以阻止迟到补话。
因此“丢弃迟到结果”默认指丢弃过时的输出资格，不能抹掉实际操作事实；用户取消后仍能查询已发生的结果。
语音提供参照但不是通用实现：`discard_late_audio` 删除指定轮的 partial，`sequence` 参数未参与筛选（`src/ling/domains/speech/service.py:115-131`）。
具身入口按当前 turn 和麦克风授权拒绝旧音频；动作有 10 秒有效期，动作/播放各有回执（`src/ling/capabilities/embodiment.py:215-241,265-309`）。
播放追踪与具身动作回执目前存内存，不能直接充当跨进程工具审计；工具取消状态需持久化（`src/ling/domains/speech/service.py:149-167`；`src/ling/capabilities/embodiment.py:281-295`）。

## §5 什么工具适合异步、什么必须同步

这里“必须同步”指结果依赖的回复/动作必须等，不指阻塞事件循环，也不要求把整个长任务绑在 HTTP 请求上。

| 判据 | 工具或场景 | 明确选择 |
| --- | --- | --- |
| 只读、耗时明显、本轮能不评价结果、失效后可静默结束 | 主动读视频、查资料，用户继续聊别的 | A；默认下一次合格轮次读取，过期不突然插话 |
| 无需交付答案、允许只留有来源的资料 | 媒体描述、知识索引补全 | C；失败留状态，推断不升格成事实 |
| 用户当前问题必须靠工具回答 | “这个视频结尾是什么”“查完再告诉我数量” | 结果依赖段同步等；改为 A 必须明确当前尚无答案并保留待答任务 |
| 短耗时且答案立即依赖结果 | 当前时间、已有缓存查询 | 同步；后台化增加调度和上下文成本，基本无收益 |
| 不可逆或对外发布，且需用户确认 | 撤回、发布、发送消息 | 未确认不得执行；确认后可以后台执行，但成功声称必须等真实回执 |
| 长时外部会话且有真实进度/结束回执 | “打个电话，结束后告诉我结果” | 有条件 A；会话控制与媒体流独立，接通、结束不能凭入队成功推断 |
| 依赖即时在场与顺序，过期即无意义 | 停止旧音频、实时点头、插话 | 不放周期 outbox 排队等待；走带期限的控制路径 |

依据：风险/确认/超时已声明，管理调用还要过 PolicyGate，不能由 payload 自证确认（`src/ling/capabilities/tools.py:39-50,130-140`；`src/ling/api/routes/manage.py:1483-1495,1511-1559`）。
“打电话”仅是未来场景，所读 `phone/service.py` 实为看手机状态机，不是已实现的拨号工具（`src/ling/domains/phone/service.py:1-16`）。
撤回提议无需再包通用异步执行：它已将人工确认与回复解耦；保留同步落提议最简单，不能改成同步等用户确认（`src/ling/kernel/turn.py:1425-1447,1838-1890`）。

## §6 成本、收益与“不空转”的冲突

**结论：A/C 能缩短本轮收尾等待，但不会让工具本身更快；只有避免无效等待或多余通知才有净收益。**
当前 Web 已经边生成边显示，A 主要减少视频读取后的终态等待；桥收最终文本再投递，那里可能连首条外发等待也减少（`src/ling/kernel/turn.py:970-1042`；`src/ling/kernel/bridge.py:725-729,849-856`）。
若原本只生成一次，A 的主动补话通常再加一次模型请求；B 的结果补充同样另调模型，而 C 不必增加对话调用。
已有视频空正文路径本来就调两次模型，迁为 A 不应机械算作“再多一次”；比较必须以实际基线为准（`src/ling/kernel/turn.py:1043-1053,1363-1367`）。
额外成本包括结果存储、事务、队列积压、重试、上下文重复 token、主动打扰及故障排查；当前没有延迟分布，不能声称固定提速百分比。
“无事件不空转调用模型”已有明确规则（`src/ling/domains/affect/service.py:5`）；结果事件可构成调用理由，却不等于每条结果都值得调用。
建议确定性闸门：未消费且未过期、允许通知、受众/授权通过、有预算、取得发言权，全部满足才生成；否则仅存结果供后续读取。
相同等待期间禁止定时问模型“工具好了没”；失败状态直接展示，多结果按窗口合并，每批最多一次补话生成，禁止补话自动递归启动新工具。
收益验收需记录本轮终态延迟、工具完成延迟、主动补话次数、过期率、重复率及模型 token；后台 worker 的排队延迟也必须计入。

## §7 分阶段实施方案（每阶段可独立验收）

1. **阶段一：只读工具 A/C 最小闭环，不主动补话。** 选一个视频读取或受控查询，持久入队、记录结果、编译器按来源读取；保留结果依赖场景的同步路径。
   验收：人为延迟工具时原轮仍能终结；执行失败不产生完成声称；重启可恢复；重复投递只有一份结果；跨窗口不可见；下一次合格提示能看到结果。
2. **阶段二：取消与有限的新轮通知。** 加持久消费映射、新结果轮入口、Web/渠道展示及投递关联；默认新输入取消旧通知资格。
   验收：同一结果投递两次只生成一次补话；新输入抢先时不插入旧话；发言权丢失不输出；投递未知不重发；模型失败后的消费状态可恢复。
3. **阶段三：有外部副作用的长任务。** 仅纳入具备确认依据、外部幂等/查询回执、独立执行容量及期限的工具，不满足任一项即不纳入。
   验收：授权撤销后未开始任务不执行；副作用发生后进程崩溃不重复操作；失联保持未知而非成功；所有阶段可按调用 id 对账。
4. **阶段四：按测量收益决定是否做 B。** 仅在同轮等待确实损害体验且能隔离结果依赖段时做分段并行；否则停在 A/C 即可交付。
   验收：插话能停止剩余输出；结果晚到不续已结束轮次；前段不声称未知结果；第二次生成的提示及结果引用可审计；收益超过额外调用成本。

## §8 不做／风险

**不做**：把所有工具 fire-and-forget、后台偷偷确认、任意结果插成 system 指令、把原轮 retry 当续写、用无限模型轮询等待结果。

| 风险 | 明确防线与剩余限制 |
| --- | --- |
| 提示注入 | 工具输出始终为不可信数据；只解析当前模型的合法意图，结果不能自发调用工具；文本包装不能保证模型绝不受影响 |
| 事实顺序错乱 | 保存请求、观察、完成、消费时间；新轮使用当下上下文，禁止回写“当时已经知道”；模型观察仍保留不确定性 |
| 重复补话/重复动作 | 稳定调用键、结果消费唯一映射、固定投递 plan；平台无幂等或查证能力时保留未知，不承诺 exactly-once |
| 用户困惑 | 新补话标明原任务；默认新消息取消旧主动通知，持续通知须事先明示；不能用随机插话伪装连贯 |
| 成本与空转 | 事件驱动并先过确定性闸门；禁止等待轮询和补话递归调用；增加模型轮次必须单独计费统计 |
| 审计断链 | 留存调用来源/参数摘要、授权依据、源 turn/attempt、执行尝试、结果引用、消费轮、投递 operation/receipt；单一 outbox done 不足以证明成功 |
| 超时与取消误判 | 停止等待不证明外部动作停止；晚到回执仍入账，过期通知可丢，事实不可丢；现有内存回执不足以跨重启恢复 |
| 容量和实现未知 | 未实测工具耗时、worker 并发与通知接受度；先量测再定截止时间和配额，不以可行性文档代替生产验证 |
