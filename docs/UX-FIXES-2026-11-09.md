# 六项体验修复设计（2026-11-09）

本文是实现契约，不改现有代码。依据为本仓库源码；性能数值是新验收目标，不是已测现状。
共同底线：计划、意向、梦不是经历；状态只影响表达，不改变权限；过期状态为 unknown；不空转调用模型；没有投递回执不声称已发送。
每项独立提交、独立验收；界面优先说“现在怎样、接下来怎么做”，内部原因码只用于日志与测试。

## §1 模型配置页：直接选择模型

### 根因／现状

- `clients/web-console/src/components/model-settings/RolesPanel.tsx:121-155,155-204`：默认槽位平时只显示文字；`editing` 才显示表单。
- 同文件 `:156-189,690-719`：须先按“更换默认”，然后分别选供应商、模型；换供应商时还自动选首个启用模型。
- 同文件 `:302-341`：下方**职责行已是单个按供应商分组的下拉**，因此用户抱怨的主要是上方默认槽位，不应误删职责绑定。
- `clients/web-console/src/components/SettingsPage.tsx:85-110,232-251`：槽位与职责共用草稿和保存；“实际生效”由服务端解析。

### 方案

- 前端：五个默认槽位直接显示可操作的组合模型选择器，移除“更换默认／完成更换”编辑门；保留一个全页“保存／放弃”。
- 下拉参考职责行：`newapi · OpenAI 兼容` 为不可选分组头，子项为模型名；当前选中项有勾选和 `aria-selected`。
- 选择值用结构化的 `provider_id + model_id` 对，不凭模型名反查供应商；重复模型名依旧能选对。
- 选中后只改当前槽位草稿；行内显示供应商、未保存标记和服务端算出的“实际生效”，保存仍走既有草稿→校验→发布。
- API／域：沿用 `/v1/settings/resolve` 与既有保存流程；补后端槽位能力校验，禁止把非 chat 供应商放进五个槽位（现前端警告见 `RolesPanel.tsx:145-147,205-209`）。
- 迁移：无；历史不匹配或已停用选项保留显示但不可新选，并说明如何换。

### 边界与失败态

- 无供应商、无启用模型时显示“先添加模型”，选择器禁用但页面可进入；读取失败用原错误态。
- 正在保存时禁止重复提交；resolve 超时仅影响“实际生效”提示，草稿不丢，不能把浏览器推算值冒充生效值。
- “快速配置”仍须二次确认，且不得覆盖用户未确认的草稿。

### 可程序化验收标准

- 给已配置槽位，首次渲染无需点击其他按钮即可展开单个选择器，且不存在第二个“供应商”选择器。
- 给两家同名模型，选第二家后草稿恰为第二家 `provider_id/model_id`；保存请求只更新该槽位。
- 给禁用的历史模型，它可见并标“已停用”；给新选择时不可提交禁用或能力不符的绑定。
- 给保存失败或 resolve 超时，原选择仍留在草稿，提示失败且不显示“已生效”。
- 给选择后未保存，服务端已发布配置不变；保存成功后服务端解析结果与行内“实际生效”一致。

### 不做

- 不重做供应商管理、职责继承、快速配置；不添加自动挑模型算法。

## §2 关系页卡死：有界列表与按需操作

### 根因／现状

- 实际页面为 `clients/web-console/src/components/IdentityPage.tsx:45-69`；调用 `/v1/accounts/subjects`，不是 `/v1/relations`。
- `src/ling/api/routes/manage.py:1112-1147`：两次查询分别取**全部** `Subject` 和 `ActorAccount`，内存组装后一次返回；这里未见 N+1，但无分页上限。
- `IdentityPage.tsx:109-115,158-174,227-235`：渲染全部人；每张未合并卡都生成“其余所有人”的 `<option>`，约为 O(N²) 个选项，足以造成大列表主线程卡顿。
- 是否另有数据库锁、请求超时或异常循环：**需调查者按真实数据与浏览器性能记录确认**，静态代码不能断言生产根因。

### 方案

- 前端首屏只请求第一页，服务端游标分页 `GET /v1/accounts/subjects?limit=30&cursor=...`，响应 `{items,next_cursor,total?}`；保留旧路由兼容方案需实现者评估，新增 v2 路由也可。
- 卡片只画当前页；合并目标改为点击“合并”时打开异步搜索框，`GET ...?q=...&limit=20`，排除本人及不可合并对象，不给每卡生成全量选项。
- 合并／拆开成功刷新当前页及相关目标；保留主体 ID、账号证明、合并指针语义，合并仍只写指针。
- 若 A=数据库全表读取慢：索引、排序和只取必要列，分页在 SQL 层执行，账号用当页 subject ID 批量查。
- 若 B=响应／序列化慢：响应只含当页摘要，账号过多者折叠并按需取详情；不得假装账号不存在。
- 若 C=React／DOM 慢：先去 O(N²) 选择器，再分页；若单页仍慢才考虑虚拟列表，不先引入复杂库。
- 迁移仅在 EXPLAIN 证明缺索引时加索引；诊断记录 SQL 耗时、返回字节、React commit 与 DOM 数。

### 边界与失败态

- 空列表给明确空态；搜索无结果与加载失败分开；请求超时可重试并可返回导航，不让全页一直转圈。
- 下一页请求可取消，旧响应不得覆盖新搜索；游标对应稳定排序，删除／合并后从第一页重读。
- 越权仍由现有鉴权处理；合并目标必须在写入时重新校验，不能信任候选搜索结果。

### 可程序化验收标准

- 给 5000 人、各 3 账号的种子数据，首屏 API p95 <300 ms（本地测试 DB，热连接），传输体 <100 KB；首屏可交互 <1 s（基准浏览器），DOM 总节点 <1200。
- 给 5000 人，首屏至多 30 卡、至多 20 个目标结果；未打开合并框时目标 `<option>` 数为 0。
- 给连续翻页，无重复／遗漏主体；给搜索与翻页乱序返回，界面只呈现最后一次查询。
- 给账号查询，数据库查询数随页数增长而非随主体数增长；单页列表 SQL 数上限 3。
- 给后端超时，10 s 内出现可操作的重试态，刷新或离开页面不被阻塞。

### 不做

- 不改合并的身份语义，不自动按昵称合并，不做整库关系画像。

## §3 日程：手动生成按钮

### 根因／现状

- `src/ling/domains/agenda/timeline.py:17-18,588-593`：D 日大纲自动在角色本地 D−1 21:00 到期，21:00 不是日界。
- `src/ling/worker.py:2865-2953,3121-3205,3256-3289`：60 秒扫描投 `schedule.outline`，worker 再调用 `outline_work`。
- `src/ling/api/routes/life_timeline.py:817-828` 和 `clients/web-console/src/components/LifeTimeline.tsx:891-931`：时间轴目前只有 GET 读取与重试，无生成入口。
- `timeline.py:633-682,4070-4135`：显式目标日可判 due／catchup／late；醒后 late 零模型、只补未来锚点。

### 方案

- 在生活→今天的时间轴标题旁加“手动生成日程”；显示目标**角色计划日** `plan_day`，默认取 GET 返回值；另给“为明天生成”次级选择，仅允许角色本地今天／明天。
- 未生成、pending 但无在途任务、可恢复失败时可点；ready／degraded 已有修订时显示“已生成”，重复点击返回同一结果，若需强制重排另立设计。
- 新增 owner-only `POST /v1/life/outline-jobs`，请求 `{plan_day,request_id}`；返回 `{job_id,plan_day,state:queued|running|unchanged|blocked}`，202 表示入队，不声称已经生成。
- GET `/v1/life/outline-jobs/{id}` 回 `queued|running|ready|degraded|failed`、修订号和人话说明；前端轮询至终态并重新读取时间轴。
- API 与自动任务共用同一抢占／幂等键与 `outline_work`；同日同快照在途只保留一项，手动请求不绕开预算、lease、退避及终态原因门。
- 当前日醒后明示“只能补接下来的确定安排，不生成过去”；明天即使早于 21:00 手动预生成，21:00 扫描看到同一版即不覆盖。
- 已确认的承诺／睡眠保护锚点仍由 `ensure_day_plan` 合并，过去段不回填；若现有作业记录不足以供查询，新增小型作业状态表迁移。

### 边界与失败态

- 双时区时按钮文案必须展示角色目标日，不能把用户 `display_date` 当 `plan_day`；跨日裁剪仍按 GET 的展示时区。
- 请求并发、刷新、断线后可按 job ID 恢复进度；生成失败显示“没生成出来，可重试／查看日志”，degraded 显示“使用规则安排”，不把两者混为成功。
- 非 owner 只可读已有授权内容，不可触发；日期非法、过往／过远日期 422；队列不可用返回明确错误且不显示生成中。

### 可程序化验收标准

- 给目标日 D 的空计划，点击两次／两个浏览器并发，最多一条在途 outbox、最多一次模型调用，均拿同一 job ID。
- 给 D 已 ready 且快照未变，再点返回 unchanged，修订号不变，模型调用 0；21:00 自动扫描也不覆盖。
- 给 D 已过醒点，执行结果 phase=late、模型调用 0、过去时间段新增数 0。
- 给已确认锚点与模型输出冲突，锚点不被覆盖；新增内容仍标计划来源，经历事实表新增数 0。
- 给 worker 失败，轮询终态可读、按钮恢复可用条件由后端判定；给非 owner 返回 403。

### 不做

- 不开放任意历史日补造经历，不提供“无限强制重生成”，不把点击当作“她做过”。

## §4 上游不可用：领域内默认回退契约

### 根因／现状

- `src/ling/domains/phone/service.py:14-16,28-34,119-143`：phone 自有 `DEFAULT_IDLE_MINUTES=10`，但实际间隔由调用方决定；空值已有默认回退。
- `src/ling/api/routes/life_timeline.py:225-243,761-779`：日程区分 empty／pending／ready／degraded／failed／unavailable，不能把读取失败等于“没有安排”。
- `src/ling/api/routes/life_timeline.py:538-544`：场景过期应是 unknown；`src/ling/api/routes/dashboard.py:514-537` 只读 phone 状态。
- 目前在 `src/ling` 搜索到 phone 的实际调用仅状态读取；“看一眼手机”依日程／场景决定间隔的运行入口**需调查**，不能凭设想指认一处已经抛错的调用链。

### 方案

- 各消费域统一接收 `DependencyValue<T>={state:ready|empty|unknown|unavailable,value?,as_of?,source}`；过期、缺计划、失败、超时均先归一成非 ready，但保留原状态供诊断。
- 判定：ready 且未过期才可作当前输入；degraded 计划只作为“计划”参考，不能作当前场景事实；empty／pending／failed／unavailable／unknown 不提供可断言的日程事实。
- 每个领域声明自己的 `default_for(context)`：phone 用自身间隔默认与安全的“位置未知／无确定活动”参数；人设默认只提供表达风格，不伪造位置、行动或授权。
- 消费边界返回 `ResolvedInput<T>={value,source:upstream|domain_default,dependency_state,fallback_reason}`；内部日志记领域、上游、状态、是否回退、请求关联 ID，不记录自由文本敏感内容。
- 对外相关响应加 `input_sources` 的紧凑摘要，例如 `{schedule:{source:"domain_default",message:"这次用了默认节奏，因为日程暂时不可用"}}`；普通用户只见一句话。
- 回退参数只影响本次调度／表达；不得写进 activity、experience、已确认位置、发送回执等事实表。已有确定性状态机继续决定动作许可。
- API／域：先在 phone 消费点验证通用契约，再给第二个真实跨域调用点复用；若查不到 phone 消费点，先补调用链诊断再落具体接线。

### 边界与失败态

- 上游超时要有界，例如 300 ms 读取预算；依赖不可用不能触发无限模型重试或整条请求阻塞。
- 安全关键依赖（身份、权限、验签、投递回执）**不允许**默认放行；只回退可缺省的行为参数。
- 上游恢复后下一次调用自动用新鲜值；旧 fallback 不缓存成事实。并发调用各自记录真实来源。

### 可程序化验收标准

- 给日程 empty／pending／failed／unavailable、场景过期或读取超时，phone 仍返回可用状态与自身默认间隔，并在响应和行为日志标出回退来源。
- 给新鲜 ready 日程，使用上游参数且 `source=upstream`；给 degraded 仅作计划参考，不能生成“她正在做 X”的事实描述。
- 给回退调用，经历／位置事实表新增数 0；模型调用数不因上游失败增加；权限与验签结果保持 fail-closed。
- 给上游恢复，下一次调用不沿用旧默认；给缺省值非法，返回可解释错误而非静默伪造事实。

### 不做

- 不造全局“万能默认日程表”，不把 unknown 改写为 idle／rest，不改变权限。

## §5 总览：按“此刻→计划→记录→运行”重排

### 根因／现状

- `clients/web-console/src/components/DashboardPage.tsx:671-772,774-861`：12 张卡线性塞入同一网格；“今天的安排”与“今天的节奏”相邻但语义不同，未来意向排在近期事实前，用户需自行辨别。
- `clients/web-console/src/styles.css:2675-2699`：宽／半卡分别 7／5 列，按 DOM 顺序自动流动；`dashboard.css:36-42` 在 940px 以下全部单列。
- `DashboardPage.tsx:610-655`：整页 GET 失败会替换全部卡片；各分段内部已有独立状态，不能让单卡失败扩大成整页失败。

### 方案

- 桌面 12 列分四区：A“现在”：此刻 6、可用性 3、情绪 3，手机 6、主动联系 6；B“接下来”：今天的节奏 6、今天的安排 6，未来意向 12。
- C“已留下的记录”：近期生活 6、最近记住的事 6、关系 12；D“连接状态”：渠道与模型 12，放页尾但故障时页顶加一条可跳转告警。
- 每区有短标题和一句语义：“可能与计划”“已发生／已记住”分隔；未来意向最多 2 条预告，保持“未安排”标记，不能写成将发生的事实。
- 卡片首层只给主值、一句解释、一个明确入口；长列表最多 3 行，详情链接去原页面，避免卡高不齐和首屏滚动过长。
- 空态分别说“暂时没有记录／尚未生成计划”；分段 unavailable 原位显示“这块暂时读不到＋重试”，不把其他卡一起盖住。
- 769–940px 两列 6／6；≤768px 单列，区块顺序不变，卡片内无水平滚动，主操作可点范围 ≥44px。
- 前端布局优先；API 仅在现有摘要超量时收紧每节的条数，保持原状态与来源字段。

### 边界与失败态

- 首屏 1440×900 至少看到“现在”和“接下来”标题；窄屏按 DOM 顺序可读，键盘焦点顺序与视觉一致。
- 页面定时刷新不清空旧卡片；刷新失败显示更新时间和轻量告警，不能把旧数据当实时状态。

### 可程序化验收标准

- 给所有分段 ready，断言区块与卡片顺序、列跨度和明确入口；给 intent 内容，断言“计划／意向”标签且无“已做”文案。
- 给 `today_outline=unavailable` 且 `intent_teaser=ready`，仅前者显示失败态，后者照常可见。
- 在 1440、900、375px 截图／DOM 测试中无横向溢出；375px 单列、焦点顺序与 DOM 一致。
- 给后台刷新失败，旧卡可见但更新时间未变化，并出现“更新失败”提示。

### 不做

- 不改各域状态计算，不增加新的“健康分”，不把计划与经历拼成同一列表。

## §6 接入器：可编辑且可回退的配置

### 根因／现状

- `clients/web-console/src/components/ConnectorsPage.tsx:223-301`：页面只有 GET 诊断、刷新与字段状态，明确写“本页只读”；`src/ling/api/routes/settings.py:587-611` 也只有只读端点。
- `src/ling/settings/connectors.py:1-35,147-223`：字段来自环境变量／运行实例，secret 只回 `set`；OneBot WS URL 可能含 token，AppID 亦按密钥隐藏。
- `src/ling/config.py:109-145,235-278`、`src/ling/app.py:257-339`：配置从进程启动值构造，WS／网关在启动时创建；改浏览器字段不会自动影响旧实例。
- `src/ling/infra/models.py:389-401`、`src/ling/settings/service.py:778-811`：模型供应商已有密文凭据机制，可复用 `SecretBox`，但接入器尚无对应持久化／激活机制。

### 方案

- 前端在 OneBot、QQ Bot 卡片加“配置”入口，表单按“收消息／发消息／访问范围／高级”分组；保存前展示变化及生效条件。
- 首批可改：OneBot WS 端口／监听地址／token、出站 WS URL、HTTP 签名 secret、发送 API 地址与 access token；QQ Bot 启用、AppID、ClientSecret、BotSecret、公钥、沙箱、API 基址；发送者／群白名单走既有全局访问策略表单的同一权威，不在两张卡复制一份。
- `instance_id`、主动发送能力、验签例外、媒体主机白名单等高风险项先只读并给出宿主配置指引；“白名单”可编辑仅指访问名单和群名单，账号绑定／证明仍在关系页。
- 新增 owner-only `GET/PUT /v1/settings/connectors/{id}/draft`、`POST .../validate`、`POST .../activate`、`POST .../rollback`；配置 `{revision,values,secret_status,effective_source,activation_state}`，密钥写入操作明确为 keep／replace／clear，GET 绝无明文或可逆掩码。
- 公开配置与密文分表存 DB；密钥用现有 `SecretBox`，修订留作者／时间／非密钥差异／密钥“已变更”标记，旧密文保留到新版本确实可用及回滚窗口结束。
- 进程启动解析顺序：已激活的 DB 配置覆盖 env，缺字段回退 env；候选草稿绝不生效。启动时验证端口、URL、凭据配套及必要的权限策略。
- 首版采用**重启生效**：激活只登记“待重启”，页面明确写“请重启 API”；启动后同一版本的诊断探针报告 active／failed；失败则自动恢复上个 active 修订并报告“已回退”。HTTP-only 无持久连接时不能把“未见连接”当失败，改用签名配置自检与可选的人工收件验证。
- 若实现者要热加载，须另做原子停旧／建新／回滚并证明所有路由与 worker 同步；本轮不接受只改 `app.state.settings` 的半热加载。

### 边界与失败态

- 新密钥不回显、不落审计明文、不进 URL／日志；保存时清空输入框表示 keep，clear 需显式二次确认。
- OneBot 监听端口无 token 时拒激活；QQ Bot 启用无凭据时拒激活；地址做 scheme／主机校验，禁止借“测试连接”任意探测内网。
- 激活失败、重启失败、连不上时保留旧凭据与旧配置；网页仍可用时给“回退上一版”，网页不可用时保留宿主 `.env` 恢复入口。
- 非 owner 403；即使本机单人部署也不得让未登录者读写部署指纹；并发编辑按 revision 做 CAS，冲突返回 409。

### 可程序化验收标准

- 给 owner 提交新 OneBot token，GET 仅见 `set=true`／修订号，不含 token、URL 查询令牌或密文；审计仅见谁、何时、哪个字段变更。
- 给普通用户、匿名请求，所有写接口分别 403／401；给旧 revision 写入返回 409，原 active 不变。
- 给无 WS token 的监听配置或缺 QQ ClientSecret 的启用配置，validate 拒绝且不创建待激活版本。
- 给激活但未重启，诊断显示 pending_restart、运行连接仍用旧版本；重启成功后显示新版本 active。
- 给新版本启动失败／连接校验失败，服务回到旧 active，旧密钥仍可用；HTTP-only 未见连接不得误判失败。
- 给 secret 输入框留空，密钥指纹不变；显式 clear 才删除；网页／运行日志均查不到明文。

### 不做

- 不在网页直接改宿主 `.env`，不开放任意环境变量编辑，不自动开启主动发送或弱化验签。

## §7 实施顺序与并行建议

1. 先做 ①、⑤ 的纯前端改动；② 的运行诊断可同时做，先量请求／SQL／DOM，再落有界列表。
2. ③ 与 ④ 可并行：一个只写日程作业，一个定义跨域输入回退；共用状态词但不共用写路径。
3. ⑥ 最后做，先锁定配置权威、重启与回退机制，再开放表单；接入器页和后端存储可分批合并，但入口只在端到端可用时显示。
4. 每项独立测试和合并；跨项回归至少覆盖生活时间轴、总览来源标签、owner 鉴权、密钥不泄露。

## §8 风险清单

- ② 静态定位到了无界查询和 O(N²) DOM，但不能证明生产卡死仅由此导致；必须记录真实数据量、慢 SQL、响应体与主线程长任务，避免只修表象。
- ② 分页改变旧 `/accounts/subjects` 的响应形状会破坏旧客户端；优先兼容旧路径或新增版本路径，并测合并后翻页一致性。
- ③ 手动与 21:00 自动并发时若使用两套幂等键会双生成；必须共享日程域 lease、预算与 outbox 去重。
- ③ “生成成功”仍是计划，不是行动事实；晚到不可补造过去，也不可为已发送消息伪造回执。
- ④ 默认值若进事实表会形成长期错误记忆；响应和日志都须保留 `source=domain_default`，过期场景须回 unknown。
- ⑤ 卡片重排不得改变现有分段独立降级；“今天的安排”旧语义与新时间轴并存时标题须说明来源。
- ⑥ DB 覆盖 env 后，启动失败可能导致无法打开网页；旧 active 密文、宿主恢复路径及启动时回滚必须在开放编辑入口前验证。
- ⑥ 更改 WS 端口需要容器端口映射配合；表单应提示“宿主端口未映射则仍接不到”，不得把配置已保存说成已连接。
- ⑥ secret 与带 token 的 WS URL 不能被浏览器 GET、审计、异常栈或“测试连接”参数泄露；负向测试要查响应、日志、修订快照。
