## 0. 先修正一条会带偏设计的事实

LEAD-notes §3/§6 推测「？」会触发自动记忆召回。直接调用 `recall_query.py` 的两个函数（`.venv/bin/python`）得到：

| 输入 | NFKC + 去标点后的 plain | `should_skip_automatic_recall` | `needs_recent_topic` |
|---|---|---|---|
| `？` / `?` | `''` | **True** | False |
| `早上好` | `早上好` | **False** | False |
| `后来呢？` | `后来呢` | False | **True** |

**[实测]** 全角问号被 `NFKC` 归一成半角 `?`，再被 `rstrip(".!?。~")` 吃掉 → plain 为空 → 属于 `_STANDALONE_REPLIES` → 跳过自动召回。所以反例里「早上好 → ？」的「？」**不会**把前天那四项需求从长期记忆里捞回来；这条归因不成立。

**[实测]** 真正未被跳过的是「早上好」：它不在 `_STANDALONE_REPLIES`，会以 `query="早上好"` 调 `_memory.recall()`。是否真能召回旧需求，取决于检索排序和阈值，本文**未验证**。

**[代码路径]** 旧话题进上下文还有两条不依赖召回的通道：`window_ctx.summary`（`context.py:1673–1685`）只要非空就无条件注入；原文层按 token 预算从新往旧取（`context.py:1460–1529`）。这两条才是「隔天续聊/换题」取舍的主战场。B 的设计重点相应放在**原文取数 + 短记忆/摘要的可见性 + 召回 query 构造**，而不是「拦住问号召回」。

## 1. 窗口常同一个，关注点会变：四种取数策略的收益比较

**[代码路径]** 窗口按 `(actor_id, channel, connector_window_ref/title)` 复用（私聊再加 `subject_id`），与话题无关（`bridge.py:1479 _ensure_window` / `:1565–1576 _find_or_create_window`）。同一窗口里昨天的方案、今早的问候、刚换的新题排成一条时间线。

同一句话 `「？」，隔天仍在续聊 vs 几秒内已换题` 的对照：

- **S-keep（隔天仍在续聊）**：前天 22:14「那个产品方案我列了四项需求」→ 22:15 Ling「好，我记下了，明天接着聊」→ 今天 08:02「早」→ 08:03「在吗」→ 今天 08:04 `「？」`，且这句紧跟在一句带锚点的「接着说前天那个方案」之后；或两人昨夜约好今早继续，`「？」` 是要求澄清昨天最后一句。
- **S-switch（几秒内已换题）**：08:02「早」→ 08:02「在吗」→ 08:03 Ling「早呀，昨天那四项需求我记着」→ 08:03 `「？」`；或 08:02「早」→ 08:03「对了，换个事，周末去哪」→ 08:03 `「？」` 指向刚改的新题。两例里 `「？」` 文本完全相同，差别只在**时间位置 + 前文锚点**。

四种策略的收益/代价（均为 **[推理]**，需回放验证）：

| 策略 | 在 S-keep 上的收益 | 在 S-switch 上的风险 | 取数含义 |
|---|---|---|---|
| 按时间（最近 N 条，现状） | 最近几句都在，短回复有着落 | 若旧话题已被挤出原文/摘要，S-keep 的锚点缺失，模型接不上 | 现状 `messages_for_prompt` 按 `sequence` 往回取到预算满 |
| 按最近几轮 | 连续语段（M1 的一串气泡）完整，指代不落空 | 换题瞬间仍把上一题的最近几轮带进来，靠模型自己分辨 | B 的主策略：在最近几轮内**优先保留完整语段**，而非机械按条截断 |
| 按话题线索 | 锚点词（「接着说前天那个方案」）能把旧话精确拉回 | 线索误判时（把「对了」当找回）会主动续错题；计算相关性有成本 | B 只在有**显式**线索时启用，作为最近几轮的补充，不用相似度猜 |
| 按显式引用 | 群里最精确（M2），引用目标就是当前指代对象 | 私聊/无引用场景完全不触发；引用目标可能已在可引用窗口外（悬空） | B 的最强信号；引用目标在库里则展开进快照，不在则标注「引用目标不可见」 |

**B 的默认排序**：显式引用 > 显式找回线索 > 最近几轮/时间邻接 > 摘要兜底。时间只作为「短回复指向哪一句」的次级信号，不作为「是否续旧话题」的主判据（与 M3 §2 一致）。

**[不足]** 没有本项目中文回放集上的对照实验，上表的收益方向是机制推理，不是实测结论。

## 2. 接上一句 vs 回看更早：判定信号与优先级

四类输入，给出 B 的具体判定：

| 输入 | 判定 | 依据信号 | 取数动作 |
|---|---|---|---|
| `「？」` 澄清刚才那句 | **接上一句**（不回看） | 文本无锚点、无引用；`plain==''` 已跳过自动召回；时间紧接上一句 | 最近 1–2 轮原文足够；不额外注入旧话题 |
| `「后来呢？」` 承接上一话题 | **接上一话题** | `needs_recent_topic()` 为 True（已实测）；无时间锚点 | 把最近一条非寒暄用户消息拼进 query（现状已有，`context.py:1557–1566`）；B 保持并把「上一话题」限定在最近几轮内 |
| `「接着说前天那个方案」` 显式找回 | **回看更早** | 时间锚点「前天」+ 话题锚点「那个方案」+ 承接词「接着说」（M3 S3.2） | 用锚点词做精确召回/原文定位，把目标话题纳入取数；不依赖相似度 |
| 群里两话题并行时的引用回复 | **按引用目标** | `envelope.reply_to` 非空（平台 id）；`mentions_actor`/`_is_addressed` 判定指向（M2） | 展开被引用消息及其邻近上下文；引用目标不可见时明确标注悬空，不静默接最近一条 |

**B 的判定优先级（从高到低，命中即停）**：

1. **显式引用/被点名** — `reply_to`（`contracts/v1.py:362`）或 `mentions_actor`（`:370`）→ 指向被引用/被 @ 的消息。群聊里这是默认解释（M2 §3.1）。
2. **显式找回锚点** — 时间锚点（前天/上次/那天）+ 话题名词，或元话语「刚看到/回晚了」+ 名词 → 回看更早消息（M3 §3.3）。
3. **承接词** — 「后来呢/然后呢/接着/刚/还说是」→ 最近话题/上一句。`needs_recent_topic()` 已覆盖一部分。
4. **时间位置 + 短回复** — 无锚点的 `「嗯」「？」「哦」`：紧接上一句 → 澄清/应答刚才那句；隔天首条 → 新开场，不强势续旧话（M1 §3.2、M3 §2）。Δt 大本身**不可判定**延迟回 vs 晚看见，不强行归因。
5. **纯时间邻接** — 兜底：取最近几轮原文，由模型在完整语段里自行判断。

**[代码路径]** 现状只实现了第 3 条的一部分（`needs_recent_topic`）和第 5 条（按时间取）；第 1 条的信号在 `envelope` 里存在但 `_is_addressed`（`bridge.py:1652–1670`）只用于「回不回」，没有用于「取哪段上下文」；第 2/4 条目前没有实现。**[推理]** 这是 B 的主要增量点，但信号权重需校准。

## 3. 人主动换题的条件：何时足以开启新话题

**[代码路径]** 现有「她想稍后再提」的机制：`autonomy.py` 的 `Followup(after_minutes, goal)`（`:129–158`）由决策提示词让模型显式给出（`:61–74`）；`bridge.py:1285 _record_followup()` 落成 `intents` 表（`domains/intent/service.py:205 record_followup`），到期由 `worker.py:3344 handle_intent_tick` 变成主动机会。意图要求有来源（`source_ref`），无来源的念头不许产生。

四种「足以开启话题」的条件，分别评估（均为 **[推理]**）：

- **当前有现实关联**：新消息与眼前正在发生的事直接相关（「你看这个」「刚才那个视频」）——足以开启新话题，因为它锚定在**当下**，不需要回看旧话。B 应让它走最近几轮取数，不把它接到更早的高相关旧记忆上。
- **自然结束**：上一话题已收束（双方都说了结束/感谢/「先这样」）——足以开启新话题。可作为弱化旧话题权重的信号（结束标记后面的新句默认不是续旧话）。
- **对方感兴趣**：对方主动追问细节、给新信息、表现出投入——足以**延续**而非换题；它提高「继续当前题」的权重，是抑制主动换题的信号。
- **有待兑现的承诺**：系统/自己记录的承诺或到点意图（「明天发你」「稍后再提」）——足以开启话题，但 B 不自己发明承诺：只有当 `intents`/承诺表里有具体来源记录时才算，并把它作为**显式锚点**注入。**[代码路径]** 这条链路已存在，但意图目前不进 `ContextCompiler.compile()` 的输入，是否要接属于 B 的候选取数点（见 §5），本文只标位置不改。

把三类分开评估（不要混成一个「主动度」分数）：

| 类别 | 定义 | 条件式判据 |
|---|---|---|
| 恰当主动 | 有现实关联/自然结束/有来源承诺，且新句与旧题无锚点 | 回复对准新句；旧题未被续接 → 判恰当；出现在上述条件都不成立时 → 复查是否误判 |
| 过度主动 | 无上述条件，模型仍抛开当前句去提旧事/主动发新题 | 当前句有明确指代对象却回复了别的话题 → 判过度；仅在新句本身模糊时发生 → 不算独立缺陷 |
| 错误续聊 | 用户已换题/开场，却把旧话题当指代对象接上（反例核心） | 新句无锚点 + 旧话题出现在快照 + 回复续旧题 → 判错误续聊；配对正向：新句有锚点时续旧题应为合法 |

**[不足]** 主动的自然度没有自动指标；只能靠人工/回放标注，且「自然」标准依人设而异——不要用一条硬规则替所有人设决定。

## 4. 旧话题恢复、群聊跟对人、新窗口是否必要

**旧话题恢复**：**[代码路径]** 「前天那个方案」这类显式找回，现状没有专门入口；`needs_recent_topic` 只处理承接词，不处理时间锚点。B 的做法是：用户重新提起时，用锚点词（时间+名词）定位原文/记忆；若命中已压进摘要的消息，摘要块仍在（`context.py:1673–1685`，永不过期），可作为定位辅助，但**摘要不等于原文**——引用/细节要求原文时必须回到原文取数。恢复是「重新激活指代对象」，不是「复制旧话题到当前轮」。

**群聊跟对说话人和被引用的消息**：**[代码路径]** 历史 user 消息按 `sender_subject_id` 查 `subjects.display_name` 加「名字：」前缀，占位名（「群友」「用户」）被过滤（`context.py:1687–1717`）；当前句用本次群名片 + 稳定昵称合并署名（`:1807–1835`）。`context.py:1557–1566` 拼 query 时，群聊里额外要求 `message.sender_subject_id == subject_id`——只把**同一发言人**的上一句拼进 query。B 应保留这条约束，并扩展到引用目标：引用指向的是**被引用那条消息的发言人**，不是当前发言人；`reply_to` 解析出的目标若落在 `[msg_id:…]` 可引用窗口（`context.py:1933–1977`，只标最近 12 条）之外，标注悬空而不是静默丢失。

**新窗口是否必要**：**B 的默认答案是不新建窗口。** **[代码路径]** 窗口按聊天目标复用、与话题无关（`bridge.py:1479/1565`），§1 已说明「同一窗口≠同一话题」是常态；新建窗口会把「隔天续聊」和「几秒内换题」都拆到不同窗口，反而丢掉判断所需的时间位置信号。仅当有**独立证据**支持时才评估：例如同一聊天目标里长期存在多条稳定话题簇、且回放显示混合取数的误续聊率显著高于分窗。这在 C 的数据条件里讨论，B 不预设。

## 6. 量化指标：条件式判据（不给期望值）

指标定义与判据，全部写成「结果 → 说明什么」：

| 指标 | 条件式判据 |
|---|---|
| 误提旧事 | 快照里出现无锚点的旧话题且回复续了它 → 取数把「相关性」当成了「指代」；同样快照但用户有锚点时续旧题 → 合法，不应算误提。两种输入必须成对，缺一无法证明锚点在起作用。 |
| 主动换题自然度 | 无现实关联/自然结束/来源承诺时抛开当前句提新题 → 过度主动；有上述条件且对准新句 → 恰当；新句本身模糊时发生 → 不计入独立缺陷。自然度只能人工标注，不用单一分数。 |
| 真正需续聊却漏掉 | 用户有显式找回/引用，但目标话题未进快照或回复没接它 → 漏续；目标进快照且接住 → 命中。漏续要区分「锚点没识别」与「目标已不可引用/已被挤出」两种成因。 |
| 指错人/指错消息 | 群聊里回复的说话人或引用目标 ≠ `reply_to`/锚点指向的对象 → 指错；@ 与文本冲突时按 §2 优先级判定，冲突无规则时单列「规则缺失」而非算作判错。引用目标在 12 条窗口外 → 悬空标注是否出现要单独断言。 |
| 输入长度 | 同一批消息，B 后 `compiled.summary()['tokens']` 或快照字符数上升 → 取数变宽（查是否挤掉其他车道）；下降 → 变窄（查是否漏掉锚点）。两个方向都记录，不用「变长=坏」或「变短=好」下结论。 |
| 额外调用 | 若 B 引入锚点召回/额外检索，记录每轮的 DB/检索调用次数变化：次数不变 → 改造在现有取数内；次数上升 → 分别记录用在哪种信号上，判断是否值得。不要预设「零额外调用」为目标。 |

**区分力要求**：每条正向断言都要配一条形态相反的反例输入（例如 §1 的 S-keep / S-switch 用**同一句** `「？」`），否则「按锚点区分」只是注释里的话。
