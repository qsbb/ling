## 0. 观测口径（先钉住，否则判据无法落地）

不变量必须能在**编译产物**上看出来，不能只看调用参数或日志。每条判据至少落到下面一个观察点：

- `messages[]`：编译后送给模型的消息数组；每项至少看 `role`、`content`，以及是否有来源标记字段（下称 `source`，若方案里叫别的名字，以「能定位到原始消息 id 的字段」为准）。
- `meta`/`context_meta`：召回命中列表、是否跳过召回、锚点解析结果、时间戳窗口等结构化字段。
- `reply_ids` / `ref_ids`：群聊引用回复中被引用消息的 id 列表；必须能区分「时间上一条」与「被引用的那一条」。

**条件式写法**：每条判据都写「出现 X → 说明 A；出现 Y → 说明 B」，不写「期望值 = 某固定数」。这样任何结果都有信息量。

**三态字段必须造三条**：若观察点是「跳过 / 召回 / 锚点直取」三态，三条输入都要有，且其中一条要让「跳过的错误实现」和「锚点直取的正确实现」给出**相反**结果（否则无区分力）。

**如果某个缺陷在正确实现和错误实现下观察点完全相同 → 标注「无法证明」，不强行判绿。**

## 1. 候选缺陷集合与判据

### D1 —「？」被当作旧话题相关性召回，而非指向刚才那句的短承接

**缺陷描述**：用户用「？」（或「怎么了？」「啥意思？」）对上一句做追问时，实现按关键词做相关性召回，捞回若干分钟/小时前的旧话题片段；或者反过来，把所有问号都当成短承接、从不召回。

**输入（消息序列 + 时间间隔）**：

```
私聊 uid=100200300
T0      ai:   "你的项目方案我看了，风险评估那部分写法不错。"   # 旧话题 A
T0+2h   user: "今天下午三点开会，记得帮我准备材料。"        # 新话题 B（时间锚点）
T0+2h+20s user: "？"                                      # 短承接，指向 B
```
**对照输入（可以是旧话题召回的形态）**：
```
T0      ai:   "你的项目方案我看了，风险评估那部分写法不错。"
T0+2h   user: "今天下午三点开会，记得帮我准备材料。"
T0+2h+20s user: "风险评估那部分当时怎么写的来着？"        # 显式找回，指向 A
```

**观察点**：`messages[]` 里是否含 T0 那条旧消息（用 `source`/原文片段判定）；`meta.recall_source` 字段是 `anchor:last_turn` / `semantic` / `none` 三态之一；`meta.anchor_id` 指向 B 的消息 id 还是 A。

**通过条件（条件式）**：
- 对「？」输入：`meta.recall_source = anchor:last_turn` 且 `meta.anchor_id = B.id` 且 `messages` 不含 T0 → 说明**按时间位置/锚点判定为短承接**。
- 对「？」输入：`meta.recall_source = semantic` 且 `messages` 含 T0（或任意旧话题片段） → 说明**把「？」当相关性召回**（D1 复现）。
- 对对照输入：`meta.recall_source = semantic/explicit` 且 `anchor_id = A.id` → 说明**显式找回走另一路径**。
- 若两种输入观察点完全相同 → **无法证明**有锚点区分。

**能让红的错误实现 vs 正确实现**：
- 正确实现：短承接走「上一句锚点直取」；含名词的旧话题找回走相关性/时间窗召回。
- 错误实现 D1：`recall(query="？")` 用问号做向量/关键词匹配，或对所有问句统一走语义召回。
- 区分力检验：「？」在两种实现下若都得到「不含旧消息」的结果（比如因为问号被过滤成空 query 而召回为空），则这条输入**无区分力**——必须用对照输入（带旧话题名词）或「？」+ 紧邻上一句是包含独有实体的消息（如「把 Q3 预算表发我」「？」）来放大差异：错误实现会把 Q3 预算表捞回来，正确实现只取上一句。

**配对的正向断言（防全绿没接线）**：同一轮必须断言 `meta.anchor_id == B.id` 且 `messages` 里出现 B 的**完整文本片段**（不是空召回）。只断言「旧消息不在」当「什么都没召回」时也会绿。

### D2 —「早上好」被当寒暄跳过召回，或所有问候都触发宽泛召回

**缺陷描述**：寒暄应跳过自动召回；错误实现有两个相反方向：①所有短句都召回（包括寒暄）；②所有问候都跳过（包括「早上好，接着说昨天那个方案」这种带承接的问候）。

**输入**：

```
私聊 uid=100200300
T0      user: "昨天我们定了用蓝绿部署方案，回滚脚本写好了。"
T0+18h  user: "早上好"                                    # 纯寒暄，应跳过召回
T0+18h+30s user: "早上好，接着说昨天那个蓝绿部署方案"        # 问候+显式找回，必须召回 T0
T0+18h+60s user: "你好"                                   # 另一纯寒暄
```
每条单独成轮，分别观察。

**观察点**：`meta.recall_skipped`（bool 或三态）与 `meta.recall_trigger`（`greeting` / `explicit_retrieve` / `short_followup` / `semantic`）；`messages` 是否含 T0 片段。

**通过条件（条件式）**：
- 「早上好」「你好」：`recall_skipped=true` 或 `trigger=greeting`，`messages` 不含 T0 → 说明**寒暄跳过**。
- 若「早上好」`messages` 含 T0 / `trigger=semantic` → 说明**宽泛召回错误**（D2 之一）。
- 「早上好，接着说昨天那个蓝绿部署方案」：`messages` 含 T0 → 说明**带内容的问候仍能触发找回**。
- 若该条也被跳过 → 说明**「所有问候都跳过」错误**（D2 之二，更危险：它和「寒暄跳过」在纯寒暄输入上表现相同）。

**能让红的错误实现 vs 正确实现**：
- 正确实现：识别「纯寒暄」= 不含话题延续语义的短问候；带后续从句的问候不跳过。
- 错误实现 A（宽泛）：对任何用户输入做向量召回。
- 错误实现 B（一刀切）：以「是否含问候词」为跳过条件。
- **区分力关键**：纯「早上好」在正确实现和错误 B 下结果相同 → **单靠它无法证明正确**。必须靠「早上好，接着说……」这条让 B 红；靠纯「早上好」让 A 红。两条合起来才覆盖 D2。

**配对的正向断言**：三条输入同一轮里既断言「纯寒暄不含 T0」，又断言「带承接的问候含 T0」。如果只有前两条负向断言，功能整体未接线时全绿。

### D3 — 滚动摘要无条件常驻，与当前话题无关

**缺陷描述**：滚动摘要（rolling summary）被无条件塞进每轮 `messages`，即使当前话题与摘要内容完全无关；或者相反：从不在 `messages` 里出现摘要，导致跨轮信息实际丢失却被判「摘要正常工作」。

**输入**：

```
私聊 uid=100200300
T0      user: "我养了只猫叫橘子，去年做的甲状腺手术花了我 8000。"
T0+30min user: "今天股市大盘怎么样？"     # 与猫完全无关
T0+30min+10s user: "能说说影响因素吗？"   # 短承接，指向大盘话题
```
另设对照输入：
```
T0+31min user: "橘子最近怎么样？"        # 与摘要强相关
```

**观察点**：`messages` 中摘要段是否存在、其内容是否包含「橘子」「甲状腺手术」「8000」；`meta.summary_included`（bool）及 `meta.summary_reason`（`relevant` / `always` / `none`）；摘要若存在，是全文还是只相关句。

**通过条件（条件式）**：
- 无关话题轮：`summary_included=false` 或 `summary_reason!=always` 且 `messages` 不含「橘子/甲状腺/8000」→ 说明**摘要按相关性门控**。
- 无关话题轮摘要仍出现且含「橘子」→ 说明**无条件常驻**（D3 复现）。
- 相关话题轮：`messages` 含「橘子」且 `summary_reason=relevant` → 说明**门控没有把摘要整体砍掉**（否则是「一刀切关闭摘要」的另一种错误）。
- 两轮都没有摘要 → **无法证明**摘要功能在工作；只能证明「没常驻」。

**能让红的错误实现 vs 正确实现**：
- 正确实现：摘要作为可检索的上下文片段，命中当前话题/锚点才注入。
- 错误实现 A（常驻）：每轮把整段滚动摘要作为 system/context 消息注入。
- 错误实现 B（常关）：为避免常驻，干脆不注入任何摘要。
- 区分力：无关轮同时让 A 红、B 绿；相关轮同时让 B 红、A 绿。必须两轮都跑，否则任一单轮都分不清。

**配对的正向断言**：同一轮同时断言「无关轮不含摘要」和「相关轮含摘要」；并且摘要中的**独有实体**（「橘子」）必须在 `messages` 里出现——只断言 `summary_included=false` 在「整个摘要功能未实现」时也绿。

### D4 — 显式找回（「接着说前天那个方案」）与短承接（「后来呢？」）走同一路径、无锚点区分

**缺陷描述**：两类输入都进同一个 `recall()`；或都判定为短承接只取上一句；或都用关键词匹配。判据要求两者在 `meta` 上出现**不同**的处理标记，且 `messages` 内容指向不同历史位置。

**输入（同一会话，两条独立轮）**：

```
私聊 uid=100200300
T0        user: "前天那个方案是用 Kafka 做削峰，我倾向于 A 版。"   # 远锚点 A
T0+1min   ai:  "收到，A 版我记下了。"                            # 近锚点 B（上一句）
T0+2day   user: "接着说前天那个方案"                             # 显式找回 → 应指 A
T0+2day+1min user: "后来呢？"                                   # 短承接 → 应指 B（上一句）
```

**观察点**：`meta.retrieval_mode`（`explicit` / `short_followup` / 其他）必须**不同**；`meta.anchor_id` 分别 = A.id 与 B.id；`messages` 分别含「Kafka / A 版」与「收到，A 版我记下了」的片段。

**通过条件（条件式）**：
- 显式轮：`mode=explicit` 且 `anchor_id=A.id` 且 `messages` 含 Kafka → 说明**按「前天」时间词定位到远锚点**。
- 短承接轮：`mode=short_followup` 且 `anchor_id=B.id` 且 `messages` 含「收到，A 版我记下了」→ 说明**按上一句定位**。
- 两轮 `mode` 相同 → 说明**无锚点区分**（D4 复现），即使恰好都捞对内容也算未覆盖不变量。
- 两轮 `anchor_id` 都 = B.id → 说明**统一走短承接**，显式找回被降级。

**能让红的错误实现 vs 正确实现**：
- 正确实现：时间词/指代消解 → 显式召回；无时间词短承接 → 上一句锚点。
- 错误实现 A（统一召回）：两条都做语义搜索；若「后来呢？」也能搜到 Kafka 段，则短承接轮 `anchor_id` 错。
- 错误实现 B（统一取上一句）：显式轮也只取「收到，A 版我记下了」，`messages` 不含 Kafka。
- 区分力：显式轮让 B 红，短承接轮让 A 红；两轮缺一不可。

**配对的正向断言**：在两个 `anchor_id` 上做不等式断言（`A.id != B.id` 且分别相等），不能只断言「messages 不为空」——那条在两条路径都乱捞时也会绿。

### D5 — 群聊引用回复指向时间上一条而非被引用的那条；指错说话人

**缺陷描述**：群聊里 A 在 10:00 发了消息，B 在 10:05 引用它，但实现把「引用对象」解析成 10:04 的时间上一条，或从消息文本误推说话人。

**输入**（群 `100200300`，均为假数据）：

```
10:00  userA(100200301): "我把部署文档放在 wiki 的 /deploy/v2 了"
10:02  userC(100200302): "收到，我看一下"
10:04  userB(100200303): "这个链接打不开"
10:05  userA(100200301): "[reply to 10:00 userA] 我更新了，再试试 /deploy/v3"
```
最后一条的 ref 结构是显式 `reply_to=<10:00 那条消息的 id>`，不是靠文本猜。

**观察点**：`reply_ids` / `ref_ids` 里的消息 id 必须 = 10:00 那条；编译后 `messages` 中被引用消息的 `speaker`/`role.name` = `userA(100200301)`；`meta.resolved_ref_id`。

**通过条件（条件式）**：
- `reply_ids` 含 10:00 的 id 且 `speaker=userA` → 说明**按显式 ref 解析，且说话人取自 ref 目标**。
- `reply_ids` 含 10:04 的 id（或说话人 = userC/userB）→ 说明**按时间上一条解析 / 说话人猜错**（D5 复现）。
- 若 `reply_ids` 为空但 `messages` 里出现了 10:00 的文本片段 → **无法证明** ref 被正确解析（可能只是语义召回碰巧命中），必须要求 id 级断言。

**能让红的错误实现 vs 正确实现**：
- 正确实现：读消息结构里的 `reply_to`/`quote` 字段定位被引用消息，说话人从被引消息取。
- 错误实现 A（时间上一条）：`messages[-2]` 或按时间最近的其他人消息。
- 错误实现 B（文本猜引用）：从「再试试」推断引用对象、从「我」猜成当前说话人。
- 区分力：选 10:00 与 10:04 **文本完全不同且说话人不同**两条，A/B 都会红；但若 ref 指向的恰好是时间上一条，则无法区分——因此输入必须让 ref 目标**不是**时间上一条（上面的 10:02/10:04 两条间隔就是为制造区分力）。

**配对的正向断言**：同一轮同时断言 `resolved_ref_id == 10:00.id` 且 `speaker == userA` 且 `messages` 含 `/deploy/v2`。只有「不是 10:04」的负向断言在 ref 完全未接线时会绿。

### D6 — 换窗口「修好」反例但同时丢掉真正需要续聊的上一句

**缺陷描述**：为修掉「跨窗口误召回」而把窗口切换当作硬边界，结果在新窗口第一句「继续」时，连真正需要续的上一句（同会话但跨窗口边界的那条）也拿不到了。

**输入**：

```
私聊 uid=100200300（会话 S1，旧窗口 W1）
T0      ai:   "方案 A 的风险我已列好，回头继续。"
T0+5min user: "好，先这样。"                # W1 最后一条
--- 用户新开窗口 W2（同一会话 S1）---
T0+6min user: "继续"                        # 需要 W1 的上一句
--- 另一会话 S2（不该串）---
T0+7min user（S2）: "继续"                   # 不该拿到 S1 的内容
```
分别观察 W2 的「继续」与 S2 的「继续」。

**观察点**：`messages` 是否含 T0 的「方案 A 的风险...」片段；`meta.window_boundary_applied`（bool）；`meta.anchor_id`；`meta.session_id`。

**通过条件（条件式）**：
- W2「继续」：`messages` 含 T0 片段 或 `anchor_id=T0.id` → 说明**窗口边界未切断必要续聊**。
- W2「继续」：`messages` 不含 T0 且 `window_boundary_applied=true` → 说明**硬边界切断了续聊**（D6 复现）。
- S2「继续」：`messages` 不含 S1 的 T0 → 说明**会话隔离仍在**。
- S2「继续」含 S1 的 T0 → 说明**跨会话串台**（另一种缺陷，同时暴露）。

**能让红的错误实现 vs 正确实现**：
- 正确实现：窗口边界只影响「召回范围」，不阻断「上一句锚点直取」；会话 id 仍是硬边界。
- 错误实现 A（硬窗口）：`if new_window: recall=[], anchor=None`。
- 错误实现 B（无边界）：跨会话也召回上一句。
- 区分力：W2 轮让 A 红，S2 轮让 B 红；只测其中一轮都会漏。

**配对的正向断言**：W2 轮断言「含 T0 片段」是正向；S2 轮断言「不含 T0」是负向，必须和 W2 的正向在同一实验里同时成立，否则「整个召回关闭」时 S2 轮也绿。

## 2. 「半成品红」设计（把轻量方案拆两半）

把「第一期的上下文取数改动」按职责拆成两个**可独立存在的半成品**：

- **半 A：锚点 / 时间位置判定**（能识别「指向上一句」「指向引用目标」「指向时间词指定的远锚点」，但**不改召回 query**，即所有召回仍用原始 query 或空 query）。
- **半 B：召回 query 调整**（会给 query 加主体词/时间词/去寒暄，但**没有锚点判定**，即把所有输入都当同一类，靠 query 文本区分）。

对每条判据问：在半 A / 半 B 下，它是红还是绿？

| 判据 | 半 A（只有锚点判定） | 半 B（只有 query 调整） | 两半都绿意味着什么 |
|---|---|---|---|
| D1（「？」短承接） | 绿（锚点指向上一句，不召回旧话题）——只要有「上一句」字段 | **红**：B 无锚点，query「？」经调整仍可能空/命中旧话题；或对「？」一律语义召回 | — |
| D1 对照（旧话题找回） | **红**：A 无 query 改写，「风险评估那部分当时怎么写的来着？」可能锚到上一句 B 而非 A | 绿（query 含话题词，能召回 A） | 两条都绿才证明两半都在 |

## 3. 最值得补的一组实验（在证据不足处把候选原因分开）

## 7. 最值得补的一组实验（落到可执行的最小集）

第 3 节给了三组，这里按读方案后的事实收敛到**一个最小实验**，它一次运行同时给出正负信号，且能分开「摘要常驻」「宽泛召回」「原文按时间取数」三个候选原因：

**E-min（D3 来源三分实验，同一会话同一份快照里做）**：

```
会话：私聊 uid=100200300
T0   user: "昨天定了四项需求，其中第三项是蓝绿部署。"     # 旧话题，将被压进摘要
... 若干扰语段使 T0 被挤出原文窗口，进入 window_ctx.summary ...
T1   user: "早上好"                                     # P3 实测：不跳过召回，query="早上好"
T2   user: "？"                                          # 紧接 T1，plain 空 → 跳过召回
观察 T2 的编译产物：
  - messages 里 lane="summary" 块是否存在、是否含「蓝绿部署」
  - meta.evidence_selected / memory_hits 是否 >0
  - 紧接 T2 再发 T3: "蓝绿部署那项后来怎样？"             # 相关轮正向对照
观察 T3 的 messages 是否含「蓝绿部署」，以及这次来源标记是否从 summary 切到原文/召回
```
**结果→归因（条件式，不是期望值）**：
- T2 摘要含「蓝绿部署」且 `evidence_selected==0` → 来源是摘要常驻（D3 成立）。
- T2 摘要含「蓝绿部署」且 `evidence_selected>0` → 两来源同真，分别计数（LEAD §6.5）。
- T2 不含但 T3 含 → 来源不是常驻，而是显式找回/相关性召回；D3 不成立。
- T3 也不含 → 不是「常驻」而是「摘要/原文整体丢失」，另一个缺陷。

**真实输出 vs 脚本模拟**：
- [真实] 标记条件：通过 `ContextCompiler.compile()` 真实编译，从返回对象读 `messages`、`meta["evidence_selected"]`、`meta["memory_hits"]`、`lane`；同时抄录 `git rev-parse --short HEAD` 与被测文件 sha256。
- [脚本模拟] 标记：像 P3 §0 那样直接调 `should_skip_automatic_recall('？')` 得到 True——这只能证明**纯函数的门槛**，不能证明编译产物里没有旧话题。它属于生成假设，不能进覆盖矩阵。
- 覆盖矩阵里目前 D1/D2 的「P3 实测」全属脚本模拟，所以填「无法证明」；D3 的「代码路径」属推理，所以只到「部分覆盖」。

**对 lead 的建议**：E-min 比 LEAD §6 的 5 条分散判据更值得先做，因为它在**同一次运行**里同时验证「负向（无关轮不出现旧事）」和「正向（相关轮出现旧事）」，并顺手给出三个候选原因的分离。若只能做一条实验，做这条。
