## 1. 我做出的决定

- 正常新装：从可信发布页取得经过签名/证明的安装包，宿主运行一次 `ling install`；交互式选择数据目录、监听地址/端口及管理员账号。安装器自动核对 Docker/Compose、拉取经核验的应用镜像和配套更新器镜像、创建受限配置及卷、启动数据库/API/worker/更新器、执行一次迁移、检查健康，最后打印控制台地址。宿主不需要仓库、Python、Node、pnpm 或现场构建。以后支持 `ling status|doctor|backup|restore-drill|logs`；这些命令是救援入口，普通更新不需要运行它们。
- 日常更新：所有者在现有「设置 -> 关于与版本」点击「检查更新」，看到当前/目标版本和可安装状态，再点「更新」并二次确认。后台先拉镜像并预检，再进入短时维护、做一致备份、显式迁移、起 API/worker 并验证。页面可暂时断开，重连后接着显示同一任务；成功以运行容器 digest、应用提交和迁移 head 三者核验为准，不以 Compose 命令退出 0 或页面重新连通为准。
- 默认只提供**升级到经验证、支持从当前版本迁移的稳定版**。不提供随意选旧版本或“一键降级”；同一 `0.x` 不代表数据库兼容。失败后是否能恢复旧应用由是否已迁移和运行时证据决定，不承诺数据库自动回退。
- 更新器独立于应用 Compose 项目运行，**不随每次 API 重启而重建自己**。API/worker 不挂 Docker socket，不执行部署；只有更新器能调用 Docker，持有宿主级权限。控制台只能提交固定格式的目标请求，不能传 shell、镜像 URL、Compose 片段或任意路径。安装器和更新器分别保留自己的最小可信代码，拒绝执行目标镜像中的部署脚本。
- 这是单机、计划内短暂停机的方案，不假装零停机。首次从现有测试安装迁移是独立的人工维护作业；先按镜像设计完成卷、端口、旧镜像/前端和备份核验，**首轮不在旧源码模式下打开网页一键更新**。

## 2. 现状为何做不到

当前 `deploy/install.sh` 能一条命令安装，但在宿主构建源码和 Web，并不负责给普通部署安装宿主更新执行器。`deploy/update/executor.py` 已有请求/状态、备份和锁的契约，却从 GitHub 拉源码、构建并再调用旧安装器，不能直接用于镜像模式。控制台的 `AboutPage.tsx` 已能检查最新 Release、确认、轮询和处理断连；`/v1/version/update-requests` 只接受最新 Release 且依赖执行器在线，`LING_UPDATE_ENABLED` 默认是 0。只给 Compose 换成 `image:`、只在界面增加按钮，都不能得到可用的一键更新。已有按版本方案 `shots/update-design/UPDATE-BY-VERSION.md` 提出 socket 容器和自动回退，但“同 major 即可降级”与“迁移后自动恢复旧代码”缺少 schema 兼容性证明，不能作为交付承诺。

## 3. 首次安装的交互与交付

1. 官方发布提供 Linux amd64/arm64 的轻量安装包和固定版本的安装入口；站点展示发布来源、版本、签名/证明与校验方法。**不执行 `curl | sh`、不信任可改写的 Release 正文或仅凭 `latest` 标签**。下载/校验步骤应由官方提供短命令或发行包中的 `ling` 完成；第一份安装包仍有引导信任问题，必须明确官方地址、可信签名身份和可离线核验方式，不能把 HTTPS 下载本身写成供应链证明。安装包及更新器以受保护源码构建，锁定版本并附验证材料；实现前不提供貌似可复制的虚构命令。
2. 交互只问用户能判断的项目：安装目录/备份目录、对外监听地址及端口、是否已有反向代理、管理员用户名。默认本机访问；选择局域网开放时提示 TLS/反代和防火墙边界，不自动开放公网。初始管理员口令用安全随机数生成并仅在受限终端显示一次；根密钥独立生成并写入受限持久文件，不默认明文回显，提供带权限检查的离线恢复材料导出/保管指引。首次登录强制改密码；已有受限 `.env` 时绝不覆盖。选择测试模式必须显著说明不会调用真实模型。通道密钥、模型供应商等留到登录后的设置页。
3. 安装前列明将创建的目录、项目名 `ling`、容器、两个数据卷的实际名称、端口、备份位置、将拉取的镜像摘要；检查端口占用、磁盘空间、Docker 权限、Compose 兼容性、GHCR 可达性与架构。若发现同名 Compose 项目/卷/数据库，**进入“现有实例迁移”流程并停下新装**，绝不以空白安装覆盖或另建同名空卷。
4. 安装器写入权限受限的配置和稳定的 Compose 文件组，应用与 worker 使用同一个固定 OCI index digest；更新器以单独 `ling-updater` 项目、固定 digest 运行。安装状态保存实际 digest、源 SHA、安装器/更新器协议、卷身份和备份配置。更新器状态/日志在持久宿主目录；API 仅获得写请求/读状态的最小目录权限。正式支持网页更新以前，安装器不得显示“已启用”或提前设置 `LING_UPDATE_ENABLED=1`。
5. 首次安装完成后展示实际 URL、当前版本、管理员登录方式和备份状态。建议默认安排定期备份并在安装验收中完成一次恢复演练；若备份目录/恢复点不满足要求，页面明确“可使用但不可一键更新”，不能因为服务已就绪就报“安装全部完成”。有不支持 systemd 的 NAS 时，更新器仍由 Docker 的 restart policy 接管，不要求用户安装宿主 Python/systemd 服务。

## 4. 更新器与信任边界

- CI 发布应用的多架构固定镜像摘要、完整源 SHA、Web 清单和可验证的摘要-源码绑定；更新器也独立发布经验证的固定镜像。可信发布目录只列已通过门禁、可从已知版本升级的稳定目标，记录最低更新器协议版本、是否有迁移、预计下载大小及必要的版本跨度。API 展示的是目录信息，**更新器要自己重新校验发布证明、仓库、源提交、目标摘要、平台和当前运行 digest**，不能相信页面/API 提交的 tag 或 Release 正文字段。签名不能让恶意的可信发布代码变安全，因此更新器只运行自身审核过的发布逻辑，目标镜像仅作为应用与一次性迁移进程执行；仍需受保护的发布权限和审计。
- 更新器采用独立无外部端口的 Compose 项目，持久化单飞锁、任务 ID、阶段、前后 digest、备份标识及关键确认信息。它需要 Docker socket，等同能控制宿主；只允许受信任的固定镜像和宿主配置访问 socket，限制可写宿主目录、只读根、无特权网络入口，**这些不能消除 socket 的宿主级风险**。拒绝在 API/worker 或浏览器进程中挂 socket。更新器自己的升级不跟随应用 `compose up`：协议保持向后兼容并有最低版本门禁；确需替换更新器时由安装包的受信任维护命令独立升级并验证，未完成前暂停网页更新。不要让更新器在任务未记账时自删/自重启，也不承诺以后完全不用宿主维护。
- 继续复用“API 写一次请求、更新器写脱敏状态、前端轮询”的方向，但镜像更新使用**新协议/实现**，旧 `executor.py` 的源码下载、构建、`install.sh` 阶段不能原封不动搬来。请求只含经校验的发布身份、预期当前 digest/commit、不可重复的任务 ID 和操作者确认；所有者权限、最近登录校验、同源/CSRF、限流和冲突检查在 API 做一遍，在更新器按当前容器与发布目录再做一遍。`LING_UPDATE_ENABLED` 只在新更新器在线、协议兼容、备份/恢复门禁齐全并完成真机演练后打开。
- 版本检查失败、更新器离线或旧镜像已不受支持时，按钮禁用并给出可执行的恢复指引。更新器只展示经过码表脱敏的进度/失败原因；密码、Docker 配置、原始日志及备份路径不返回网页。页内只展示“下载、预检、备份、迁移、切换、验证”等真实阶段，不用假的百分比/剩余时间。

## 5. 一次网页更新的实际顺序

1. **准备（旧服务在线）**：获取目标 digest 与可信证明，拉取对应平台镜像并校验身份；检查当前运行 image ID/digest、卷、端口、更新器协议、磁盘与数据库迁移链。已有 cron/旧安装器/人工任务要能被同一跨工具锁阻止；持锁直到完成验证或人工停机交接。需要解锁/消耗日常备份的操作先经过隔离恢复演练。
2. **维护与一致备份**：前端告知即将断线。安装器/更新器实现受控维护门禁，阻断 HTTP 写入、机器人入站、后台任务及所有已知写者，等待在途任务排空；维护门禁必须由更新器在应用生命周期之外控制，并在新 API 启动后仍能强制阻断公开端口及机器人输入，不能仅靠旧 API 内的开关。停 API/worker 后，用受信任的一次性只读取数工具读取 `app-data`，对仍在线的 db 导出 dump/墓碑，确保没有旧 API 依赖。校验 dump、媒体、有效根密钥、env 密钥材料及 manifest 属于**同一恢复点**，密钥与 dump 分开限权保存，并在不同故障域留有恢复副本。当前 `backup.sh` 依赖运行中的 API 且退出 0 不证明完整，需先改造和实测；静默、校验、空间或恢复演练任一门禁不达标，旧服务恢复运行但本次更新不得进入迁移。不要允许“媒体部分备份”作为默认更新放行条件。
3. **迁移与切换**：保持原 db 容器、`ling_db-data`、`ling_app-data` 不变；镜像模式 API 默认 `LING_RUN_MIGRATIONS=0`，一次性 `run --rm --no-deps -e LING_RUN_MIGRATIONS=1 api migrate` 执行目标镜像迁移，核对日志与 `alembic_version` 等于目标 Alembic head。再按目标 digest 启动 API，核实 `/readyz`、登录、Web 清单/提交及应用只读检查；启动 worker 并检查 outbox/连接。维护写门禁在测试通过前一直有效，不能因为新 API 已绑定宿主端口就允许外部写入。
4. **收尾**：重新确认实际运行的两个容器是同一目标摘要、版本/提交与发布证据相符、DB 在目标 head；确认备份任务的 Compose 文件组/环境变量未漂移并可定期产出可恢复备份。持久写入成功记录后解除维护、恢复入口与定时任务；页面重连后只认同一任务 ID 和新旧版本实测，不从一个 502 猜测成功或失败。

## 6. 故障时给用户什么结果

| 发生阶段 | 允许自动做什么 | 网页表达 |
| --- | --- | --- |
| 拉取、预检、备份失败，且没有迁移 | 不动或恢复旧 API/worker，验证旧 digest/服务；保留失败记录 | “更新未开始/未切换，仍在旧版本”，只有实测旧服务正常才能这样说 |
| 已迁移，目标启动或验证失败 | 继续维护/停写，记录 schema、旧/新 digest、恢复点；允许已证明安全的前向修复；**不自动切旧镜像或恢复旧 dump** | “更新未完成，需要维护处理”，给操作员恢复入口，不提供一键无条件重试/忽略 |
| 更新器重启、页面断连、状态未知 | 按持久任务 ID 和容器/DB 实况对账；不能确认则停在人工门禁 | “正在确认状态”，不新建第二次任务 |
| 已成功，后续业务出问题 | 重新打开维护，按数据兼容性和恢复点做人工决策；旧镜像仅用于经过验证的兼容方案 | 不展示会误导的“回退版本”按钮 |

恢复旧库必须连同同恢复点的媒体、根密钥、env 和后续新增的撤回墓碑处理；恢复点后的正常数据可能丢失，须人工确认。安装器提供 `doctor`、`restore-drill` 和受控人工恢复工具，网页可以给出任务编号和清晰的下一步，但不能把“以当前运行为准”作为跳过验证的自愈按钮。支持更新器离线时的宿主命令救援，这是必要的诚实边界。

## 7. 怎么分阶段实现与验收

1. **先打包，手动升级可用**：完成原镜像设计中的 CI、摘要证明、多架构 Web 打包、镜像 Compose、独立部署包和安装器。隔离空白新装以及真实备份恢复成功后，再迁移测试机；此阶段控制台更新按钮禁用。验收：无需宿主编译工具；新装不覆盖现有实例；旧数据卷、端口与密钥不变，旧版能按归档材料人工恢复。
2. **更新器闭环**：实现独立更新器/持久任务状态、可信目录解析与发布绑定、同一跨工具锁、维护门禁及支持 API 停机的一致备份。让现有 `check-release`/`update-requests` 与页面按新的可安装条件演进；旧协议必须显式拒绝或兼容，不能在同一 `v1` 语义下偷偷改成不同更新源。先在隔离项目完成一次新装、两次连续网页升级、更新器重启后恢复对账，才能在测试机开启 `LING_UPDATE_ENABLED=1`。
3. **故障注入与交付**：覆盖拉取失败、恶意/错摘要、发布证据不符、备份缺媒体/根密钥、迁移跳过或失败、schema head 不一致、端口冲突、断电/更新器重启、断连重连、旧执行器残留和并发请求。每次演练都检查卷身份、密钥可解密、墓碑不复活、cron 的实际备份与隔离恢复；不能通过的故障路径应禁用网页更新，不靠提示文案放行。

最低验收不是“页面有按钮”，而是：一台干净 Linux/NAS 上取得并核验安装包后能只靠安装器完成新装；正常版本更新无需 SSH/本地构建；所有失败都能说明当前实际运行版本及恢复状态，未知状态不会伪装成功；带数据更新与恢复演练证实无卷、密钥、媒体及撤回信息丢失。旧 `install.sh` 和 `UPDATES.md` 继续描述源码模式，镜像模式交付后要明确各自边界，并把控制台旧的“拉取并构建”文案改成实际的“下载并验证镜像”。
