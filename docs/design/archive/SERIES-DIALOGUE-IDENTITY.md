# 「凝心溯溪」对话与身份设计考古：言、序对 ling 的启示

> 范围与出处：下文的「言/」「序/」分别指 `/Users/lingxi/project/astrbot_plugin_conversation_flow/`、`/Users/lingxi/project/astrbot_plugin_identity_guardian/`；「ling/」指本仓库。`文件:行号` 均以此前缀为根目录。**「作者明确」**指 README、metadata、CHANGELOG 或设计文档写下的意图；**「实现核对」**指代码现状；**「推断/建议」**是本文判断。历史草案只用于还原动机，不能当作现行实现依据；两仓都在归档声明中明确了这一点。（言/`docs/implementation-plan.md:1-7`；序/`开发文档.md:1-15`）

## 1. 系列定位

- **作者明确**：系列按职责拆分，言负责「怎么说、何时回应、如何衔接」，序负责身份、关系、权限边界和群组行动；序的历史设计文档将二者概括成言解决「怎么说」、序解决「能做什么」。系列片段由序、知、情登记，言在同一次主模型请求中排序、去重和收敛，安全边界先于知识与表达约束；这不是两个模型轮流答话。（言/`README.md:3-16`、`README.md:50-60`；序/`开发文档.md:1701-1711`）
- **推断**：作者追求的「像人」不是给裸 LLM 多写一段人设，而是把**发言时机与节奏**、**身份及行动资格**分给不同的组件。证据是言明确处理「逢 @ 必回」「一大串文字」「打断群友」等链路痛点，序明确反对把核心定位成自动群治理。（言/`README.md:34-44`；序/`README.md:37-59`）

## 2. 「言」的设计意图与关键机制

### 为什么存在

- **作者明确**：元数据把目的写为让 AstrBot 更自然地判断何时回应、如何分段、怎样衔接上下文，并处理群聊参与、短期跨会话连续性、图片意图和服务式追问收尾。README 把具体缺陷列为「bot 逢 @ 必回且永远精神饱满」、换平台后丢话题、短追问丢对象、多 bot 刷屏、打断群友、图片一刀切和重复客服式结尾。（言/`metadata.yaml:3-6`；言/`README.md:34-44`）
- **作者明确，历史缘起**：最初三项需求是自然收口时可沉默、长回复按真人节奏分段、思考期间收到补充时抑制旧答并衔接新消息。后来功能扩展，不能把早期计划中的示例词或路线当成今天的规则。（言/`docs/implementation-plan.md:1-7`、`docs/implementation-plan.md:39-45`）

### 何时回应：模型参与，但默认不另开一轮模型

- **实现核对**：默认 `silence_enabled=true`、`silence_strategy=inject`。言在已有的 `on_llm_request` 中把高门槛沉默指令加到 `extra_user_content_parts`；主模型若在该次生成中输出 `<SILENCE/>`，回复阶段清空结果。**这不增加独立预判调用，却仍需本轮主模型推理；不能把它说成「沉默零 Token」。** 指令优先允许普通问候、呼唤、撒娇、求关注得到回应，「好的/嗯/谢谢/晚安」不能凭词面一刀切，不确定时短答。（言/`README.md:117-134`、`README.md:463-482`；言/`core/silence_judge.py:123-130`、`core/silence_judge.py:152-166`）
- **作者明确**：可选 `prejudge` 会先调轻量 LLM 输出 JSON；判定沉默则拦下主模型，`both` 则预判后仍允许主模型决定。预判至多针对 200 字的输入；代码对空文本、超长文本和信任白名单跳过。因此「言完全不调额外模型」只适用于默认 inject 及本地规则路径，不适用于显式开启预判、可选分段助手或其他特殊后台能力。（言/`README.md:119-126`、`README.md:486-498`、`README.md:136-151`；言/`core/silence_judge.py:159-166`、`core/silence_judge.py:206-233`）
- **实现核对**：有些「这次不回」在模型之前就能决定：群聊读空气命中滑窗回复上限或重复礼貌收尾时，直接静默、不发起 LLM；极低回复意愿还可概率硬静默，但明确求助/紧急消息不会被硬静默。模型层的 `<SILENCE/>` 则用于需要语境辨别的自然收口。（言/`README.md:334-352`、`README.md:370-386`、`README.md:463-480`）
- **设计取舍，作者明确**：硬限流默认设得宽松（120 秒 6 次），因为阈值太低会错拦连续聊天的人；群内「正在对别人说」默认只给主模型软提示，硬拦关闭，因为错拦「@ 别人但也想让 bot 看」的损失比多回一句更难接受。（言/`README.md:338-352`、`README.md:420-424`；言/`core/config.py:78-91`）

### 停顿、分段、插话与收尾

- **作者明确**：默认分段先让主模型用双空行表达段落意图，原段落优先保留；没有主动分段时才用标点和长度规则兜底，短回复不因普通句号/逗号硬切，代码块与混合媒体保护原结构。默认常规触发线 60 字、最多 5 段；段间延迟默认按有效字符数计算并夹在 500–4000 毫秒。其历史目标明确是「长回复拆成多条按真人节奏发送」，但是否真的像人打字，文档里没有实验结论。（言/`README.md:81-98`、`README.md:136-151`；言/`docs/implementation-plan.md:39-45`）
- **作者明确的取舍**：可选 `chunking_llm_assist` 默认关闭，因额外耗 Token；未分段长文才可能另调轻量模型。单段保持宿主默认发送链，避免与 TTS 等装饰插件冲突；多段才由言逐段发送。早期曾因规则误切完整段落而增加保护，说明「机械按长度切」不是作者最终追求。（言/`README.md:136-151`、`README.md:500-517`；言/`docs/implementation-plan.md:30-37`）
- **作者明确**：插话是逻辑上的旧结果失效、下一段前停发，并非保证取消 Provider 端推理或撤回已发段落；这限制了「打断即可省掉旧模型成本」的说法。（言/`README.md:46-48`；言/`docs/implementation-plan.md:19-26`）
- **作者明确**：「服务式追问收尾」指反复以「还需要我帮你……吗」「有需要随时告诉我」结尾。默认按会话和当前用户、900 秒窗口记连续次数，命中 2 轮后从提醒升级为禁止征询式结尾；只看**实际交付的最终回复尾部**，不禁止正文里必要的澄清问句。本地正则与内存计数完成检测，不为此另调 LLM。（言/`README.md:356-364`；言/`core/followup_guard.py:1-5`、`core/followup_guard.py:56-65`、`core/followup_guard.py:75-89`、`core/followup_guard.py:128-146`；言/`core/prompts.py:9-36`）

### 群聊参与与短期跨会话连续性

- **作者明确**：消息链中的 @ bot、引用 bot 是强「对我说」信号；@ 别人、引用别人是强「对他人说」信号；昵称命中只算弱信号，缺省面向全群。整个场景检测是本地规则、零额外 Token；对别人的话默认软提示主模型少接或不接，硬拦仅在强信号且本轮未唤醒 bot 时可选开启。**这不是对所有未唤醒群消息逐条调用模型做参与裁判。**（言/`README.md:388-424`；言/`main.py:5791-5846`）
- **作者明确**：被唤醒时才默认注入最近群聊上下文，默认 10 条，并保留 bot 自己的发言及引用归属；「先发正文，随后单独 @Bot」有 15 秒反向唤醒窗口，但单独 @ 只是让 bot 回看并判断，不等于必回。群上下文由插件维护，因为 AstrBot 没有跨平台获取群历史的 API。（言/`README.md:259-285`）
- **作者明确**：同一人的跨会话近期感知**默认关闭**，仅限管理员在情中验证并绑定的同一自然人。默认硬保留 120 分钟，内存中每人最多 64 事件、全局最多 2048，查询最多扫描近 24 个候选，重启清空；「保留」不代表每轮注入。（言/`README.md:233-243`、`README.md:257`；言/`docs/recent-activity-context-design.md:1-23`、`docs/recent-activity-context-design.md:166-175`）
- **作者明确的取舍**：当前会话相关完整轮次优先；跨会话「好/嗯/继续」只在 5 分钟内恰好一个其他私聊候选时弱承接，5–30 分钟需话题或实体重合，30 分钟后需明确跨会话指代。普通命中最多 1 个、600 字胶囊，明确承接最多 2 个、1200 字；时间只排序，不单独授予注入资格。这样避免「最近 N 条」压过当前焦点，或把「聊过游戏」误写成「正在玩游戏」。普通聊天只做本地校验与有界扫描，不新增同步 LLM 调用。（言/`README.md:243-257`；言/`docs/recent-activity-context-design.md:25-56`）

## 3. 「序」的设计意图与关键机制

### 为什么存在：让行动能力随身份而变，同时保证不越权

- **作者明确**：序的核心**不是自动群治理**，而是把身份、关系、对象与风险映射为可执行行动，使情绪、人设和对话意图能安全落地。历史需求写得更直接：bot 不只回复，还要知道自己在当前群的地位、正与谁交流，才能处理本人请求、与主人互动、群信息管理等情境。（序/`README.md:37-59`；序/`开发文档.md:21-36`、`开发文档.md:50-63`）
- **作者明确的取舍**：「身份不等于授权」「允许行动而非强制行动」；bot 的群 role 仅是平台能力上限，最终还看请求者、目标、关系、动作与配置。普通成员可以请求影响自己，却不能凭一句话让 bot 处罚第三人；强保护身份与严格限时的互动例外分开。（序/`README.md:50-59`；序/`core/prompts.py:27-53`）
- **作者明确，历史对比**：传统群管更像关键词规则加静态命令；序针对的是同一 bot 在不同群、不同对话对象面前**能对谁做什么**。AstrBot 历史上全局工具激活无法同时按群 A/B role 开关，早期草案用全局可见加运行时校验；现行实现又加了**请求级工具过滤**，以免普通成员群里看见管理员工具，但执行前的 `PolicyEngine` 仍是安全门。（序/`开发文档.md:27-36`、`开发文档.md:431-448`；序/`CHANGELOG.md:455-470`；序/`main.py:1310-1342`）

### 三方身份与受控行动边界

- **实现核对**：身份以平台事件的 bot ID、发送者原始 ID、当前 `platform_id + group_id` 为输入；群 role 从 OneBot 查询并按「平台实例、群、用户」缓存，查询失败降为 member 且不缓存。**目标**不是默认把发送者等同于受影响者：有 `target_id` 且不同于 sender 时另查目标 role/关系，再交给策略判断。（序/`README.md:25`、`README.md:63-67`；序/`core/identity.py:21-22`、`core/identity.py:62-77`、`core/identity.py:83-125`、`core/identity.py:128-176`）
- **实现核对**：`on_llm_request` 先按当前事件构造 actor，按 bot role 过滤本请求不可用工具，再计算允许行动描述，登记 `identity.boundary` 和 `identity.security_rules` 提示片段。提示内容把 bot 身份、当前发送者身份/关系和行动边界作为平台与代码事实告诉主模型；与言协作时由言优先编排，未安装言时仍直接注入。**提示只帮助模型少试错，不是授权凭证**；每次实际有副作用的工具调用还要走策略和 API 护栏。（序/`main.py:1240-1248`、`main.py:1271-1342`；序/`core/prompts.py:27-53`；序/`core/policy.py:1-4`、`core/policy.py:92-104`；序/`README.md:88-90`）
- **作者明确**：社交关系标签与操作授权分轨。主人/控制管理员等权限按当前原始平台账号与配置判定，情的「同一自然人」只用于连续性，不使另一个已合并账号自动取得群管、保护或主动消息权限；自称主人、昵称相同也不能提权。（序/`README.md:25`、`README.md:50-59`、`README.md:92-107`；序/`core/identity.py:128-150`）

### 按 Bot/群隔离的入群审核，以及隐私方向

- **作者明确**：入群审核控制面配置按 `platform_id + group_id` 隔离，新群/未配置群两个开关默认关，刷新群列表不暗中写配置。**推断**：这防止多 Bot 或多群共用同一审核开关、题库、通知目标，避免一个群的答案或审批流程误作用到另一个群。（序/`README.md:225-233`；序/`core/join_review_store.py:245-271`、`core/join_review_store.py:630-635`）
- **作者明确**：开自动审核时，先看该群预设、再看知识库证据；预设答案语义比对或有证据的判断才可能调用审核 LLM，无高置信依据时转忽略/人工，不能让模型无参考答案自由裁决。插件**永不自动拒绝入群申请**；只有管理员在 Page 明确驳回并通过实时权限/API 校验才真的拒绝。故「序每条群消息都调审核模型」不成立；审核针对启用的申请流程，内容审核则标为默认关闭且运行时未启用。（序/`README.md:63-75`、`README.md:241-258`、`README.md:401-420`）
- **作者明确**：序的 `identity.context_bridge_authorization@1.0` 只裁决这轮**能否读取另一作用域**，不读取正文也不发送。已绑定私聊→另一私聊、本人群聊发言→其私聊可弱关联；群→另一群拒绝；私聊→群默认拒绝。当前群消息明确同意「续私聊话题」仅 `topic_only`，明确同意公开具体内容才 `details`；同意只对当前消息有效，否定、假设、引用中的授权词等不算同意。言还限制必要片段、遮盖凭据。（序/`README.md:98-107`；言/`README.md:251-257`；言/`docs/recent-activity-context-design.md:67-77`、`docs/recent-activity-context-design.md:130-136`）
- **作者明确**：主动消息另用完整私聊 UMO 精确白名单，不因主人关系或自然人合并自动开放，也不接受群目标。这说明「认识这个人」「允许读取近期背景」「可以主动发给这个收件会话」是三个不同的授权问题。（序/`README.md:92-107`）
