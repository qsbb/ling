## 2. 系列整体设计哲学（本任务的总问题）

### 2.1 他为什么做这一整套：裸 LLM／裸 AstrBot 缺什么

- **作者明确（最直接的一句）**：言存在的理由，是让 AstrBot「像真人一样判断何时沉默、何时分段、被插话时如何自然衔接」（言/`README.md:3`）。
- **作者明确（缺陷清单，逐条列举）**：言把要消灭的行为写成一句：「bot 逢 @ 必回且永远精神饱满；换平台后丢失刚才话题；短追问丢失上一轮对象；多 bot 刷屏；打断群友对话；引用归属错乱；图片消息一刀切；重复客服式收尾；暴露工具机制词」（言/`README.md:40`）。
- **作者明确（序的否定对象）**：传统群管＝关键词正则＋规则表＋固定处罚，它要回答的是「bot 此刻以什么身份、能对谁做什么」（序/`开发文档.md:27-36`，历史草案，仅作动机证据）。
- **推断**：把这些并起来，裸 LLM 缺的是**一段会话中所有非语言的部分**——什么时候不说、说多长、被打断怎么办、以什么身份说、有没有声音、在不在场。人可以毫不费力地做到这些，LLM 本身一件都做不到。**系列就是为这些「做不到」逐项建仓。**

### 2.2 他想让 AI 角色成为什么

- **作者明确**：序的定位是「让 bot 在 QQ 群里像真实成员一样理解『自己是谁、对方是谁、双方是什么关系、当前能做什么』」（序/`README.md:3`）。
- **作者明确**：情的定位是记录关系状态，「并把语气、篇幅与主动性等关系表达约束注入 LLM 请求」，同时明确「它不接管发送、不生成内容、不授予权限」（情/`README.md:25`）。
- **作者明确**：临的定位是「让虚拟角色走进现实空间的具身桥接」（临/`README.md:5`）。
- **作者明确**：声的定位是系列的「语音模块」，「集中管理朗读触发、结构化分段、发送节奏、取消语义、输出清理和 TTS 后端」（声/`README.md:3`）。
- **推断**：他写下的不是「更聪明的助手」，而是一份**「人的构成清单」**：知道事（知）、在乎谁（情）、知进退（言）、守边界（序）、知冷暖和地（境）、有身体（临）、有嗓子（声）、能自我修复（核）。**这一整套的重心是「成为一个持续在场的存在」，而不是「把回答写好」。**

### 2.3 「拟人化」的具体判据：三层时间观

- **用户原话（经状态记录转述）**：「用户反馈：第二轮『注入即标注』对记忆层过于机械——人不会精确记得『什么时候学过什么』，与拟人化方向冲突。结论：**拟人 ≠ 没有时间感，而是『节奏层精确、记忆层模糊、表达层拟人』**。」据此回滚知与核的改动，「只有言按拟人化方案修订」（状态记录 `:99-103`、`:119`）。
- **作者明确的落地**：言的修订是「连发结论句去掉秒级起止时刻；隔夜标签用『凌晨／早上／上午／中午／下午／晚上／深夜』时段词替代 HH:MM；合并模板加表达纪律（**时间是感知不是台词**）」（状态记录 `:111`）。
- **推断**：这是全系列最像「哲学」的一条，因为它**主动放弃了更容易的做法**（给模型精确时间戳）。判据是分层的：机器要精确（4 秒还是 4 小时），人要模糊（「昨天」「很久以前」），**说出口的**必须自然。这一条直接贯穿到声（模拟「准备这一条语音所需的时间」，声/`README.md:75-80`）：节奏层精确、感知层自然。

### 2.4 贯穿全系列的同一把尺子：能力与意愿分离

- **作者明确**：序的第 2 条哲学「允许行动而非强制行动：工具可用只表示『可以做』，不代表『必须做』；是否执行由主对话 LLM 结合人设、情绪与上下文自主判断」；第 1 条「身份不等于授权」（序/`README.md:52-53`）。
- **作者明确**：情的对应条款「规则驱动数值：LLM 只接收表达建议，不允许直接修改关系数值」（情/`README.md:41`）。
- **作者明确**：声把同一条用在声音上——两种触发模式互斥，「概率模式不向 LLM 提供 TTS 工具，LLM 模式不执行概率自动 TTS」（声/`README.md:35`）。
- **作者明确**：核把同一条用在运维上——「检查可并发，写操作串行」，且可写状态只能进同一协调器（核/`README.md:32`）。
- **推断**：这四个模块各自用自己的方式执行同一条纪律：**代码只管「能不能」，模型管「想不想」**。声音上的「概率」正是这条纪律的折中产物（§4.1）。

> 注：合并前的另一份总览曾称裸基座的缺口「文档里没写」，与本小节出处（言/`README.md:40`、序/`README.md:52-53`、情/`README.md:41`）不符。**合并后以原文出处为准**，缺口确有逐条写明，本节保留完整引用。

### 2.5 还缺什么：他自己写下的天花板

- **作者明确**：系列插件是「宿主的租户」——运行在 AstrBot 进程内，不改 Core、不猴子补丁、不碰宿主私有对象（核/`CONVENTIONS.md:15`）。
- **作者明确**：境「不做生活日程」（核/`CONVENTIONS.md:35`）；八字的职责表里没有任何一个字承担「人格」或「她此刻的整体状态」。
- **实现核对**：状态记录记载一次全系列事故——系列插件普遍调用了一个 **AstrBot 中并不存在的方法**找对端实例，导致「核统一路由与插件间联动**从上线起一直静默失效**（fail-closed，不报错、日志仅 debug 级）」（状态记录 `:983`）。
- **推断**：这次事故正好点出这种结构最典型的代价：**没有主体，就最容易相信「看起来接上了」**。这不是巧合，而是「八个互不依赖的租户」这一形态的结构性风险，也正是 §6 讨论 ling 存在理由的起点。

## 3. 实际架构关系（枢不可用之后的真实情况）

### 3.1 三条真实存在的协作通道

**通道一：AstrBot 钩子优先级表——序列即架构**

- **作者明确**：规范固定了钩子槽位，并写明两条硬顺序：注入链「序(800) → 知(700) → 情(600) → 境(550) → 言(500)」，理由「身份与安全边界先于知识注入，知识先于对话收敛」；交付链「言(600) 先完成分段，声(400) 后做语音合成——语音必须拿到最终分段结果」。调整已占槽位等于破坏性变更（核/`CONVENTIONS.md:132-144`）。
- **推断**：这是系列**真正在跑的那层架构**——一张由数字表达的执行顺序表。它不需要任何中心组件，只要宿主按 priority 调用插件就成立。

**通道二：进程内版本化契约——调用方按插件 ID 取实例，先校验契约名与主版本**

- **作者明确**：「插件之间是进程内邻居，不是依赖方」：跨插件协作只走版本化契约，禁止 import 其他插件内部模块、禁止读写其他插件数据目录（核/`CONVENTIONS.md:16`）。跨插件调用「全部走 in-process 实例方法（`adapter.get_plugin_instance`），不经 HTTP、不依赖 dashboard 会话」（核/`CONVENTIONS.md:164`）。
- **作者明确**：已落地的契约：`series.diagnostics@1.0`（必选，核聚合）、`series.control@1.0`（配置接管）、`series.webui@2.0`（管理面板）、`series.model_router@1.0`（模型路由）、`active_learner.knowledge@1.0`（知→序）（核/`CONVENTIONS.md:166-252`、`CONVENTIONS.md:283-295`）。
- **实现核对**：`ningxin.request_context.v1` 是 6 个仓库各存一份字节一致副本的普通 dict，挂在 `event` extra 上；每插件只写自己分区，`phase` 只可单调前进（核/`CONVENTIONS.md:253-263`）。

**通道三：契约失效一律降级，各插件照常独立运行**

- **作者明确**：言「没有安装或没有启用『核』时，言仍照常完成对话调节，只是缺少统一日志查看入口」（言/`README.md:32`）；声「没有安装或没有运行『核』也没关系，语音合成、分段发送和外部 API 等功能都会照常工作」（声/`README.md:352`）；临「契约不可用或核未安装时……应继续隔离运行」（核/`README.md:155`）。
- **实现核对**：独立能力矩阵逐页核过 8 个 Page × 5 场景（核不存在／未加载／control 不可用／核 WebUI 不可用／diagnostics 不可用），结论是这些插件「都没有硬编码 `astrbot_plugin_update_manager` 或 `/api/series/`」，核缺席不会切断它们的 Page（核/`docs/STANDALONE-MATRIX.md:66-67`；原则见核/`docs/SERIES-CAPABILITY-PLAN-2026-09-14.md:13`、`:42`）。

### 3.1b 为什么必须是「显式、可版本化契约」——作者写下的两条历史教训

- **作者明确（教训一，duck-typing 静默失效）**：规范直写 0.x 时代曾靠 duck-typing 探测「知」的 `recall`，对端没实现时桥接**静默失效**、排查成本很高；因此现在要求契约名与 major 校验，不兼容即停用。出处：核/`CONVENTIONS.md:244-260`。
- **作者明确（教训二，热重载类身份冲突）**：跨插件传 Python 对象在热重载后会造成「同名不同类」的 `isinstance` 失败，所以统一请求上下文只放 **JSON 可表达的普通 dict**，并规定字段单写者。出处：核/`CONVENTIONS.md:244-260`。
- **推断**：这两条是「为什么不能随手 import 对方」的实证理由——不是洁癖，是**静默失效真的发生过**。它也给出 ling 可借鉴的纪律：领域之间只交换可序列化的普通数据 + 可解释的失败，不要让一个模块持有另一个模块的对象。

### 3.1c 「枢」的作者归属与清单陷阱

- **实现核对**：枢的 `metadata.yaml:7` 把 `author` 写作 `Justice-ocr`。其初始发起动机**文档里没写**，因此**不宜**表述为凌溪亲自从零设计该模块。出处：`astrbot_plugin_orchestration_hub/metadata.yaml:1-9`。
- **实现核对**：「仍在清单里」不等于「可用架构」：枢仍留在核的可信安装登记中（核/`core/trusted.py:86-89`），但审计层已把它列为忽略仓库（核/`core/series_audit.py:24`），规范解释这是「历史安装兼容」，并明确「按忽略决定不对其发起契约调用与治理操作」（核/`CONVENTIONS.md:163`）。

### 3.2 「没有中心调度器」的两条硬证据

- **实现核对**：临的运行态快照把 `orchestration_hub_resolver` 明确列在 `not_consumed`（未消费）清单里（临/`core/turn_orchestrator.py:2203-2208`）。**这是代码级的自述：这一环我没接。**
- **实现核对**：临的系列复用文档写明「具身客户端只连接 `astrbot_plugin_embodiment_bridge` 的 HTTP/SSE 接口；它不直接调用『知、言、序、情、境、声、核』」，所有复用都在 Bridge 后端、只消费显式声明的版本化契约，并逐条列出调用频率与失败行为（临/`docs/SERIES_INTEGRATIONS_CN.md:3-13`）。

### 3.3 所以应该怎样诚实描述

- **推断**：**系列 ＝ 8 个互不依赖的进程内租户 ＋ 一张钩子顺序表 ＋ 一组各自降级的契约。** 它没有总线、没有注册中心、没有编排层。增加一个模块的默认效果是「多一个同优先级的注入方」，而不是「接入一个整体」。
- **作者明确**：系列承认这条路线有硬上限——核明确「不做插件侧独立 WebUI／救援服务器」「不做第二控制台」「不猴子补丁 AstrBot 内部」，宿主缺失的能力一律转为上游提案（如公开 per-sender agent stop API，状态记录 `:144-146`）（核/`docs/SERIES-CAPABILITY-PLAN-2026-09-14.md:251-256`）。
- **作者明确**：原本确实设想过一个承担「服务注册与契约解析」的层（核/`docs/AI开发提示词.md` 与临/`docs/SERIES_INTEGRATIONS_CN.md:23` 写作时并存着相应表述，单字「枢」也「视为已分配，不得释放」，核/`CONVENTIONS.md:41`）。**但它尚未完成、当前不可用**，因此**当前没有任何插件经过它**——本文所有协作关系都不依赖它，也不以它为已实现架构。

## 4. 命名体系解读

- **作者明确**：展示名＝单汉字，单字唯一、一经分配不变；职责表逐字给出（核/`CONVENTIONS.md:27-39`）。
- **推断**：八字并排读，不是功能清单，而是一份「人」的构成表：

| 字 | 人的哪一部分 | 作者原话 |
|---|---|---|
| 知 | 知道的事 | 「可验证知识……不存私人情节」（核/`CONVENTIONS.md:31`） |
| 情 | 在乎谁 | 「情绪、好感、四维信任、熟悉度」（核/`CONVENTIONS.md:34`） |
| 言 | 何时开口、怎么开口 | 「沉默判断、分段、插话衔接、交付政策」（核/`CONVENTIONS.md:32`） |
| 序 | 能做什么、不能做什么 | 「身份与行动授权……最终否决权」（核/`CONVENTIONS.md:33`） |
| 境 | 身处何地、冷暖如何 | 「环境事实……不做生活日程」（核/`CONVENTIONS.md:35`） |
| 临 | 身体在哪里 | 「VR/MR 设备……动作意图、空间感知」（核/`CONVENTIONS.md:37`） |
| 声 | 嗓子 | 「双 TTS 后端、多音色、AI 语音导演」（核/`CONVENTIONS.md:36`） |
| 核 | 免疫／自愈 | 「更新与治理……配置接管」（核/`CONVENTIONS.md:38`） |

- **作者明确（核字的来历）**：「『核』代表系列插件的更新管理核心」（核/`docs/AI开发提示词.md:20`）。**推断**：这解释了为什么一个「更新器」能占 29k 行——它不是工具脚本，而是系列体内**负责自愈的那一层**，与面向用户的能力不在同一层级。
- **推断**：单字体系真正的功能是**强制职责正交**。一旦某功能横跨两个字，作者就必须在规范里写明谁是主谁是客——例如「语音必须拿到最终分段结果」就是把「说多少」判给言、把「怎么发声」判给声（核/`CONVENTIONS.md:142`）。
- **推断**：这套命名里**没有**「心」「魂」「我」「生活」「日程」任何一个字。人格被当作**不归任何插件所有**的东西（由宿主人设与主对话模型承担）。这条沉默，恰是 §6 全部讨论的起点。

## 5. 「声」「核」的设计意图与关键机制

### 5.1 声：一副存在但不一定使用的嗓子

**口径先校正**

- **实现核对**：后端选项是 `mimo` / `astrbot` / `fishaudio`，默认 `mimo`（声/`_conf_schema.json:2-7`、声/`core/config.py:52`）；README 能力与清单写「三 TTS 后端（MiMo / AstrBot / FishAudio）」（声/`README.md:23`）。**但 `metadata.yaml` 的 `short_desc` 仍写「双 TTS 后端」**——旧标签滞后于实现，引用时以配置三项为准。
- **作者明确（血统，关系到「谁原创」）**：声基于开源项目 `astrbot_plugin_mimo_tts_clone` 修改，「沿用原项目的 MiMo v2.5 voiceclone 接入、音色管理、**概率自动语音**、情绪路由、**AI 风格导演**、Pages 管理和插件服务能力」（声/`README.md:26`、`README.md:398`）。**推断**：概率触发与 AI 导演不是凌溪首创；他的增量在多后端切换、交付取消与契约、外部 API、发布纪律。

**为什么多后端**

- **推断**：多后端把「有没有嗓子」与「用什么嗓子」解耦：`astrbot` 直接复用用户已配置的 TTS，零额外成本；`mimo` 提供音色克隆（专属嗓音）；`fishaudio` 提供更强表现力与自建服务。动机亦有现实证据——配置项专门为「NAS 直连 `api.fish.audio` 被 DNS 污染或被 Cloudflare 拦截」预留代理（声/`_conf_schema.json:96`）。**这是「必须能在真实网络里活下来」的工程考虑，不是审美选择。**

**多音色解决什么**

- **实现核对**：音色解析优先级为「显式指定 → 情绪默认 → 用户默认 → 群默认 → 全局默认」（声/`core/voice_store.py:212-238`）。
- **推断**：五级优先级要解决的是**「同一个角色在不同关系里听起来可以不完全一样」**——对某人、某群、某种情绪可换音色。它服务于角色感，不是功能选项。

**AI 语音导演：让 LLM 决定怎么说，不动说什么**

- **作者明确**：「开启后，插件会先调用 AstrBot LLM，为待朗读文本生成一份隐藏的音频导演方案：`style_context` 会作为 MiMo `user` 消息参与合成，`speech_text` 只作为音频朗读文本使用。**最终聊天文字仍保持原样，不会被改写。**」（声/`README.md:193-195`）
- **作者明确（提示词原文）**：「`style_context` 只描述语气、节奏、情绪、停顿、亲近感、场景感，不要复述正文」；`speech_text` 可剔除「嗯、啊、呃、那个、就是说、然后呢」等填充词，用标点增加自然停顿，「**让朗读更像真人**」；且「必须保持原意，不要新增事实、承诺、称呼、表情、动作或解释」（声/`core/style_director.py:13-23`）。
- **实现核对**：默认关闭（`ai_style_director_enabled` 默认 `false`），注明「仅 MiMo 后端」「不会改变最终回复给用户的文字」（声/`_conf_schema.json:200-205`）；用 `voice_hub_speak` 工具直接给风格时跳过二次导演，避免二次改写（声/`README.md:155-157`）。
- **推断**：所以它不是「让 LLM 决定说什么」，而是**让它决定这段话该用什么口气念**——把「语言生成」与「表演指导」拆成两次判断。它是有成本的：README 明写「会额外消耗一次 LLM 调用」（声/`README.md:199`），默认关闭也证明作者认为它不是无脑常开项。

**概率自动语音：为什么是概率**

- **作者明确**：`tts_trigger_mode` 是唯一运行模式，二者互斥——`probability` 会「过滤 `voice_hub_speak`」并沿用 `auto_tts_probability`；`llm_decides` 则「向 LLM 保留唯一的 `voice_hub_speak`」，由其判断是否适合发语音，并「完全跳过概率自动 TTS」（声/`README.md:147-150`）。
- **实现核对**：门控顺序＝已处理→非概率模式→仅文字→无结果链→已有外部音频→非 LLM 结果→访问控制→（可选）LLM 朗读意愿 →概率抽取；概率分支为 `roll = random.random()`，`roll <= auto_tts_probability` 才转语音，并把 `roll` 与 `reason` 写入事件与 `request_context`（声/`main.py:1788-1826`、`main.py:1827-1849`）。
- **作者明确**：推荐 `0.1`–`0.3`，理由是「避免群聊中过度刷屏」；默认值 `0.0` 即关闭（声/`README.md:174`；声/`_conf_schema.json:339-343`、声/`core/config.py:19-20`）。
- **作者明确（中间档）**：`llm_tts_judge_enabled` 让主 LLM 在回复开头输出朗读意愿标记，「太长、含代码、羞耻尴尬或纯功能性内容会主动跳过」，未输出标记时**退回概率逻辑**（声/`_conf_schema.json` 的 `llm_tts_judge_enabled` hint；声/`README.md:175`）。
- **推断：为什么是概率，而不是总要或总不要。**
  1. **总要**＝语音变成有声播报：连「好的」都念出来，日常的沉默质感消失，且每条回复都叠加 TTS 成本与播放等待。
  2. **总不要**＝等于没有嗓子，用户感受不到它存在。
  3. **概率**给出的是**「有时会开口」的知觉**：同一类话，多数时候是文字，偶尔是声音。这正是「嗓子在，但不一定用」的体验结构——也就是「能力与意愿分离」（§2.4）在声音上唯一可低成本实现的形态。
  4. 概率**可审计**：每次决策都带 `roll` 与 `reason` 写入请求上下文，「为什么这次出声／没出声」事后可查（声/`main.py:1820-1849`），符合系列「可观测是功能」（核/`CONVENTIONS.md:19`）。
  5. 三档并存（概率／模型标记／模型工具）本身说明：**「谁来决定要不要出声」被他当成一个需要按场景调档的产品问题**，而不是一条应当写死的规则。

**这份设计想给出什么样的存在感**

- **作者明确**：声不注册任何 TTS 聊天命令，语音只经概率自动 TTS、`voice_hub_speak` 工具、Pages 试听或插件服务触发（声/`README.md:145`；核/`CONVENTIONS.md:61` 记「声：无聊天命令」）。**推断**：这是刻意的取舍——若用户能 `/朗读`，语音就成了功能；没有命令、只剩概率与模型判断，语音才更像生理现象。
- **作者明确（可被中断）**：声消费言的交付令牌，「用户在合成或分段发送期间补充新消息后，言会取消旧令牌；声在开始合成、每段合成完成、每段发送前后都检查状态，尚未发送的旧语音会停止发送，并将取消状态回传给当前 LLM；**声不会主动清空或终止整轮**」（声/`README.md:68-73`）。逐段发送还「按『每 1 秒语音等待多少毫秒』模拟 Bot 准备这一条语音所需的时间」（默认 700ms/秒），等待期间仍检查取消令牌，且「不额外发起一次 LLM 请求」（声/`README.md:75-80`）。
- **推断**：这两条说明他要的不是「语音输出通道」，而是**有延迟、会说到一半被打断、且不会因为被打断就乱掉的角色**。存在感里最容易被忽略的一层是：**能被中断，才像在场。**
- **作者明确（一副嗓子，多处使用）**：声对外提供 OpenAI 兼容 `POST /v1/audio/speech`（默认只监听 `127.0.0.1`），并给临 `voice.audio_output@1.0`（PCM16 WAV、60 秒超时、固定失败码、消费方只读不得删）（声/`README.md:32`、`README.md:257-300`）。**推断**：同一副嗓子服务聊天、具身设备与外部应用，是「角色只有一个声音」的工程化写法。

### 5.2 核：为什么一个「更新器」需要这么重

**为什么存在**

- **作者明确**：核是「安全、串行、可回滚的 AstrBot 插件更新管理器」（核/`README.md:3`），字义是「系列插件的更新管理核心」（核/`docs/AI开发提示词.md:20`）。
- **作者明确（边界）**：「仅管理 AstrBot 插件，不更新 AstrBot 本体、Python、Docker 镜像、操作系统或本插件自身」，「默认只检查；自动规则默认关闭」（核/`docs/AI开发提示词.md:39`）。

**为什么「冻结不可变计划」——普通更新不够吗**

- **作者明确**：「冻结不可变计划（TTL 有效期内），避免执行与预览漂移」（核/`README.md:31`）。
- **实现核对**：计划生成即固化了 `expires_at`（默认 TTL 900 秒）、`astrbot_version`、`catalog_fingerprint`、`rule_revision`、`policy` 与逐项 `items`，并对整体做稳定哈希（核/`core/planner.py:30`、`planner.py:100-130`）；执行前校验会以 `PLAN_EXPIRED`、`ASTRBOT_VERSION_CHANGED`、`RULE_REVISION_CHANGED`、`CATALOG_CHANGED` 拒绝，并逐项比对 `fingerprint`（核/`core/planner.py:132-157`）。
- **推断**：普通「点更新」把**决策与执行压在同一瞬间**；冻结计划把二者拆开，使「我看到的是这些、即将更新的也是这些」成为可验证的不变量。这解决的不是「更新会不会失败」，而是**「更新的是不是我批准的那件事」**。对一个人同时维护 8 个会被远端推送新版本的插件，这是真实风险。

**串行与事务边界**

- **作者明确**：「经 AstrBot 核心串行更新，单事务加文件租约锁，杜绝并发」；检查可有限并发，但「任何会改变插件状态的安装、更新、启停、重载和回滚仍统一进入同一更新协调器」（核/`README.md:32`）。
- **实现核对**：协调器同时持进程内 `asyncio.Lock` 与文件租约锁，冲突分别以 `PROCESS_LOCKED` / `FILE_LOCKED` 拒绝；取消只「在下一事务边界停止批次」（核/`core/coordinator.py:31-34`、`coordinator.py:51-62`、`coordinator.py:68-97`）。

**自动回滚＋健康检查：他在担心什么**

- **作者明确**：「更新前自动备份，更新后执行加载／版本／启用状态检查；声明 `plugin.health@1.0` 的插件还会执行业务健康检查，**失败自动回滚**」（核/`README.md:34`）。
- **实现核对**：事务状态机 `LOCKED → BACKED_UP → CORE_UPDATE_RUNNING → HEALTHY → COMMITTED`；任一步异常即 `FAILED`，有备份则进入 `ROLLING_BACK`，成功为 `ROLLED_BACK`（并留诚实警告「代码已回滚；共享 Python 依赖可能已变化」），失败为独立的 `ROLLBACK_FAILED`（核/`core/transaction.py:205-275`）。
- **实现核对**：健康检查是五道关——插件不存在、版本不符、启用状态变化、业务探针失败（含契约不兼容／畸形／探针异常）、业务自评不健康（判定条件 `status != "ok" or not all(checks.values())`）（核/`core/health.py:26-96`）。
- **实现核对**：回滚自身也受检——备份必须在 data 范围内且非符号链接、回滚前用清单 `digest` 校验（不符即 `BACKUP_DIGEST_MISMATCH`）、旧目录移入 `failed/` 而非删除、**回滚后仍要再跑一次健康检查**（失败即 `ROLLBACK_HEALTH_FAILED`）（核/`core/transaction.py:169-197`）。
- **推断：他担心的其实是三件事。**
  1. **「装上去就不吭声」。** 插件更新后加载失败，AstrBot 未必会喊；若没有健康检查，机器人只是悄悄少了一项能力，可能几小时无人察觉。这正是为何用 `BUSINESS_HEALTH_UNHEALTHY` 而不只是「能否 import」。
  2. **「回滚到一半，比不回滚更糟」。** 因此校验 digest、坏版本留档、回滚后再验，并明写「共享依赖可能已变化」——他清楚回滚**不能**承诺完全复原。
  3. **「自己把自己搞坏」。** 核禁止自更新与自停用（核/`README.md:37`）；数据必须写 data 目录而非插件目录，因为「核的自更新会在运行中替换插件目录」（核/`CONVENTIONS.md:92`）。

**它和其余插件是什么关系、给谁用**

- **作者明确**：核是**可选增强**、不是运行依赖——「standalone 优先：没核时每个插件 Page 必须完成全部配置／上传／预览／管理动作；managed 是增强不是替代」（核/`docs/SERIES-CAPABILITY-PLAN-2026-09-14.md:42`）；状态记录亦记「核是可选增强，standalone 是默认运行态」（状态记录 `:185`）。
- **作者明确**：核向系列供给三类能力——① 生命周期治理（检查／计划／更新／回滚／备份／健康）；② 统一模型路由 `series.model_router@1.0`（声的导演与 TTS 都按「插件显式配置 → 核 → AstrBot 原生」解析，声/`README.md:344`）；③ 诊断聚合与配置接管（`series.diagnostics@1.0`、`series.control@1.0`）。
- **用户原话（经状态记录转述）**：「Pages 面板保留，只装一个插件时可用；装核后核通过 `series.webui` 统一接管，**不代理原生 Page API**」（状态记录 `:186`）。**推断**：这句话钉死了核的定位——它是**控制台**，不是**中间层**；它不转发业务流量，故其有无不改变角色行为。
- **作者明确的诚实边界**：只做备份、不含恢复（核/`README.md:36`）；手工回滚只接受 `COMMITTED` 事务且要求当前版本仍等于 `to_version`（核/`core/transaction.py:298-334`）；清理时「永不删除唯一恢复点」（核/`core/transaction.py:396-401`）。
- **推断**：核的 29k 行买到的不是「更新更快」，而是**「改动可以被安全地试一次，并且能被原路退回」**。对一个人维护八个会互相注入 prompt 的插件，这不是运维奢侈品，而是敢改的前提。

## 6. 与 ling 的关系

### 6.1 不是「服务端替代」，而是同一理念的两层

- **作者明确（ling 侧）**：ling 是「一个**独立运行的拟人化 AI 角色系统**」，「QQ、微信、Web 控制台、移动端都只是**连接到她的渠道**，**她本身不依赖任何第三方机器人框架运行时**」（ling/`README.md:3-10`）。
- **作者明确（系列侧）**：所有系列插件都是「宿主的租户」，运行在 AstrBot 进程内，不改 Core（核/`CONVENTIONS.md:15`）。
- **推断**：二者不是替代关系。系列回答的是「**在别人的框架里，能把一个 bot 修剪到多像人**」；ling 回答的是「**如果她就是主体，系统该长什么样**」。系列已经把「在 AstrBot 内能做到什么程度」按 8 个正交维度验过一遍；ling 是在问「去掉这个框架的天花板之后，还剩哪些必须由她自己拥有」。

### 6.2 系列做不到、ling 能做到的

| # | 系列的上限（作者明确／实现核对） | ling 的对应能力 | 出处 |
|---|---|---|---|
| 1 | 说话时机依附**钩子**：只在被唤醒的一轮请求内获得决策机会 | 「注意」是独立一层——消息先进注意，再谈处理；注意力是稀疏且有选择性的 | 核/`CONVENTIONS.md:16`、`:134`；ling/`docs/ATTENTION-DESIGN.md:32-49` |
| 2 | 「发不发」是**回复附近的单点判定**（概率／沉默标记／门控） | 「能否做」与「想不想做」彻底分开，且**发送前再查一次**授权／受众／能力／时效 | ling/`docs/AUTONOMY-DESIGN.md:50-52`、`:78-83` |
| 3 | **没有日程与生活**：境明写「不做生活日程」 | 有自己要做的活动与精力状态，「不是随时待命」 | 核/`CONVENTIONS.md:35`；ling/`README.md:30` |
| 4 | 记忆是**插件级**：跨插件只靠 `request_context` 传片段，无统一生命周期 | 短期／长期／核心分层，会遗忘、会撤回、会修正，来源可追溯 | 核/`CONVENTIONS.md:31`；ling/`README.md:29` |
| 5 | 跨插件**无中心**：曾因用了不存在的方法而「从上线起一直静默失效」 | 20 个领域＋13 份 v1 契约＋单一真源，改动先改契约 | 状态记录 `:983`；ling/`README.md:37`、`:139-147` |
| 6 | 交付依赖宿主：能停「尚未发出的」语音，但「已经发送的音频无法撤回」，也无法终止 Provider 端推理 | 「不假装送达」：无回执不记成功，失败分四类，不确定的去对账 | 声/`README.md:72-73`；ling/`README.md:34-35` |
| 7 | **人格不在插件里**：八字表中无人承担人格，「她此刻的整体状态」无归属 | 人格是领域之一；「情绪影响的是回复意愿和简短程度，怎么表达由人格决定，不写死在代码里」 | 核/`CONVENTIONS.md:29-39`；ling/`README.md:28` |

- **推断**：这张表最关键的不是 1、2 两条「实现差距」，而是 **5 与 7**。系列证明了一件结构性的事：**用插件拼「像人」，天花板被「租户模型」锁住**——插件之间只能互相注入 prompt 片段、读取对方声明的契约，**谁都无法拥有「她此刻是什么状态」**。而这恰是拟人化的第一要件。状态记录里那次联动静默失效（状态记录 `:983`），就是这种结构最容易付出的代价。

### 6.3 如果只能抄三件事（只从可用插件里选）

**第一件：声的「可取消交付」——把「说到一半被打断」当成一等公民**

- **抄什么**：表达不是「生成完再发」，而是**分段＋令牌＋在合成开始、每段完成、每段发送前后检查取消**；被打断时只停掉未发出的部分，**不终止整轮、不撤回已发内容**，并把取消状态**交回模型**由它决定继续／重说／结束（声/`README.md:68-80`）。
- **为什么**：三条判据都很硬且可直接移植——**取消是局部行为**（只作用于未交付之段）、**状态要交回**（交付层不替模型做决定）、**不额外调模型**（不为取消付一次推理）。这正好落在 ling 的「能否做／想不想做」分离上：取消属于「能否」，续说什么属于「想不想」。
- **注意**：声自己写明已发音频无法撤回、Provider 端推理无法终止（声/`README.md:72-73`）。移植时**不要把「取消」承诺成「撤回」**。

**第二件：核的「冻结计划＋失败必回滚＋回滚也要验」**

- **抄什么**：① 决策与执行分离——计划带 TTL、目录指纹、规则修订，执行前逐项校验，任一变化即拒绝；② 事务状态机显式、每步落审计；③ 失败自动回滚，回滚前校验备份 digest、坏版本留档不删、**回滚后仍要跑健康检查**；④ 诚实的残留说明（「代码已回滚；共享 Python 依赖可能已变化」）（核/`core/planner.py:100-157`；核/`core/transaction.py:205-275`、`transaction.py:169-197`）。
- **为什么**：ling 自己写着「真实 Docker 上的升级／回滚演练**尚未完成**，不要把自动更新当成已验证能力」（ling/`README.md:67-69`、`:178-180`）。核提供的是一整套**「更新是危险操作」的仪式**，含「默认关闭」「只管理插件不管理本体」「拒绝自更新」等边界（核/`docs/AI开发提示词.md:39`、核/`README.md:37`）。对 ling 尤其可用的，是**「回滚不等于复原」**这条诚实原则——可直接并入它已有的「不假装送达」。

**第三件：言的「硬门在前、语境判断在后」的沉默分层**

- **抄什么**：先由**本地规则**做不可协商的硬门——明确求助／紧急消息绝不被硬静默（情/`README.md:43`）、群聊读空气命中滑窗上限时直接不发起 LLM；再由**主模型在同一次请求内**判断自然收口（`<SILENCE/>`）；只有显式选择时才另开轻量预判（言/`README.md:40`；言/`core/silence_judge.py:153-166`）。同时要求「连续静默有上限」（情的 `mood_max_consecutive_silences` 默认 2）。
- **为什么**：ling 已有注意力分层，但还缺一层判据——**哪些沉默是可以的，哪些沉默等于功能失败**。系列的答案很具体：静默不能吞掉紧急求助与命令；「忽略」与「没看见」在状态上必须分开（ling/`docs/AUTONOMY-DESIGN.md:53`）。
- **注意**：言的默认 `silence_strategy=inject` 仍发生在「已经看过这条消息」之后，**不能当作 ling 的注意力层**——这与同批文档「不该抄：用 `<SILENCE/>` 代替注意力层」的结论一致。

**落选三项及理由（避免误抄）**

- **声的概率自动语音**：它是「没有更好的语境判断时」的折中，而 ling 的目标正是「让模型在边界内自己判断」。可借其**三档结构**（规则概率／模型标记／模型工具），不宜把「概率」当默认。
- **核的配置接管 `series.control@1.0` 与 WebUI 聚合**：解决的是「8 个独立插件如何被一个控制台统一管理」。ling 是单体，该问题不存在；强行引入只会得到第二套配置真源。
- **境／临／知的整体移植**：各自绑定 AstrBot 的平台事实（OneBot 群 role、Quest 传输、插件级 scope）。只借机制，不借状态机与题库。

## 7. 一页结论

1. **系列为什么存在**：裸 LLM 能决定「回什么」，不能决定「何时不回、怎么说话、以什么身份说、有没有声音、在不在场」。八个单字就是把「不像人」的部分逐项拆开来建仓（言/`README.md:3`、`:40`；序/`README.md:52-53`）。
2. **它的真实架构**是一张钩子顺序表（序800→知700→情600→境550→言500；交付链言600→声400，核/`CONVENTIONS.md:134-142`）＋一组各自降级的进程内契约；**没有中心调度器**，原本设想承担该职责的枢**尚未完成、当前不可用**（临/`core/turn_orchestrator.py:2206` 记其为未消费）。
3. **命名体系是「人的构成表」**：知／情／言／序／境／临／声 对应知道什么、在乎谁、怎么开口、能做什么、身处何境、身体何在、嗓子如何；核是自愈层（核/`docs/AI开发提示词.md:20`）。表里没有「人格」与「生活」——这是刻意的留白，也是 ling 的起点。
4. **声**要的不是「能出声」，而是「嗓子存在但不一定用」：默认关闭、推荐 0.1–0.3 的概率触发（声/`README.md:174`）、导演只改口气不改内容（声/`README.md:193-195`）、被打断只停未发之段且不终止整轮（声/`README.md:68-80`）。
5. **核**要的不是「能更新」，而是「批准的那件事被原样执行，坏了自己退回去」：冻结计划防漂移（核/`README.md:31`）、串行事务、业务健康检查、自动回滚、**回滚后仍再验**（核/`core/transaction.py:169-275`）。
6. **他最核心的一句话**是「拟人 ≠ 没有时间感，而是节奏层精确、记忆层模糊、表达层拟人」（状态记录 `:102`），由此派生出「时间是感知不是台词」（`:111`）。
7. **他的工程纪律**是四句：代码定边界、模型定意愿（序/`README.md:52-53`；情/`README.md:41`）；禁止「看起来已接管」（核/`docs/SERIES-CAPABILITY-PLAN-2026-09-14.md:47`）；standalone 优先、核是增强不是替代（同文件 `:42`）；插件是宿主的租户（核/`CONVENTIONS.md:15`）。
8. **与 ling 的关系**不是替代：系列在框架里把 bot 修剪得像人，ling 把「她本人」当作主体。系列结构里没有「日程、生活、人格、整体状态」的位置（核/`CONVENTIONS.md:35` 明写境「不做生活日程」），而这些恰是 ling 必须自己拥有的东西。
9. **系列暴露的天花板**是租户模型：插件只能互相注入 prompt 片段、读对方声明的契约，谁都不持有「她此刻的状态」；那次全系列联动「从上线起一直静默失效」（状态记录 `:983`）就是这种结构最容易付的代价。
10. **给 ling 抄三件**：声的**可取消交付**（局部取消＋状态交回＋不额外调模型）、核的**冻结计划与失败必回滚（含回滚后再验与诚实残留）**、言的**硬门在前／语境判断在后的沉默分层**（紧急求助永不被静默、连续静默有上限、「忽略」≠「没看见」）。三者只借机制，不借平台耦合与状态机。
