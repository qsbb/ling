# 晚回失败兜底文案设计：让「没答上」也像她说的话

调研日期：2026-11-11。本文设计 ling 的**延后回复（deferred reply）失败兜底**。现状是一句写死的常量，换谁都一样，不像她。

---

## §0 结论先讲

1. **现状**：`src/ling/worker.py:1263` 写死了一句 `DEFERRED_FALLBACK_TEXT = "刚才想晚点回你，但没能及时整理好；你刚才的问题我还没有回答。"`，所有场景、所有用户、群聊私聊，都用这一句。
2. **它现在是对的，但不够像人。** 代码注释（`worker.py:1252-1262`）明确要求：只陈述**可核实的事实**，不说「我马上回」「刚才在忙」这类无从核实的话，更不能暗示已送达。这个约束**必须保留**——它比"像她"更重要。
3. **核心设计判断：不改"事实骨架"，只改"说法"。** 兜底句包含两个不可动摇的事实命题：① 我之前说过要晚点回；② 我没能答上。这两条必须永远在场。可变的只有：语气、长度、是否提到"我在做什么"、群聊还是私聊的措辞。
4. **推荐做法：模板 + 受约束的模型改写，而不是纯模型生成。** 纯模型生成有编造风险（"刚才在整理你给我看的那段视频"——她并不知道是什么），而且失败时模型本来就不可用。**模板保证事实，模型只负责让它像她**；模型不可用就退回模板。
5. **群聊和私聊必须不同。** 群聊里"没能及时回你"是当着所有人的面承认延迟，措辞要更轻、更不占用公共注意力；私聊可以更贴近、更交代。
6. **被抢占（`cancelled`）时一个字都不发。** 这条现已在 `worker.py:1578-1592` 正确实现，注释写得很清楚：新轮已经把旧输入一起处理了，再补一句就是"插进新话题的迟到补话"。**本设计不改变这个行为。**

---

## §1 什么时候该有兜底

代码里 deferred 的终点有四种，必须分开对待（`worker.py:1402-1494`）：

| outcome | 触发原因 | 该不该发兜底 | 现状 |
|---|---|---|---|
| `delivered` | 正常生成并送达 | 不需要 | ✅ 对 |
| `cancelled` | `PREEMPT_REASON_NEW_INPUT`（用户又来消息了）、`blocked`（授权失效） | **绝不发** | ✅ 对（`worker.py:1578-1592`） |
| `failed` | `model_router_unavailable`（`:1402`）、`generation_timeout`（`:1476`）、硬截止到期 | **发** | ✅ 发 |
| `expired` | 超过硬截止仍无结果 | 发 | 走 failed 路径 |

**关键区分**：`cancelled` 与 `failed` 的差别不是"成功/失败"，而是**"用户是否还在等这个答案"**。
- `cancelled` 意味着用户已经用新消息把话题推进了，旧问题作废 → 补一句是骚扰。
- `failed` 意味着用户问了一个问题，她答应了要答，最后没答上 → 不补一句是失信。

**建议补充一条**：如果 `cancelled` 的原因是 `blocked`（授权失效、权限被撤销），也不要发。理由同上——系统状态问题不该让用户承担。

## §2 兜底内容怎么产生

### 2.1 方案对比

| 方案 | 像她 | 不会编造 | 失败时可用 | 结论 |
|---|---|---|---|---|
| A. 固定模板（现状） | ❌ | ✅ | ✅ | 保底 |
| B. 纯模型生成 | ✅ | ❌ | ❌（模型本来就挂了） | **不可取** |
| C. 模板骨架 + 模型改写语气 | ✅ | ✅ | ✅（降级到 A） | **推荐** |
| D. 多个模板随机选 | 一般 | ✅ | ✅ | 可作为 C 的降级 |

**为什么 B 不可取**：兜底发生的前提就是模型调用失败（`model_router_unavailable`）或超时（`generation_timeout`）。此时再去调模型，大概率再失败一次；即使成功，模型也可能编造"我刚才在做什么"。这违反本项目「拿不到就留空，绝不编造」的铁律。

### 2.2 推荐架构（C）

```
事实骨架（代码决定，不可变）
   ├─ 我说过要晚点回      ← 真实（她登记过 deferred）
   ├─ 我没能答上          ← 真实（生成失败/超时）
   └─ 我不承诺何时答       ← 约束
        ↓
风格参数（代码决定）
   ├─ 场景：私聊 / 群聊
   ├─ 失败原因：超时 / 模型不可用 / 硬截止
   └─ 语气档位：从人格配置读取
        ↓
模板渲染（确定性）→ 得到候选句
        ↓
（可选）模型改写：只允许改语气词与语序，不许增删事实
        ↓
事实校验：改后文本必须仍包含两个事实命题 → 否则丢弃，用模板原文
```

### 2.3 模型改写的硬约束

如果决定启用模型改写（`DEFERRED_FALLBACK_REWRITE_ENABLED`，默认 **false**）：

- **输入**：模板句 + 人格语气描述 + 场景。**不输入**原始用户问题（避免模型顺着内容编造"我刚才在想你说的那件事"）。
- **输出**：≤ 60 字。
- **校验（必做，不通过就丢弃）**：
  1. 不得出现**未经证实的具体内容**：时间承诺（"马上"、"一会儿"）、原因归因（"刚才在忙"、"网络不好"）、已送达暗示（"你看到了吗"）。
  2. 必须保留"没答上"这个语义。
  3. 不得引入用户问题中的实体。
- **超时**：3 秒。超时直接用模板。
- **频次**：同一窗口每天最多改写 N 次（建议 3），避免失败时反复调模型。

**实现上建议**：把改写做成**离线预生成**——睡眠期用当前人格批量生成若干条候选，缓存起来；兜底时直接从缓存挑。这样兜底路径**永远零模型调用**，既满足"零模型"的既有约束（`worker.py:1240-1243` 的注释强调定时扫描必须零模型），又能得到个性化文案。

### 2.4 要不要带上"原本想说什么"

**不带。** 三个理由：

1. **不可得**：失败时原文根本没生成出来（超时）或生成被中断（部分文本可能不堪用）。
2. **有害**：半截文本如果是错的，说出来就是把错误送出去。
3. **不像人**：人不会说"我刚才想说但是没说完，我本来打算说……"。

**唯一例外**：如果中断时**已经拿到了完整的语义**（例如生成成功但投递失败），那不属于本兜底场景，应该走重投递而不是兜底。

## §3 分场景措辞

### 3.1 私聊

| 失败原因 | 建议措辞（事实骨架 + 风格） | 说明 |
|---|---|---|
| `generation_timeout` | 「刚才说要晚点回你，结果没整理好。你刚才问的事我还没答上，等下再跟你讲。」 | 承认延迟，不承诺具体时间 |
| `model_router_unavailable` | 「刚才想晚点回你，但没接上。你问的事我还记着，没答上。」 | "没接上"比"系统故障"自然 |
| 硬截止到期 | 同现状那句（已是最保守的版本） | 保留为最终保底 |

**私聊的语气要点**：
- 可以用"你"，可以稍微示弱（「没整理好」「没接上」）。
- 必须**明确承认没答**，不能含糊过去。
- 不承诺时间（不写"马上""一会儿"）——无法核实。

### 3.2 群聊

| 失败原因 | 建议措辞 | 说明 |
|---|---|---|
| `generation_timeout` | 「刚才说要晚点回，结果没整理好，回头再说。」 | 更短、更轻，不占用公共注意力 |
| `model_router_unavailable` | 「刚才那句话我还没能答上，等下补。」 | 不点名具体是谁，避免把某人架在公共场合 |
| 硬截止到期 | 「刚才要回的还没答上，回头补。」 | 最短 |

**群聊的语气要点**：
- **更短**。群聊里长句子是负担。
- **不点名**。私聊细节不该在群里复述（哪怕只是"你问的那个事"）。
- **不示弱过头**。群聊场合过度道歉会显得奇怪。

### 3.3 一条额外的边界

如果原问题涉及**隐私/敏感内容**，群聊兜底**绝不能**提及问题内容，哪怕是模糊指代。用最泛化的一句（「刚才要回的还没答上」）。

## §4 与人格系统的关系

**从人格配置读取什么**：
- 语气档位（正式/随意/黏人）
- 自称（我 / 人家 / 名字）——注意本项目有"她"的设定
- 句尾习惯（是否用句号、是否用语气词）

**不要从人格配置读什么**：
- 不要为"兜底"单独写一套人格。兜底句应该像是**同一个人的另一句话**，不是另一个人设。
- 不要让兜底句带上情绪表演（"我好难过没能回你"）——失败是系统问题，不该演成情感事件。

## §6 风险

1. **改写引入编造**。这是最大风险，靠 §2.3 的事实校验挡住；校验不过一律回落模板。
2. **兜底变成常态**。如果 `model_router_unavailable` 频繁发生，用户会反复看到道歉句，体验比沉默更差。应监控 `deferred_fallback_used` 事件（已有，`worker.py:1626`）的频率，超过阈值应告警而不是继续发。
3. **群聊刷屏**。若一次会话里多条 deferred 同时失败，会连发多条。建议同窗口在 N 分钟内只发一次兜底。
4. **与"晚回"本身的关系**。兜底文案要基于**她确实说过"等会儿"**这个前提（代码注释已强调）。如果 deferred 不是用户可见的承诺（比如内部重试），就不该有兜底句。
